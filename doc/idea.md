# TracePhone 아이디어 기록

이 문서는 TracePhone 프로젝트의 **아이디어와 의사결정 과정**을 시간순으로 누적한다.
확정된 설계 내용은 `doc/design.md`에 따로 정리한다.

---

## 2026-09-03 — 프로젝트 출발

### 목적

휴대폰에서 사용된 데이터의 **누적치**를 확인한다. 구체적으로는

- 어떤 앱이 데이터를 얼마나 썼는지 **앱별로** 확인한다.
- 그 데이터가 **모바일 데이터**였는지 **Wi-Fi**였는지 구분한다.
- 하루치가 아니라 **장기간 누적**으로 본다.

### 왜 필요한가

Android 설정에도 데이터 사용량 화면이 있지만 두 가지 한계가 있다.

1. 대체로 **현재 청구 주기**만 보여준다. 그 이전과 비교하기 어렵다.
2. 시스템이 보관하는 상세 이력 자체가 영구적이지 않다. 기기에 따라 다르지만 **수 주에서 90일 정도**가 지나면 사라진다.

즉 "지난 반년 동안 이 앱이 모바일 데이터를 얼마나 먹었나"는 지금 확인할 방법이 없다.
이 공백을 메우는 것이 TracePhone의 존재 이유다.

## 결정 근거

### 1. 왜 Android 전용인가

앱별 네트워크 사용량은 Android의 `NetworkStatsManager` API로만 얻을 수 있다.
**iOS는 앱별 데이터 사용량 조회를 OS 차원에서 제공하지 않는다.** 우회 방법도 없다.
따라서 크로스 플랫폼을 고민할 여지 자체가 없고, 처음부터 Android 전용으로 간다.

### 2. 왜 Flutter가 아니라 네이티브인가

Flutter로 만들어도 데이터 수집부는 결국 Kotlin 플랫폼 채널로 작성해야 한다.
핵심 로직이 어차피 Kotlin이라면 Dart 계층을 하나 더 얹는 것은 순수한 추가 복잡도다.
UI 재사용 이득도 없다 — iOS에서는 이 앱이 성립하지 않으므로.

→ **Jetpack Compose 기반 Android 네이티브**로 결정.

### 3. 왜 조회만으로는 부족한가

시스템 통계의 보관 기간이 유한하다는 점이 핵심이다.
조회 전용 앱을 만들면 시스템이 지운 과거는 영원히 볼 수 없다.

→ **주기적으로 스냅샷을 떠서 자체 DB(Room)에 누적**한다.
   이것이 이 앱이 시스템 설정 화면과 다른 유일하고 결정적인 지점이다.

### 4. 왜 알림은 지금 넣지 않는가

"누적치를 확인한다"는 목적에 알림은 필수가 아니다.
월 목표치 설정 UI, 알림 채널, 권한(`POST_NOTIFICATIONS`), 초과 판정 로직이 한 번에 딸려온다.
핵심 기능이 실기기에서 정확한 값을 내는 것을 먼저 확인한 뒤에 판단한다. (YAGNI)

## 검토했다가 접은 선택지

### ADB 기반 PC 도구 (C# 또는 Python)

폰을 USB로 연결해 `adb`로 통계를 덤프하고 PC에서 분석하는 방식.

- 장점: 폰에 앱을 설치하지 않아도 된다.
- 접은 이유: **상시 수집이 불가능하다.** 장기 누적이 목적인데 PC에 연결한 순간에만 데이터를 가져올 수 있으면 목적을 달성하지 못한다. 개발자 모드 상시 활성화도 부담이다.

### 실시간 트래픽 모니터링 (VPN 서비스 방식)

`VpnService`로 패킷을 가로채 실시간 집계하는 방식.

- 접은 이유: 배터리 소모가 크고, VPN 슬롯을 점유해 실제 VPN과 공존할 수 없다. `NetworkStatsManager`가 이미 OS 차원에서 정확한 집계를 제공하므로 얻는 것에 비해 대가가 너무 크다.

## 기술 조사 메모

구현 시 반드시 알고 있어야 하는 제약 세 가지.

### `PACKAGE_USAGE_STATS`는 일반 런타임 권한이 아니다

`requestPermissions()`로 받을 수 없다.
매니페스트에 선언하되, 실제 허용 여부는 `AppOpsManager.checkOpNoThrow(OPSTR_GET_USAGE_STATS, ...)`로 확인하고,
허용되지 않았으면 `Settings.ACTION_USAGE_ACCESS_SETTINGS` 인텐트로 시스템 설정 화면에 사용자를 보내야 한다.
(조사 당시에는 `unsafeCheckOpNoThrow`가 권장 API였으나 API 37에서 다시 뒤집혔다. 아래 2026-09-03 첫 빌드 항목 참고.)
**사용자가 거기서 직접 스위치를 켜야 한다.** 앱이 대신 켤 수 없다.

### 시스템이 주는 값은 "그 날의 누적치"이지 증분이 아니다

같은 날짜를 두 번 조회하면 같은(또는 더 커진) 값이 나온다.
DB에 넣을 때 **더하면 중복 집계가 된다.** 반드시 덮어쓰기(upsert)여야 한다.
→ 이 프로젝트에서 가장 실수하기 쉬운 지점. 회귀 테스트 항목으로 못박아 둔다.

### UID는 앱과 1:1이 아니다

- `sharedUserId`로 여러 패키지가 한 UID를 공유할 수 있다 (`getPackagesForUid()`가 배열을 반환하는 이유).
- 특수 UID가 섞여 들어온다: `UID_TETHERING`(-5), `UID_REMOVED`(-4), `UID_ALL`(-1).
- 제거된 앱의 UID는 이름 매핑이 실패한다.

→ 매핑 실패는 예외가 아니라 **정상 상황**으로 다룬다. "제거된 앱 (uid 10234)" 같은 대체 라벨을 붙인다.

## 2026-09-03 — 초기 구현 완료

설계를 `doc/design.md`에 확정하고 전체 골격을 구현했다.

### 만든 것

| 계층 | 내용 |
|---|---|
| `core` | `AppLog`(로그 형식 통일), `SyncConstants`(주기·백필 일수), `ByteFormatter`(바이트 → "1.24 GB") |
| `domain` | `UsageBytes`, `AppUsage`, `UsagePeriod`, `NetworkKind` 등 순수 Kotlin 모델 / 저장소·권한 인터페이스 / 유스케이스 4종 |
| `data` | `NetworkStatsDataSource`(시스템 조회), `UsagePermissionChecker`(AppOps), `AppIdentityResolver`(UID→이름), Room 3종, `UsageRepositoryImpl` |
| `work` | `DailyUsageSyncWorker`, `UsageSyncScheduler` |
| `ui` | 권한 화면 / 요약 화면 / 앱 상세 화면 + 재사용 컴포넌트 4종 |
| 테스트 | 단위 5개 파일, DAO 계측 1개 파일 |

### 구현 중 새로 내린 결정

**1. 상세 화면에 기간을 인자로 넘긴다**

요약 화면에서 '이번 달'을 보다가 앱을 눌렀는데 상세가 다른 기간을 보여주면 수치가 어긋나 보인다.
경로를 `app_detail/{uid}/{period}`로 두어 기간을 그대로 이어받게 했다.

**2. '전체 누적' 기간의 일자별 추이는 실제 기록 시작일부터 그린다**

전체 누적의 시작일을 1970-01-01로 두었는데, 이를 그대로 일자별로 채우면 빈 점이 2만 개 생긴다.
저장된 가장 오래된 기록 날짜부터만 채우도록 `UsageRepositoryImpl.fillMissingDates`에서 범위를 좁혔다.

**3. 즉시 동기화는 KEEP 정책을 쓴다**

`REPLACE`로 두면 화면을 빠르게 오갈 때 직전 작업이 계속 취소되어 아무것도 완료되지 않는다.
이미 대기 중인 작업이 있으면 그것이 끝나기를 기다리게 했다.

**4. 앱 아이콘은 Coil 없이 직접 로드한다**

앱 아이콘은 `PackageManager`가 주는 `Drawable`이라 네트워크 이미지 로더가 할 일이 없다.
의존성을 하나 줄이고 `produceState` + 프로세스 캐시로 처리했다.

**5. 파괴적 마이그레이션을 쓰지 않는다**

이 DB의 누적 기록은 시스템이 지운 뒤에도 남는 유일한 자산이라 한 번 잃으면 복구할 수 없다.
`fallbackToDestructiveMigration()`을 의도적으로 설정하지 않았다.

### 아직 확인하지 못한 것

이 PC에 **Android SDK와 Gradle이 설치되어 있지 않아 빌드와 테스트를 실행하지 못했다.**
JDK 17(Temurin)만 확인되었다. Android Studio 설치 후 첫 빌드로 컴파일을 검증해야 한다.

`gradle-wrapper.jar`은 바이너리라 생성할 수 없었다. Android Studio가 프로젝트를 열 때
래퍼를 만들어 주거나, Gradle이 설치된 환경에서 `gradle wrapper`로 생성하면 된다.

### 다음에 할 일

1. Android Studio에서 프로젝트를 열어 Gradle 동기화와 첫 빌드 통과 확인
2. `./gradlew test` — 단위 테스트 통과 확인
3. 실기기 설치 후 `doc/design.md` 10절의 수동 검증 6항목 수행

## 2026-09-03 — 빌드 툴체인을 AGP 9로 결정

Android Studio 2026.1.3을 설치하고 나서 처음 잡아둔 툴체인이 낡았다는 것이 드러났다.

### 무엇이 문제였나

초기에 AGP 8.7.3 / Gradle 8.9 / Kotlin 2.0.21로 잡았다. 2024년 10월 기준의 조합이다.
설치된 Studio는 AGP 9.4 기준선으로 빌드되었고 **내장 JDK가 25**다.
Gradle 8.9는 JDK 25에서 실행되지 않으므로, 그대로 두면 Gradle JDK를 따로 17로 낮춰야 했다.

### 결정: AGP 9.x로 올린다

새로 시작하는 프로젝트를 2년 된 툴체인으로 출발시킬 이유가 없다.
Studio 내장 JDK를 그대로 쓸 수 있고, 앞으로 몇 년간 업그레이드 압박이 없다.

버전은 추측하지 않고 Google Maven과 Gradle 배포 API에서 실제 값을 확인해 확정했다.

| 항목 | 이전 | 확정 |
|---|---|---|
| AGP | 8.7.3 | **9.4.0** |
| Gradle | 8.9 | **9.7.1** |
| Kotlin | 2.0.21 | **2.4.10** |
| KSP | 2.0.21-1.0.28 | **2.3.11** |
| compileSdk / targetSdk | 35 | **37** |
| Java source/target | 17 | 17 (유지) |

### AGP 9 때문에 바뀐 것

**1. `org.jetbrains.kotlin.android` 플러그인을 적용하지 않는다**

AGP 9는 Kotlin 지원을 내장한다. 이 플러그인은 새 DSL과 호환되지 않아 적용하면 오히려 실패한다.
Compose 컴파일러 플러그인(`org.jetbrains.kotlin.plugin.compose`)은 여전히 별도로 필요하다.

**2. `kotlinOptions { jvmTarget = ... }` 블록을 없앴다**

Kotlin의 `jvmTarget`이 `android.compileOptions.targetCompatibility`를 자동으로 따른다.
Java 17 하나만 지정하면 되므로 중복 설정이 사라졌다.

**3. KSP 버전 체계가 바뀌었다**

예전에는 `2.0.21-1.0.28`처럼 Kotlin 버전이 앞에 붙었는데, 이제 `2.3.11`처럼 독립적으로 매겨진다.

**4. 안 쓰는 테스트 의존성을 뺐다**

MockK와 Turbine을 넣어두었지만 실제 테스트는 가짜 구현(`FakeUsageRepository`)과 `.first()`로 작성해
둘 다 한 번도 쓰지 않았다. 버전을 관리할 대상만 늘어나므로 제거했다.

## 2026-09-03 — 첫 빌드 통과

Android SDK(`android-37.0`) 설치 후 첫 빌드와 단위 테스트가 통과했다.

### 결과

| 항목 | 결과 |
|---|---|
| 컴파일 (Kotlin + KSP + Hilt + Room) | 통과 |
| 단위 테스트 | 24개 전부 통과 (실패 0, 오류 0) |
| `app-debug.apk` 패키징 | 성공 (약 19MB) |
| 컴파일 경고 | 0건 |

테스트 내역: `ByteFormatterTest` 4 · `UsageBytesTest` 3 · `UsagePeriodTest` 10 ·
`GetAppUsageUseCaseTest` 4 · `SyncUsageUseCaseTest` 3

AGP 9 전환에서 우려했던 문제(내장 Kotlin, Compose 플러그인 조합, KSP 버전 체계 변경)는
모두 실제로는 걸리지 않았다. 설계 문서에 적어둔 구성 그대로 빌드되었다.

### 첫 빌드에서 나온 경고 두 건과 처리

**1. `hiltViewModel`이 다른 패키지로 이동했다**

`androidx.hilt.navigation.compose` → `androidx.hilt.lifecycle.viewmodel.compose`.
아티팩트도 `hilt-navigation-compose` → `hilt-lifecycle-viewmodel-compose`로 바꿨다.
이 앱은 내비게이션 백스택에 묶인 ViewModel을 쓰지 않으므로 navigation 쪽 의존성이 필요 없다.

**2. API 37에서 AppOps 검사 API의 권장/비권장이 뒤집혔다**

예전에는 `checkOpNoThrow`가 deprecated고 `unsafeCheckOpNoThrow`가 대체재였는데,
API 37에서는 반대가 되었다. `checkOpNoThrow(String, int, String)`는 API 19부터 있던 메서드라
버전 분기 없이 그냥 부르면 된다. **결과적으로 코드가 짧아졌다.**

### 남은 블로커: 실기기

`adb devices`에 연결된 기기가 없고 AVD도 없다. 다음 두 가지를 아직 하지 못했다.

1. **계측 테스트** (`DailyAppUsageDaoTest`) — 중복 집계 회귀 테스트가 여기 들어 있다
2. **실기기 수동 검증** — `doc/design.md` 10절의 6개 항목

에뮬레이터로는 2번을 할 수 없다(실제 트래픽이 없어 값이 0에 가깝다).
그러므로 실기기를 USB로 연결하는 것이 두 가지를 한 번에 해결하는 길이다.

### 통과한 항목

| 항목 | 결과 |

| 단위 테스트 24개 | 통과 |

### 중복 집계 회귀 테스트 상세

가장 중요한 검증이라 실기기에서 직접 확인했다.
앱을 강제 종료 후 재실행하는 방식으로 동기화를 3회 추가 실행하고,
과거 날짜(2026-09-01)의 합계가 변하는지 확인했다.

```
[초기]        행=11954  날짜수=90  2026-09-01 합계=24519154370
[동기화 1회 후] 행=11955  날짜수=90  2026-09-01 합계=24519154370
[동기화 2회 후] 행=11955  날짜수=90  2026-09-01 합계=24519154370
[동기화 3회 후] 행=11955  날짜수=90  2026-09-01 합계=24519154370
```

합계가 바이트 단위까지 동일하다. 복합 기본키 + REPLACE 전략이 의도대로 동작한다.
(행이 1개 는 것은 오늘 날짜에 새 앱의 트래픽이 잡힌 것으로 정상이다.)

### 검증 중 발견해 고친 문제

**1. 계측 테스트가 전부 실패 — 코루틴 버전 불일치**

→ `MainActivity.onCreate`에서 `enableEdgeToEdge()` 호출.
   Scaffold 밖에 있는 `PermissionScreen`에는 `windowInsetsPadding(WindowInsets.safeDrawing)` 추가.

## 2026-09-03 — 설정 화면과 50MB 차이: 표시 단위 문제였다

교차 검증에서 앱과 삼성 설정 화면의 모바일 사용량이 약 50MB 차이난다는 보고를 받았다.

### 조사 과정

수치 자체가 틀렸는지, 조회 방식이 틀렸는지, 표시가 틀렸는지를 먼저 갈랐다.

**1단계 — 앱 화면과 DB 대조**

앱이 표시한 940.69 MB는 DB 합계(986,389,338바이트)와 정확히 일치했다. 집계 로직은 무결.

**2단계 — 특수 UID 기여 확인**

테더링·시스템 UID가 원인일 수 있어 확인했으나 모바일 기여가 1.62 MB뿐이었다. 원인 아님.

**3단계 — 조회 방식 진단**

실기기에 일회용 진단 테스트를 붙여 네 가지 조회 결과를 비교했다.

```
A 하루씩 UID별 합계 (앱 저장값) = 986,389,604
B 하루씩 기기 합계             = 986,607,919
C 한 번에 기기 합계            = 986,607,923
D 한 번에 UID별 합계           = 986,389,614

A-D (하루 단위 쪼개기 영향)    = -10 bytes
C-D (UID 미귀속 트래픽)        = 218,309 bytes (0.02%)
B-C (기기 합계의 쪼개기 영향)  = -4 bytes
```

하루 단위로 쪼개 조회하는 방식은 값을 사실상 바꾸지 않았다(-10바이트).
UID에 귀속되지 않는 트래픽도 0.21 MB뿐이다. **조회는 정확했다.**

**4단계 — 표시 단위 확인**

같은 바이트 수를 시스템 API가 어떻게 표시하는지 직접 물었다.

```
원본 바이트                = 986,389,338
시스템 formatFileSize      = 0.99GB       <- 1000 기준
1000 기준 계산             = 986.39 MB
1024 기준 계산 (당시 앱)   = 940.69 MB
```

차이는 45.70 MB. 보고받은 "50메가 정도"와 일치한다.

### 근본 원인

**표시 단위 규약이 시스템과 반대였다.**

`ByteFormatter`를 1024 기준(이진 접두어)으로 만들면서 KDoc에
"Android 시스템 UI와 같은 1024 기준을 사용해 설정 화면과 교차 검증하기 쉽게 한다"고 적었는데,
**그 전제가 사실과 반대였다.** Android의 `Formatter.formatFileSize`는 1000 단위 SI 접두어를 쓴다.

의도(설정 화면과 맞추기)는 옳았고 사실 확인을 하지 않은 것이 잘못이었다.
GB 근처에서 두 규약은 7% 넘게 벌어지므로, 앱이 사용량을 놓치고 있는 것처럼 보이게 된다.

### 조치

`ByteFormatter.UNIT_STEP`을 1024에서 1000으로 바꿨다. 그 외 코드는 손대지 않았다.
실기기에서 확인한 값(`986,389,338` → `"986.39 MB"`)을 단위 테스트로 고정해
같은 실수가 되돌아오지 못하게 했다.

### 덤으로 알게 된 것

`connectedAndroidTest`는 앱을 재설치하므로 **appops로 부여한 `GET_USAGE_STATS`가 초기화된다.**
계측 테스트를 돌린 뒤에는 권한을 다시 부여해야 앱이 정상 동작한다.
(`querySummaryForDevice`는 일반 앱 권한으로는 호출할 수 없어 진단 테스트도 이 때문에 실패했다.)

## 2026-09-03 — 기간을 고정 4종에서 '단위 + 이동'으로 바꿈

'오늘/이번 주/이번 달/전체 누적' 네 가지 고정 기간만으로는 어제나 지난달을 볼 수 없었다.
일·주·월 단위로 과거를 자유롭게 넘겨볼 수 있게 바꿨다.

### 모델 변경

`PeriodOption`(고정 4종)을 두 개념으로 갈랐다.

```kotlin
enum class PeriodUnit { DAY, WEEK, MONTH, ALL }
data class PeriodSelection(val unit: PeriodUnit, val offset: Int = 0)
```

**날짜를 직접 들고 있지 않은 이유**가 핵심이다.
`offset = 0`인 '오늘'은 자정이 지나면 새 날짜를 가리켜야 한다.
선택을 날짜로 저장하면 앱을 켜둔 채 날짜가 바뀌었을 때 어제를 계속 보게 된다.
`UsagePeriod.of(selection, today)`가 볼 때마다 오늘 기준으로 풀어낸다.

### 이동 규칙

| 상황 | 동작 |
|---|---|
| 다음(오른쪽) | 현재 칸이면 비활성 — 미래에는 기록이 없다 |
| 이전(왼쪽) | 저장된 가장 오래된 날짜에 걸치는 칸까지만 활성 |
| 전체 누적 | 이동 개념이 없어 양쪽 모두 비활성 |
| 단위 변경 | 항상 현재 칸에서 다시 시작 |

현재 칸의 주·달은 오늘까지만, 지난 칸은 그 주/달 전체를 포함한다.

이동 하한을 두기 위해 DAO에 `SELECT MIN(usageDate)`를 Flow로 추가했다.
동기화로 기록이 늘면 하한도 자동으로 따라간다.

### 딸려온 변경: 상세 화면 경로

경로가 `app_detail/{uid}/{period}`(열거형)에서
`app_detail/{uid}/{시작일}/{종료일}`(ISO 문자열)로 바뀌었다.

임의의 칸으로 이동한 상태를 단위 이름만으로는 표현할 수 없기 때문이다.
지난주를 보다가 앱을 눌렀는데 상세 화면이 이번 주를 보여주면 두 화면의 수치가 어긋난다.
상세 화면은 이제 오늘 기준으로 기간을 다시 계산하지 않고 받은 범위를 그대로 쓴다.
그 결과 `AppDetailViewModel`에서 `Clock` 의존성이 사라졌다.

### UI

칩 아래 전용 줄에 `<  라벨  >` 형태로 뒀다.
이동할 수 없는 화살표는 **숨기지 않고 비활성화**한다.
숨기면 가운데 라벨의 위치가 흔들려 어느 쪽으로 갈 수 있는지 오히려 알기 어려워진다.

날짜 표시 형식(`yyyy년 M월 d일` 등)은 문자열 리소스에 뒀다.
코드에 박아두면 다른 언어를 추가할 때 손댈 곳이 흩어진다.

### 검증

단위 테스트를 10개에서 20개로 늘렸다. 월 이동이 각 달의 실제 길이를 따르는지(2월 28일),
해를 넘어가는지(2025년 12월), 미래로 갈 수 없는지 등을 고정했다.

실기기에서 이동을 단계별로 실행해 합계가 바뀌는 것을 확인했다.

```
월 현재 34.31 GB -> 이전 159.69 GB -> 이전 146.04 GB -> 다음 159.69 GB
```

8월에서 7월로 갔다 돌아왔을 때 합계가 159.69 GB로 같다. 왕복이 어긋나지 않는다.

## 2026-09-03 — 상세 화면 그래프에 Y축 추가

막대 그래프에 눈금이 없어 "이 날 대략 몇 GB인지"를 알 수 없었다.
세로축에 눈금 용량과 격자선을 넣었다.

### 핵심: 눈금 값을 반올림한다

실제 최댓값을 축 맨 위에 그대로 쓰면 `5.13 GB` 같은 값이 찍힌다.
그러면 중간 높이의 막대가 얼마인지 암산해야 해서 축이 있으나 마나다.

`ChartAxis.forMaxValue()`가 눈금 간격을 **1·2·5 × 10ⁿ** 꼴로 고른다.

```
데이터 최댓값 5.13 GB  ->  눈금 0 / 2.00 GB / 4.00 GB / 6.00 GB
데이터 최댓값 18.31 GB ->  눈금 0 / 5.00 GB / 10.00 GB / 15.00 GB / 20.00 GB
```

축 최댓값이 데이터보다 높아 위쪽 여백이 생기지만, 막대가 천장에 붙지 않아 오히려 읽기 좋다.

### 왜 core에 뒀는가

눈금 계산은 Compose와 무관한 순수 계산이다.
`core/ChartAxis.kt`로 분리해 단위 테스트 7개를 붙였다.
캔버스 그리기 코드 안에 두었다면 검증할 방법이 없었다.

경계값을 테스트로 못박았다.

- 축 최댓값이 데이터 최댓값보다 작아지지 않는지 (작으면 막대가 잘린다)
- 눈금 간격이 모두 같은지
- 기록이 0일 때 축이 무너지지 않는지
- 아주 작은 값에서 간격이 0이 되지 않는지 (바이트를 Long으로 나누면 0이 될 수 있다)

### 그리기

Compose `TextMeasurer`로 눈금 라벨을 먼저 측정해 왼쪽 여백을 정하고,
그 폭만큼 그래프 영역을 밀어 넣었다. 날짜 축 라벨 줄도 같은 폭만큼 들여써 세로로 정렬된다.

맨 위 눈금 라벨은 격자선 가운데에 두면 화면 밖으로 넘치므로 영역 안쪽으로 잘라 넣는다.

### 남은 다듬을 거리

축 라벨이 `20.00 GB`처럼 소수점 두 자리를 항상 붙인다. `20 GB`가 더 깔끔하지만,
`ByteFormatter`를 축 전용으로 한 번 더 나누면 표시 규칙이 둘로 갈라진다.
설정 화면과의 수치 대조가 이 앱의 신뢰성 근거이므로 표시 규칙을 하나로 유지하는 쪽을 택했다.

## 2026-09-03 — 축 표기 정리, 조회 조건 기억, 주 시작 월요일

### 1. 축 라벨의 소수점

`20.00 GB`처럼 의미 없는 0이 붙어 있었다. `ByteFormatter.formatCompact`를 추가해
`2.00 GB -> 2 GB`, `600.00 MB -> 600 MB`로 떼어냈다.

**소수점을 전부 없애지는 않았다.** 눈금 간격이 500 MB이면 1.5 GB 지점에 격자선이 그어지는데,
이를 `2 GB`로 적으면 선의 위치와 라벨이 어긋나 그래프를 잘못 읽게 된다.
`1.5 GB`는 그대로 두고 `1.50` 같은 꼬리 0만 없앤다.

축 전용 함수를 따로 둔 이유는, 앱 목록의 `986.39 MB`는 설정 화면과 대조해야 하므로
자릿수를 그대로 유지해야 하기 때문이다. 표시 규칙을 하나로 합칠 수 없는 지점이다.

### 2. 조회 조건 기억

기간 단위와 정렬을 DataStore에 저장한다.

- 열거형의 **이름 문자열**로 저장한다. ordinal은 항목을 끼워 넣으면 의미가 어긋난다.
- 알아볼 수 없는 값(항목이 사라진 뒤 남은 옛 값)은 조용히 기본값으로 되돌린다.
- 읽기 실패(IOException)에도 화면은 떠야 하므로 기본값으로 진행하고 로그만 남긴다.
- **'몇 칸 전인지'는 저장하지 않는다.** 3주 전을 보다 껐는데 다음에도 3주 전이 나오면
  지금이 언제인지부터 다시 파악해야 한다.
- 저장 값은 시작할 때 한 번만 읽는다. 계속 관찰하면 칩을 누를 때마다 저장소를 왕복해 반응이 굼떠진다.

### 3. 주 시작 요일을 월요일로 고정

`UsagePeriod.DEFAULT_FIRST_DAY_OF_WEEK = MONDAY`.

기기 로케일을 따르지 않는다. 로케일에 맡기면 같은 데이터를 보고도 기기마다
'이번 주'의 범위가 달라져 수치를 비교할 수 없다.

### 검증 중 발견한 결함: 그래프가 선택한 기간보다 늦게 시작

주 단위로 `8월 31일 ~ 9월 3일`을 선택했는데 그래프 x축이 `9/1 ~ 9/3`으로 나왔다.

원인은 '전체 누적'의 빈 점 2만 개를 막으려고 넣었던 코드였다.
`fillMissingDates`가 **그 앱의 첫 기록일**을 기준으로 잘라서, 8월 31일에 기록이 없는 앱은
그래프가 하루 늦게 시작했다. 화면에 적힌 기간과 그래프 범위가 어긋난 것이다.

**저장소 전체의 첫 기록일**로 자르도록 고쳤다.

- 전체 누적: 시작일 1970년 -> 전체 첫 기록일(2026-06-06)로 잘림. 의도대로 90개.
- 주·월: 시작일이 이미 기록 범위 안이므로 그대로 유지. 기록 없는 날도 빈 자리로 남는다.

고친 뒤 x축이 `8/31 ~ 9/3`으로 선택한 주 전체를 덮는 것을 확인했다.

## 2026-09-03 — 사용량 경고 알림 (위젯은 보류)

경고 알림과 홈 화면 위젯을 함께 검토했다가 **알림만 먼저** 만들기로 했다.

### 위젯을 미룬 이유

위젯의 핵심 표시 내용(한도 대비 진행률)과 알림의 판정 기준이 같은 설정을 쓴다.
위젯을 먼저 만들면 한도가 없어 숫자만 띄우는 반쪽이 되고, 알림을 넣을 때 다시 손대야 한다.

### 확정된 결정

| 항목 | 결정 |
|---|---|
| 임계치 | 모든 앱에 적용되는 공통 값 하나 |
| 평가 주기 | 15분 (WorkManager 최소 주기) |
| 대상 회선 | 모바일만 |
| 알림 빈도 | 앱당 하루 1회 |
| 홈 위젯 | 향후 진행 |

### 배터리 판단

"15분마다 백그라운드 집계가 부담되지 않는가"가 핵심 질문이었다.

**우리 앱은 트래픽을 세지 않는다.** 커널이 UID별 바이트를 이미 상시 집계하고 있고
`NetworkStatsManager`는 그 누적값을 읽어올 뿐이다. 패킷을 가로채는 VPN 방식과 비용의 성격이 다르다.

실측 근거: 7일치 조회(14회) + 979행 저장이 306ms, 앱 콜드 스타트가 154ms.
일일 경고는 오늘치만 필요해 조회 2회면 끝나므로 50ms 안쪽이다.
하루 96회 × 약 0.2~0.3초 ≒ 하루 CPU 20~30초. 체감 영향은 1% 미만으로 본다.

포그라운드 서비스는 쓰지 않기로 했다. 초 단위 실시간을 얻는 대신 상시 알림과 배터리 대가가 크고,
"오늘 이 앱이 한도를 넘었다"가 15분 늦어도 의미가 달라지지 않는다.

### 구현 중 발견해 고친 것 두 가지

**1. domain이 Android에 의존해 단위 테스트가 전부 실패**

`EvaluateUsageAlertsUseCase`에 `AppLog.info`를 넣었는데, 이는 `android.util.Log`를 감싼 것이라
JVM 테스트에서 `Method i in android.util.Log not mocked`로 터졌다.
알림을 보내는 경로 5개가 전부 실패하고 0을 기대하는 2개만 통과해 원인이 드러났다.

domain을 순수 Kotlin으로 유지한다는 원칙을 내가 깬 것이다.
로그를 호출부인 `UsageAlertWorker`로 옮겼다.

**2. 설정을 바꿔도 아무 일이 일어나지 않음**

설정에서 한도를 낮추고 돌아와도 판정이 돌지 않았다.
요약 화면 ViewModel이 이미 만들어져 있어 `init`이 다시 실행되지 않기 때문이다.
사용자 입장에서는 설정이 먹지 않는 것으로 보인다.

설정 변경 직후에 바로 판정하도록 `SettingsViewModel`에서 호출을 추가했다.

### 검증

단위 테스트 7개로 판정 규칙을 고정했다. 특히 경계와 중복 방지를 못박았다.

- 경고가 꺼져 있으면 아무것도 알리지 않음
- 한도와 정확히 같은 값도 초과로 봄

- 같은 앱은 하루 한 번만
- 날짜가 바뀌면 다시 알림

**임시로 1MB 선택지를 넣어 알림 발송을 확인하고 되돌렸다.**


`dumpsys jobscheduler`에서 `DailyUsageSyncWorker`와 `UsageAlertWorker` 둘 다 등록 확인.

## 2026-09-03 — 한도 직접 입력, 시간대별 상세 화면

### 1. 한도를 목록 + 직접 입력으로

목록을 100 / 200 / 300 MB로 줄이고 MB 단위 직접 입력을 더했다.
**직접 입력이 0이면 목록에서 고른 값을, 0보다 크면 입력값을 쓴다.**

목록만 두면 원하는 값이 없을 때 막히고, 입력만 두면 매번 숫자를 쳐야 한다.

구현에서 신경 쓴 것

- **적용 버튼을 누를 때만 저장한다.** 글자를 칠 때마다 저장하면 "1"을 친 순간
  1MB 한도로 판정이 돌아 알림이 쏟아진다. 화면 안에서만 값을 들고 있다가 넘긴다.
- 숫자만 받고 자릿수에 상한을 둔다. 부호나 소수점이 섞이면 해석이 갈리고,
  지나치게 큰 값은 바이트 환산에서 넘칠 수 있다.
- 직접 입력을 쓰는 동안 목록은 흐리게 처리해 무엇이 적용되는지 드러낸다.
  그래도 헷갈리므로 맨 아래에 "현재 적용: 250 MB"를 적는다.

저장 키를 새로 만들었다(`preset_limit_bytes`, `custom_limit_megabytes`).
예전 키(`per_app_daily_limit_bytes`)에 남은 500MB가 새 목록에 없어 아무 항목도
선택되지 않은 상태가 되는 것을 피하려는 것이다.

### 2. 시간대별 상세 화면

앱 상세의 일자별 막대를 누르면 그 날을 시간대별로 본다.

**핵심 제약: 시스템은 사용량을 시간 단위로 기록하지 않는다.**
기기마다 다르지만 보통 두 시간짜리 구간으로 묶어 두므로 한 구간이 여러 시간대에 걸친다.

`HourlyBucketSplitter`가 겹친 시간에 비례해 나눈다. 그래서 **시간별 값은 근사치**이고,
화면에 그 사실을 적어 둔다. 밝히지 않으면 사용자가 정확한 시각으로 오해한다.

나눈 값의 합이 원래 값과 어긋나면 시간별 합계와 하루 합계가 달라 보인다.
정수 나눗셈에서 버려지는 나머지를 가장 많이 겹친 시간대에 몰아주어 총합을 보존한다.
이 규칙을 단위 테스트 9개로 고정했다(하루 밖으로 나간 구간, 길이 0인 구간, 총합 보존 등).

조회는 `queryDetailsForUid`를 쓴다. 시간이 나뉜 구간을 한 번에 돌려주므로
하루를 두 번의 호출로 훑는다. 시간마다 따로 조회하면 48번을 호출해야 하고,
그렇게 해도 시스템이 내부적으로 같은 구간을 비례 배분할 뿐이라 더 정확해지지 않는다.

### 그래프 코드를 하나로 합쳤다

일자별과 시간대별 그래프는 축 라벨만 다르고 그리는 방식이 같다.
`UsageBarChart`로 합치고 `DailyTrendChart`는 날짜를 라벨로 바꾸는 일만 하도록 줄였다.

## 포그라운드 / 백그라운드 구분 (DB v2)

### 전제부터 확인했다

코드에 이런 주석이 있었다.

> 같은 UID라도 로밍/포그라운드 여부 등에 따라 버킷이 나뉘어 오므로 UID 단위로 합산한다.

**검증한 적이 없는 문장이었다.** 안드로이드 문서를 보면 `querySummary`가 state를
합쳐서 준다고 읽을 여지도 있었다. 스키마 마이그레이션까지 가는 작업이라
설계 전에 버리는 조사 코드를 만들어 실기기에서 확인했다.

```
[1] querySummary 가 돌려준 state 종류: [DEFAULT(=백그라운드), FOREGROUND]
[1] UID 수: 36, UID당 버킷 수 분포: {2=15, 1=19, 4=1, 3=1}
[3] state 별 합=94431328, querySummary 합=94431328, 차이=0
[4] UID 36개 × state 2개 = 72회 조회에 85ms
```

주석이 맞았다. **정보는 이미 오고 있었고 우리가 합치면서 버리고 있었다.**
조회를 늘릴 필요가 없다. 조사 코드는 확인 후 지웠다.

### 기본키를 늘리지 않고 열을 더했다

`(날짜, uid, 회선, state)`로 기본키를 늘리는 안을 검토했다가 버렸다.

마이그레이션에서 기존 행은 `state='UNKNOWN'`이 된다. 그 날짜를 다시 동기화하면
`FOREGROUND`/`BACKGROUND` 행이 새로 생기는데 `UNKNOWN` 행은 그대로 남는다.
**같은 날이 두 번 세어진다.** 이 프로젝트가 가장 조심해 온 실수다.

막으려면 '날짜별 삭제 후 삽입'으로 바꿔야 하는데, 그러면 시스템 보관 기간이 지난
과거 날짜를 동기화할 때 조회 결과가 비어 **아카이브를 지워버린다.**
다시 만들 수 없는 자료를 위험에 빠뜨리는 대가로 중복을 막는 셈이라 앞뒤가 맞지 않는다.

열 두 개를 더하는 쪽은 `ALTER TABLE ADD COLUMN` 두 번이면 끝나고,
덮어쓰기 규칙이 그대로 남는다. 기존 행은 손대지 않는다.

**null을 허용한 것이 핵심이다.** 기본값 0을 주면 과거 기록이
"포그라운드 0 = 전부 백그라운드"로 보인다. 사실이 아니라 **모르는 것**이다.

### 목록과 상세의 백분율이 어긋났다

처음에는 목록에 '측정된 몫 대비' 비율을 적었다. 구분 없는 옛 기록이 비율을
희석하지 않게 하려는 의도였다. 실기기에서 보니 같은 인스타그램이
목록에서는 **2%**, 상세에서는 **1%** 로 나왔다.

두 값 모두 그 화면 안에서는 옳지만, 나란히 보면 하나는 오류로 읽힌다.
상세는 세 몫을 모두 보여주므로 전체 대비여야 합이 100%가 되고, 목록에는 그 자리가 없다.

**구분 없는 몫이 섞인 줄에서는 백분율을 아예 적지 않기로 했다.**
바이트 값은 두 화면에서 같으므로 어긋날 일이 없고, 그 줄의 기록이
온전하지 않다는 사실도 함께 드러난다.

### 실기기 검증

| 확인 | 결과 |
|---|---|
| 마이그레이션 | 계측 테스트 2개. 기존 행 값 보존, 예전 행의 새 열은 null |
| 백그라운드 정렬 | DB에서 계산한 9월 순위와 화면이 정확히 일치 |

9월 백그라운드 상위는 테더링 1.36 GB(100%), Google Play 726.89 MB(32%),

### 그밖에 배운 것

- **계측 테스트는 앱을 제거한다.** 누적 DB가 통째로 지워졌다.
  이번에는 90일 백필로 복구했지만, 시스템 보관 기간을 넘긴 기록이었다면 끝이었다.
  **내보내기/백업을 먼저 만들어야 할 이유가 하나 더 늘었다.**
- `room-testing`은 kotlinx-serialization을 쓴다. AGP가 계측 테스트 클래스패스를
  앱 APK 버전으로 고정하므로 앱 쪽에도 같은 BOM을 적용해야 한다.
  코루틴에서 겪은 것과 똑같은 문제다.
- **uiautomator 덤프는 탭 직후 갱신 전 화면을 잡는다.** 정렬이 틀린 줄 알고
  한참 찾았는데 스크린샷을 찍어 보니 정상이었다. 화면 변화를 확인할 때는 스크린샷을 쓴다.

## 백그라운드를 회선별로 나눴다

"백그라운드 사용량은 모바일, Wi-Fi로 구분이 불가능한가?"

**가능했다. 저장은 이미 그렇게 되어 있었다.** 행이 `(날짜, uid, 회선)` 단위이므로
포그라운드 열도 회선별로 따로 들어 있다. 조회할 때 내가 두 회선을 합쳤을 뿐이다.
마이그레이션도 재동기화도 필요 없이, 쌓인 자료를 다르게 읽기만 하면 됐다.

### 합쳐 보면 결론이 달라진다

2026년 8월 실측이다.

```
                     모바일 백그   모바일 합   Wi-Fi 백그    Wi-Fi 합
토스                    52.5MB      96.5MB    145.1MB    390.1MB
카카오톡                 43.7MB     142.8MB    107.1MB    762.0MB
스마트스코어              26.4MB     823.5MB     11.0MB    494.9MB

전체 모바일  백그라운드   709.3MB /  8,949.6MB (7%)
전체 Wi-Fi   백그라운드 2,638.0MB / 148,061.7MB (1%)
```

**인스타그램이 목록에서 사라졌다.** 합산 기준으로는 9월 백그라운드 4위였는데
그 대부분이 Wi-Fi였다. 요금 관점에서는 신경 쓸 대상이 아니다.

**토스가 올라왔다.** 모바일로 쓴 96.5 MB 중 52.5 MB, 절반 이상을 화면을 보지 않을 때 쓴다.
합치면 Wi-Fi 390 MB에 묻혀 드러나지 않던 사실이다.

정렬 기준은 `MOBILE_BACKGROUND` 하나로 뒀다. 칩을 둘로 늘릴 수도 있었지만
정렬 칩이 다섯 개가 되면 가로로 더 밀려나고, 요금이 붙는 쪽은 모바일뿐이다.
경고 알림이 모바일만 보는 것과도 기준이 맞는다.

### 모델을 어떻게 바꿨나

`AppUsage`가 들고 있던 `UsageBytes`(수신/송신)는 아무 데서도 수신/송신을 따로 쓰지 않았다.
확인하고 `UsageStateSplit`(총량 + 포그라운드 + 구분없음)으로 바꿨다.
수신/송신이 필요한 상세 화면은 `DailyUsagePoint`를 쓰므로 잃는 정보가 없다.

```kotlin
data class NetworkUsageSplit(val mobile: UsageStateSplit, val wifi: UsageStateSplit)
data class AppUsage(val app: AppIdentity, val usage: NetworkUsageSplit)
```

`AppUsage.mobile` / `.wifi` 접근자를 남겨 기존 호출부는 그대로 둔다.
회선별 값을 하나의 타입으로 묶어 두면 목록과 상세가 같은 모양을 쓴다.

단위 테스트 86개로 늘었다. 새로 넣은 것 중 하나는
**"Wi-Fi 백그라운드가 아무리 커도 모바일 백그라운드 순위를 밀어내지 못한다"**이다.
이 정렬을 만든 이유가 그것이므로 회귀로 잡히게 고정했다.

### 실기기 검증 (회선별)

**정렬은 DB 계산과 정확히 일치했다.** 9월 모바일 백그라운드 상위는
토스 1.69 MB, 카카오톡 1.65 MB, Kia 1.53 MB, 컬쳐랜드 496 KB 순이다.
컬쳐랜드는 모바일로 쓴 496 KB 전부가 백그라운드였다.

상세 화면의 토스가 이 변경의 이유를 그대로 보여준다.

```
모바일  12.26 MB   직접 사용 86%   백그라운드 14%
Wi-Fi   22.89 MB   직접 사용 36%   백그라운드 64%
```

합치면 "백그라운드 47%"가 되는데, 그 숫자는 두 회선 어느 쪽도 설명하지 못한다.

**한 번 헤맸다.** 정렬을 바꾼 직후 화면이 DB 계산과 어긋나 보였다.
목록이 스크롤된 상태였을 뿐인데, 기간 카드와 정렬 칩이 목록 위에 고정돼 있어
맨 위처럼 보였다. 스크롤을 강제로 올리니 DB와 정확히 맞았다.
**화면 상단이 고정된 화면에서는 '맨 위처럼 보이는 것'을 믿으면 안 된다.**

**줄 넘침도 실기기에서만 드러났다.** 두 회선을 한 줄에 적으니
`Wi-Fi 14.74` / `MB`로 숫자와 단위가 갈라졌다. 목록은 모바일 백그라운드만 적고
Wi-Fi는 상세 화면에 맡기기로 했다. 순위가 이미 모바일 기준이라 잃는 정보가 없다.

단위 테스트 86개, 계측 테스트 14개 전부 통과. 아카이브는 90일 11,958행으로 재구축했다.

## 요금제 한도와 홈 화면 위젯

두 가지를 함께 만들었다. 위젯이 보여줄 핵심이 결국 "이번 달 한도 중 얼마"라
한도 없이 위젯만 만들면 보여줄 것이 빈약해진다.

### 정한 것

| 항목 | 결정 |
|---|---|
| 청구 주기 | 시작일 지정 (기본 1일) |
| 위젯 내용 | 진행률 + 많이 쓴 앱 **2개** |
| 알림 | 80%와 100%에 각각 한 번 |

### 시작일이 그 달에 없을 때

이 계산에서 가장 틀리기 쉬운 지점이다. 31일 시작인데 2월이 오면 그런 날짜가 없다.
그 달의 마지막 날로 줄여 잡으면 `1/31 ~ 2/27`, `2/28 ~ 3/30`처럼 이어진다.

건너뛰거나 다음 달로 미루면 **하루가 어느 주기에도 속하지 않거나 두 주기에 겹친다.**
그 하루의 사용량이 사라지거나 두 번 세어진다는 뜻이다.
1년치를 하루씩 훑으며 "모든 날은 정확히 한 주기에 속하고, 새 주기는 앞 주기 끝 다음 날에
시작한다"를 단위 테스트로 고정했다.

### 화면과 위젯이 같은 함수를 쓴다

`readMobileUsageForPeriod` 하나를 둘 다 쓴다. 저장분(어제까지) + 시스템의 오늘치다.
따로 계산하면 홈 화면과 앱 안의 숫자가 달라지고, 어느 쪽이 맞는지 사용자가
판단할 방법이 없어 둘 다 믿지 못하게 된다.

### 실기기에서 잡은 진짜 버그

위젯이 갱신되지 않았다. 10 GB로 바꿨을 때는 됐고 6 GB로 바꿨을 때는 안 됐다.

원인은 `SettingsViewModel`이 설정 저장과 위젯 갱신을 `viewModelScope`에서 돌린 것이었다.
**적용을 누르고 곧바로 뒤로 나가면 화면과 함께 코루틴이 취소된다.**
저장 → 판정(시스템 조회) → 위젯 갱신 순서라 갱신까지 가기 전에 끊긴 것이다.
10 GB 때 된 것은 우연히 화면에 더 머물렀기 때문이다.

`@ApplicationScope`(SupervisorJob)를 두고 설정을 바꾸는 일을 모두 그쪽으로 옮겼다.
저장 자체도 같은 위험에 있었으므로 함께 옮겼다. 읽기(StateFlow)는 화면 수명 그대로 둔다.

고친 뒤 같은 상황을 재현해 확인했다. 적용 직후 즉시 이탈 → 저장 5000, 위젯 첫 확인에서 5 GB.

### 헤맨 것

한도 값이 저절로 바뀐 줄 알고 한참 뒤졌는데 **사용자가 폰에서 직접 바꾼 것**이었다.
실기기를 함께 쓰는 동안에는 내가 만든 변화만 있다고 가정하면 안 된다.

`adb shell input text`는 한글을 넣지 못한다(NullPointerException).
위젯 목록에서 앱을 찾을 때는 검색 대신 목록을 훑어야 했고, 이때 표시되는 이름은
앱 화면의 제목이 아니라 **애플리케이션 이름(TracePhone)** 이다.

### 실기기 검증

| 확인 | 결과 |
|---|---|
| 주기 계산 | 화면 `8월 15일 ~ 9월 14일`, DB 계산 4290.48 MB와 카드 `4.29 GB` 일치 |
| 초과 표시 | `4.29 GB / 3 GB · 143% · 한도를 1.29 GB 넘겼습니다` (빨강) |
| 정상 표시 | `4.29 GB / 10 GB · 42%`, 하루 475.79 MB (= 5.71 GB ÷ 12일) |

## 위젯 글자색과 투명도

위젯은 배경화면 위에 놓인다. **기기 테마는 배경화면이 밝은지 어두운지 알지 못한다.**
어두운 배경화면에 밝은 테마를 쓰면 검은 글자가 묻힌다. 배경화면을 아는 것은 사용자뿐이라
직접 고르게 했다.

글자색은 자동·흰색·검정 셋이다. 색 목록을 넓히면 꾸밈은 늘지만 배경과 대비가 약한 색을
고르면 숫자가 안 보이게 된다. 셋이면 어떤 배경화면에서도 읽힘을 보장할 수 있다.

### '투명도'로 저장한다

화면에서 투명도라고 말하면서 코드에서 불투명도로 저장하면, 100이 어느 쪽인지 매번 되짚어야 한다.
이름 그대로 투명도를 저장하고 그리기 직전에 한 번만 뒤집는다.

### 야간 모드를 직접 읽는다

Glance의 `ColorProvider`는 색 하나 또는 색 리소스만 받는다.
day/night 조합을 받는 API를 기대했는데 1.2.0에는 없었다(`javap`으로 확인).
색 리소스를 쓰면 테마는 따라가지만 **런타임에 알파를 바꿀 수 없다.**
투명도를 적용하려면 실제 색 값이 필요하므로, `provideGlance`가 받은 `Context`에서
야간 모드 여부를 읽어 우리가 색을 고른다.

덕분에 `WidgetColors`는 (설정, 야간 여부) 두 값만 받는 순수한 계산이 되었다.

### 막대는 색을 따라가지 않는다

글자색을 따라 막대까지 바뀌면 '한도를 넘겼는지'를 색으로 알 수 없다.
막대는 진한 파랑·빨강 고정이고, **빈 부분만** 글자색을 옅게 깐다.
고정색으로 두면 배경을 투명하게 했을 때 배경화면과 겹쳐 막대의 끝이 어디인지 알 수 없다.

### 실기기 검증

| 확인 | 결과 |
|---|---|
| 글자색 흰색 | 저장 `WHITE`, 위젯 글자가 흰색으로 바뀜 |
| 투명도 60% | 저장 `60`, 위젯 배경 너머로 배경화면이 비침 |
| 기본값 복구 | `AUTO` / `0` — 설정 전 모습 그대로 |

문자열에서 한 번 걸렸다. `100%%로 두면...`처럼 적었는데 **서식 인자가 없는 문자열은
`%%`가 그대로 나온다.** 슬라이더가 옆에 있으니 "오른쪽 끝으로 두면"으로 바꿔 퍼센트 기호를 없앴다.

단위 테스트 115개 통과.

## 경고를 배수마다 반복하고, 목록을 넓혔다

### 한 번만 알리면 부족하다

한도가 50MB인데 하루 한 번만 알리면, 첫 알림 뒤로 100MB를 쓰든 300MB를 쓰든 조용하다.
경고의 목적이 "지금 멈출지 판단하게 하는 것"이라면 그 한 번으로는 부족하다.

**한도의 몇 배를 넘겼는지**를 기준으로 바꿨다. `사용량 / 한도`의 몫이고,
앱마다 마지막으로 알린 배수를 기억해 그 값이 커졌을 때만 알린다.
50MB 한도면 50·100·150·200에서 각각 한 번씩이다.

같은 구간에서 더 써도(50 → 90) 배수가 그대로라 알리지 않는다.
한 번에 여러 배수를 뛰어넘어도 알림은 한 번이다. 15분 사이에 40MB에서 210MB로 뛰었다고
알림 네 개를 쏟아 낼 이유는 없다.

저장은 `uid:배수` 문자열 집합으로 바꿨다. 날짜가 바뀌면 통째로 없는 것으로 보는 규칙은 그대로다.

**기존 테스트 하나가 이 변경을 잡아냈다.** '이미 알린 앱이 있어도 새로 넘긴 앱은 알린다'가
`[1, 2]`를 기대했는데 `[1, 1, 2]`가 나왔다. 앱 1이 2배에서 3배로 올라갔으니
다시 알리는 게 맞다. 그 테스트가 보려던 것은 '앱 2가 알림을 받는가'뿐이므로
앱 1의 배수를 그대로 두도록 고쳤다.

### 실기기 검증

한도를 낮춰 배수를 올리는 방식으로 재현했다. 대상은 다음(`net.daum.android.daum`, 오늘 111MB).

| 한도 | 배수 | 저장된 기록 |
|---|---|---|
| 50 MB | 2 | `10339:2` |
| 30 MB | 3 | `10339:3` (다시 알림) |
| 20 MB | 5 | `10339:5` (다시 알림) |
| 20 MB (그대로) | 5 | `10339:5` (알림 없음) |

한도를 **올리면** 배수가 내려가지만 기록은 낮추지 않는다.
낮추면 이미 알린 구간을 다시 알리게 된다.

### 목록이 화면의 4분의 1뿐이었다

머리말(한도 카드·기간 칩·기간 이동·합계 카드·정렬 칩)이 2340px 중 **1550px**을 차지했다.
앱 한 줄이 293px이니 목록에 남는 자리는 두 줄이었다.

행을 줄이는 방법도 있었지만 그러면 모바일/Wi-Fi 비율을 한눈에 보는 막대를 잃는다.
머리말을 `LazyColumn`의 칸으로 넣어 함께 스크롤되게 하면 **보여주는 정보를 하나도 버리지 않고**
한 번 내릴 때 일곱 줄이 들어온다.

정렬 칩만 `stickyHeader`로 붙였다. 목록을 훑다가 기준을 바꾸려고 매번 맨 위로 올라가야 하면
정렬을 아예 쓰지 않게 된다.

`stickyHeader`는 확장 함수가 아니라 `LazyListScope`의 멤버였다(임포트 불필요).

### 덤으로 고친 것

합계 카드에서 `146.94 MB / 390.99 MB`가 한 줄에 안 들어가 **`390.99` 와 `MB` 가 갈라졌다.**
회선마다 이름 아래에 값을 두고 막대와 같은 좌우 순서로 놓았다.
위젯에서 겪은 것과 같은 종류의 문제다.

단위 테스트 120개 통과.

## 시간대별 막대를 눌러 값을 읽는다, 그리고 S20 확인

### 높이만 보고는 값을 알 수 없다

시간대별 화면에는 막대가 24개다. 세로축 격자선에 대어 어림잡는 것도 이 정도로 촘촘하면 어렵다.
막대를 누르면 그 시간대의 합계·모바일·Wi-Fi를 숫자로 적기로 했다.

**누르기 전에는 가장 많이 쓴 시간대를 골라 둔다.** 원래 화면 아래에 따로 있던
'가장 많이 쓴 시간대' 카드와 새로 만들 '고른 시간대' 카드는 같은 자리에 같은 모양으로 놓이므로
두 개를 둘 이유가 없다. 하나로 합치면

- 24개에서 가장 높은 것을 눈으로 찾을 필요가 없고
- 카드가 처음부터 채워져 있어 첫 탭에서 화면이 밀리지 않고
- 칠해진 칸이 있으니 누를 수 있다는 사실이 드러난다

안내 문구("막대를 누르면 …")는 카드 맨 아래에 두고, 한 번 누르면 없앤다.
카드가 화면 맨 끝이라 문구가 사라져도 위쪽 내용이 밀리지 않는다.

### 되돌리기는 넣지 않았다

같은 막대를 다시 눌러 선택을 푸는 방식을 생각했다가 버렸다.
누르기 전 상태가 '가장 많이 쓴 시간대'이므로, 선택을 풀면 값이 다른 시간대로 튄다.
"눌렀는데 왜 값이 바뀌지"라는 혼란만 남는다. 다른 막대를 누르면 그쪽으로 옮겨 갈 뿐이다.

### 고른 막대는 칸 전체를 칠한다

막대에 테두리를 두르는 방법을 먼저 생각했으나, 사용량이 적은 시간대는 막대가 거의 없어
테두리가 실선 하나로 뭉친다. 칸 전체를 위아래로 옅게 칠하면 값이 0이어도 어디를 골랐는지 보인다.

**실기기에서 보니 그것만으로는 부족했다.** 칠한 자리가 막대보다 뒤에 깔리는데,
기본 선택이 하필 가장 높은 막대라 위쪽 자투리만 남았다. 축 꼭대기까지 닿는 막대라면 아예 안 보인다.
막대 위에 밑줄을 하나 더 그었다.

밑줄을 처음엔 강조색(파랑)으로 그었다가 되돌렸다. **Wi-Fi 계열색과 닮아
막대 아래쪽에 Wi-Fi를 조금 쓴 것처럼 보였다.** 글자색으로 바꾸니 데이터가 아니라
표시라는 것이 분명해졌다. 칠하는 색도 같은 글자색을 옅게 쓴 것이라 색이 하나로 줄었다.

### `BarSelection`으로 묶은 이유

`selectedIndex`와 `onBarSelected`를 따로 받으면 **누른 막대와 화면에 적힌 값이 어긋난 채로도
컴파일이 통과한다.** 한 덩어리로 묶으면 둘을 같이 다루게 된다.
매개변수가 하나로 줄어드는 것은 덤이다.

탭 판정과 칠하기가 `slotWidthOf` 하나를 함께 쓰게 한 것도 같은 이유다.
계산이 두 벌이면 누른 자리와 칠해지는 자리가 어긋난다.

### S20에서 되는가

기기가 연결되어 있지 않아 정적으로 확인했다.

- `minSdk 26`. S20은 Android 10으로 나와 13까지 올라가므로 전부 넘는다.
- `lintDebug`가 `NewApi`를 하나도 잡지 않았다. 쓰지 못할 API는 없다.

OS 버전에 따라 달라지는 것은 세 가지뿐이고, 모두 기능이 빠지는 것이 아니라 모양이 달라지는 정도다.

| 항목 | Android 12 이하에서 |
|---|---|
| 알림 권한 요청 | 요청 화면이 뜨지 않음 (API 33부터 런타임 권한) |
| 테마 색 | 고정 색 (Dynamic color는 API 31부터) |
| 위젯 기본 크기 | 4×1로 놓임 (`targetCellWidth/Height`가 API 31부터) |

위젯은 크기 조절이 열려 있으므로 아래 모서리를 끌면 앱 2개짜리 형태가 나온다.

**정적으로 답이 나오지 않는 두 가지**는 ROM 재량이라 실기기가 필요하다.

- `querySummary`가 상태별로 나뉜 버킷을 주는가. 안 주면 백그라운드가 '모름'으로 보인다(깨지지는 않는다).
- 시간대별 기록의 구간 길이와 보관 기간.
  `adb shell settings get global netstats_uid_bucket_duration` / `netstats_uid_rotate_age`로 읽는다.

S20을 연결하면 두 가지를 바로 확인한다.

## S20 실기기 확인

정적 분석으로는 답이 나오지 않는다고 적어 두었던 두 가지를 실기기로 확인했다.
기기는 **SM-G981N, Android 13(API 33), One UI 5.1**.

S20은 Android 10으로 나왔지만 이 기기는 13까지 올라와 있었다.
API 31 이상이라 알림 권한 요청·Dynamic color·위젯 기본 크기(4×2)가
최신 기기와 똑같이 동작한다. 앞서 적어 둔 "Android 12 이하면 다르다"는 단서가
이 기기에는 하나도 걸리지 않는다.

### 1. 포그라운드/백그라운드 구분 — 된다

가장 궁금했던 것이다. ROM이 상태별로 나뉜 버킷을 주지 않으면 '모름'으로 빠진다.

Google Play 스토어의 모바일 37.13MB가 **직접 사용 15.73MB(42%) / 백그라운드 21.39MB(58%)** 로
갈렸다. 0이나 100%가 아니라 그럴듯한 비율이 나왔으니 실제로 나뉜 값을 받은 것이다.

### 2. 시간대별 구간 길이 — 같다

`netstats_uid_bucket_duration`, `netstats_uid_rotate_age`, `netstats_uid_delete_age`가
셋 다 `null`이었다. 최신 기기에서 읽은 값과 같고, 삼성이 손대지 않았다는 뜻이다.
AOSP 기본값(구간 2시간, 보관 15일)을 쓰므로 근사 정도도 기기 사이에 다르지 않다.

### 3. 막대 터치 — 동작

Google Play 스토어 9월 2일에서 기본 선택이 `가장 많이 쓴 시간대 (7시 ~ 8시)`,
합계 118.01MB / 모바일 4.59MB / Wi-Fi 113.42MB.
옆 막대를 누르니 `8시 ~ 9시`로 옮겨 가고 안내 문구가 사라졌다.
칠한 칸과 밑줄도 함께 옮겨 갔다.

### 겪은 것

`adb devices`가 계속 `unauthorized`였다. 폰에서 USB 디버깅 승인 창을 눌러야 한다.
`adb kill-server && adb start-server`로 창을 다시 띄웠다.

앱을 켜자마자 화면을 찍었더니 스플래시만 나왔다. 그 뒤로는 `adb shell 'sleep N; input tap ...'`처럼
**기기 쪽에서 기다리게** 했다. 호스트에서 기다리는 것보다 화면 전환에 맞추기 쉽다.

## 가시성 정리 — 실기기 화면을 근거로

S23·S20 화면을 여러 장 보고 나서 걸리는 것을 다섯 가지 골랐다.
전부 짐작이 아니라 찍힌 화면과 코드에서 확인한 것이다.

### 1. 앱 행 네 줄 중 세 줄이 값을 되풀이하고 있었다

```
다음                      111.44 MB   <- 합계
▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬   <- 100% 주황, 단색
111.44 MB           7 KB   <- 합계와 같은 숫자
모바일 백그라운드 26 KB      <- 전체의 0.02%
```

NAVER도 같은 모양이었다. **대부분의 앱이 한쪽 회선만 쓰기 때문이다.**

한쪽 회선이 1%에 못 미치면 막대와 회선별 값 줄을 접기로 했다.
행 높이가 앱마다 달라지지만 그게 오히려 낫다.
두 회선을 섞어 쓰는 앱만 커지므로 **그 자체가 신호**가 된다.

판단은 화면이 아니라 `NetworkUsageSplit`에 뒀다. 데이터에 대한 질문이다.

백그라운드 줄은 정렬 기준이 백그라운드일 때만 보여준다.
"정렬 근거가 되는 값은 보여준다"는 규칙 하나로 정리된다.

실기기에서 **두 줄 → 아홉 줄**이 됐다.

### 2. 24개 막대에서 '7시'를 눈으로 찾을 수 없었다

가로축 라벨이 `0시`와 `23시` 둘뿐이었다. 카드에 적힌 글자를 읽어야만 몇 시인지 알았다.

`0 · 6 · 12 · 18 · 23시`에 라벨과 세로 격자선을 넣었다.
**라벨만 넣고 선을 빼면 여전히 세어야 한다.** 둘 다 필요하다.

일자별 그래프도 처음과 끝만 있었다. 한 달치면 서른 개다. 넷을 고르게 뽑아 적는다.

`UsageBarChart`는 `BarAxisLabel(index, text)` 목록을 받는다.
그리는 쪽은 시각인지 날짜인지 알 필요가 없다.

이 참에 그래프의 좌표 계산을 `PlotArea` 하나로 모았다.
탭 판정과 그리기가 각자 계산하면 누른 자리와 그려진 자리가 어긋난다.

### 3. 빠른지 느린지를 사용자가 암산하고 있었다

`1.19 GB / 6 GB · 19%`. 9월 4일이면 주기의 13%가 지났으니 빠른 것인데,
그걸 알려면 날짜를 세어 나눠 봐야 했다.

진행 막대에 **오늘 눈금**을 긋고 `주기의 13%가 지났습니다 · 예상보다 빠릅니다`를 적었다.
막대가 눈금을 넘었는지만 보면 된다.

5%p의 여유를 뒀다. 하루 이틀 치 출렁임에 문구가 바뀌면 그 말을 믿지 않게 된다.

지난 날수는 오늘을 포함해 센다. 오늘 쓴 양이 이미 `usedBytes`에 들어 있어서,
기준일이 어긋나면 **매일 아침 '빠름'으로 읽힌다.**

### 4. `모바일 백그`는 줄인 말이었고 그러고도 잘렸다

폭을 맞추려고 줄여 놓은 것이 화면 밖으로 잘려 나갔다.
네 칩에서 '순'을 떼니 `합계 · 모바일 · Wi-Fi · 백그라운드`가 되어 넷이 다 들어갔다.

### 5. `146.96  MB` 가 갈라져 보였다

전부 고정폭이라 단위 앞 공백이 숫자 한 자리만큼 벌어진 탓이다.
`ByteText`가 숫자는 고정폭으로, 단위는 한 단계 작은 일반 글꼴로 그린다.

문장 안에 값이 끼어드는 곳에는 쓰지 않았다. 거기서는 값이 표가 아니라 문장의 일부다.

### 겪은 것

`@Composable` 바로 뒤에 새 함수를 끼워 넣어 어노테이션이 원래 함수에서 떨어져 나갔다.
`This annotation is not repeatable` 하나로 다섯 개의 오류가 딸려 나왔다.
문서 주석 위에 붙은 어노테이션은 눈에 안 띈다.

고치려고 넣은 코드를 중복 제거 스크립트가 도로 지웠다.
`replace(..., 1)`이 지운 첫 번째가 방금 넣은 쪽이었다.

단위 테스트 120 → **129개**.

## 가독성 2차 — 걱정한 곳이 아니라 반대쪽이 문제였다

### 다크가 아니라 라이트가, 그리고 사실은 둘 다

새로 넣은 표시가 전부 `onSurface` 기반이라 다크 모드가 걱정돼 색을 조사했다.
결과는 반대였다. **라이트에서 다섯 중 넷이 대비 기준 미달**이었고,
하필 요금이 붙는 쪽인 모바일 주황이 2.53으로 가장 나빴다.

그런데 그 2.53도 틀린 숫자였다. **배경을 화면 바탕색으로 잡았는데
막대와 범례는 대부분 `Card` 안에 있다.** Material3 카드 바탕은 `surfaceContainerHighest`이고,
`Theme.kt`가 그 토큰을 지정하지 않아 M3 기본값이 그대로 쓰인다.

제대로 재니 라이트 2.09, 그리고 **다크도 안전하지 않았다** — 카드 위에서
Wi-Fi 2.94, 백그라운드 2.59. 직접 검산해 확인했다(#3A78E8 on #36343B = 2.93).

### 나누는 것 말고는 방법이 없었다

라이트 카드에서 3:1이려면 휘도 0.207 **이하**, 다크 카드에서 3:1이려면 0.207 **이상**.
두 구간이 한 점에서 스친다. **하나의 값으로 양쪽을 만족시키는 건 수학적으로 불가능하다.**

OKLab으로 옮겨 색상과 채도는 두고 명도만 재조준했다. 색상 이동 최대 2도.
'따뜻한 색 = 모바일'이 뒤집히지 않도록 채널 순서를 테스트로 고정했다.
대비만 맞추다 보면 색상이 밀려나기 쉽고, 그러면 사용자가 두 회선을 반대로 읽는다.

**라이트 모드 겉모습이 눈에 띄게 바뀌었다.** 주황이 `#E8833A`에서 `#A04B00`으로 진해졌다.
안 보이던 걸 보이게 하는 대가다.

부작용도 있다. 다섯 색을 같은 휘도로 맞추니 **색끼리의 대비가 1.0~1.04**가 됐다.
맞붙여 그리는 막대는 색각 이상 사용자에게 경계가 사라진다.
휘도를 어긋나게 배치해 푸는 건 제약상 불가능해서 칸 사이를 1dp 띄웠다.

위젯 색은 일부러 팔레트에 묶지 않았다. 위젯은 **배경화면을 알지 못해서**
흰 벽지와 검은 벽지 양쪽에서 읽혀야 하고, 테마별로 갈린 앱 팔레트는 한쪽 끝에서 반드시 실패한다.
값이 같아 보였던 건 우연이었다. 이름만 `LIMIT_PROGRESS_COLOR`로 바꿔 뜻을 드러냈다.

> **정정 (2026-09-11).** 우연이 아니었다. 옛 Wi-Fi 값이 그대로 남은 것이고,
> 명도만 옮기는 방식을 썼으니 색상이 같은 게 당연했다. 아래 「위젯 색 충돌을 확인하러
> 갔다가」 참고.

### 내가 만든 회귀 — 아이콘이 이름에서 떨어졌다

직전에 행을 1줄과 3줄로 갈라 놓으면서, 3줄 행에서 아이콘이
이름·막대·값 전체의 중앙으로 내려갔다. 약 15dp 어긋난다.

아이콘을 이름 줄 `Row` 안으로 옮기니 정렬이 저절로 맞았다.
중첩도 한 겹 줄었고 막대가 52dp 넓어졌다. **구조를 바꾸는 쪽이 더 단순했다.**

### 배경 띠 하나로 두 문제를 풀었다

막대가 크기를 말해 주지 않는 것(952 MB와 5 MB의 막대가 같은 길이)과
행 경계가 여백뿐인 것을, 행 배경에 행 높이 전체를 덮는 옅은 띠 하나로 함께 풀었다.
높이가 늘지 않아 압축 효과도 그대로다. 구분선은 넣지 않았다 — 가로선이 셋이 된다.

길이 기준은 **정렬 기준값**으로 했다. 목록이 그 값으로 줄 서 있으니 계단처럼 읽힌다.

### 접근성 — 만들어 놓고 쓸 수 없던 기능

막대를 눌러 값을 보는 기능을 방금 만들었는데,
스크린 리더로는 **그 막대를 고를 수조차 없었다.** 절반만 만든 셈이다.

투명한 칸을 겹쳐 트리만 만들었다. 여기서 두 가지 함정을 피했다.

- **`clickable`을 쓰면 안 된다.** 최소 터치 크기 48dp가 강제되어
  13dp짜리 칸들의 터치 영역이 겹치고 **잘 돌던 탭 판정이 깨진다.**
- **`Canvas`에 `contentDescription`을 붙이면 안 된다.** 두 번 탭할 때
  포커스 사각형 한가운데에 실제 터치가 합성되어 **엉뚱한 막대가 선택된다.**

축 눈금은 노드로 만들지 않았다. 눈금이 있는 이유는 막대 높이를 값으로 환산하기 위해서인데,
막대마다 값을 직접 읽어 주면 **환산할 대상이 없는 숫자**만 남는다.

'전체 누적'에서 막대가 수백 개가 될 수 있다는 것도 이번에 알았다. 상한 31개를 뒀다.

### TalkBack을 켜지 않고 검증했다

`adb shell uiautomator dump`가 접근성 트리를 그대로 뱉는다.

```
* 시간대별 사용량 그래프. 0시부터 23시까지 24개 시간대. 세로축 최대 60 MB. ...
* 0시, 사용 없음
* 5시, 55.72 MB     <- checked="true" (고른 막대)
...
* 다음, 합계 111.44 MB
```

막대 노드의 `bounds` 폭이 **36px(≈13dp)**로 유지된 것도 여기서 확인했다.
`clickable`이었다면 132px로 부풀었을 자리다.
목록 행은 한 노드로 병합되고 앱 이름이 따로 남지 않았다.

요약이 "60.00 MB"라고 읽는 걸 보고 `formatCompact`로 바꿨다.
화면 축 라벨은 "60 MB"인데 음성만 다르면, 눈으로 보는 사람과 귀로 듣는 사람이
서로 다른 화면을 말하게 된다.

단위 테스트 129 → **142개**.

## 정보 밀도 — 크기를 조금씩 줄여 더 많이 보여주기 (2026-09-04)

"내용의 사이즈를 조금씩 줄이더라도 더 많은 정보를 보여줄 수 있는 개선책은?"

### 먼저 쟀다

요약 화면이 세로 공간을 어떻게 쓰고 있었는지 (S23+, 콘텐츠 영역 약 740dp).

| 구간 | 높이 |
|---|---|
| 한도 카드 (6줄) | 202dp |
| 기간 단위 칩 | 48dp |
| 기간 이동 화살표 | 48dp |
| 합계 카드 | 136dp |
| 정렬 칩 (고정) | 48dp |
| **머리말 합계** | **502dp = 화면의 68%** |

앱을 보러 온 사람에게 화면의 3분의 2가 서론이었다. 앱은 네 줄 들어왔다.

### 줄일 수 없는 바닥이 있다

행 높이는 마음대로 줄일 수 없다. **터치 대상 최소 48dp**가 벽이다.
아이콘 32dp + 여백 8dp가 정확히 48dp고 거기가 끝이다. 행에서 짜낼 수 있는 건 20%뿐이었다.

**진짜 이득은 머리말에 있었다.**

### 앱 바 제목이 놀고 있었다

`데이터 사용량`이라는 고정 문구가 앱 바를 차지하고 있었다. 화면이 하나뿐인 앱에서
그 줄은 아무것도 알려주지 않는다. 그러면서 정작 계속 바뀌는 기간 라벨은
목록 위에 48dp짜리 줄을 따로 쓰고 있었다. 자리를 맞바꿨다.

### 짧은 문장 셋이 각각 한 줄을 쓰고 있었다

한도 카드가 여섯 줄이었다. 남은 양·하루치·속도가 전부 한 줄에 들어갈 만큼 짧은데도.
넷을 한 줄에 몰아넣어 봤더니 `하루 178.26 …`으로 단위가 잘렸다.

**줄마다 한 가지만 말하도록** 다시 묶었다 — 주기 / 사용 / 막대 / 남은 것.
경과율을 주기 줄로 올리자 남은 것 줄이 가로폭을 통째로 쓰게 됐다. 202dp → 140dp.

### 한 줄을 두 칸으로 나눴다

이름·막대·회선별 값이 각각 한 줄을 쓰던 것을 왼쪽 칸(이름·막대)과
오른쪽 칸(합계·회선별 값)으로 나누니 **아이콘 높이 안에 다 들어갔다.**
섞어 쓰는 앱의 행이 92dp → 56dp.

회선별 두 값에는 막대와 같은 색을 입혔다. 좁은 칸에 라벨을 다시 넣을 자리가 없는데,
색이 그 일을 대신한다. 지난번에 4.5:1로 맞춰 둔 팔레트라 글자로 써도 읽힌다.

### 몫(%)을 넣었더니 모순이 드러났다

행마다 `18%`를 붙였다. 높이는 안 늘고 정보는 하나 는다.

그런데 실기기에서 **Instagram이 `65%`인데 배경 띠는 거의 비어 있었다.**
띠는 정렬 기준값(모바일)을, 몫은 합계를 재고 있었다.
지난번에 "띠 길이가 단조 감소해 계단처럼 읽힌다"는 이유로 정렬 기준값을 골랐는데,
숫자를 하나 더 얹자 그 선택이 **한 줄 안의 모순**으로 나타났다.

셋(띠·몫·합계) 다 합계로 통일했다. 목록의 순서는 정렬 칩이 말해 준다.
한 줄 안의 표시들이 서로 어긋나는 쪽이 훨씬 나쁘다.

### 결과

| | 전 | 후 |
|---|---|---|
| 머리말 | 502dp | 336dp |
| 단일 회선 행 | 60dp | 48dp |
| 혼합 회선 행 | 92dp | 56dp |
| 첫 화면 앱 줄 수 | 4줄 | **7~9줄** |

버린 정보는 없고, 글자 크기를 줄인 것은 합계 하나뿐이다.

라이트·다크 양쪽 실기기 확인. 단위 테스트 142 → **145개**.

### 곁가지로 배운 것

`19% · 빠름`이 `19%  ·  빠름`으로 벌어졌다. 고정폭 글꼴에서는 구분점과 공백도
숫자 한 자리 폭을 차지한다. 세로로 나열되지 않는 값에는 고정폭을 쓸 이유가 없다.

## 설정에서 다크 모드 고르기 (2026-09-04)

기기 전체 설정을 따라가기만 하던 것을 앱에서 직접 고를 수 있게 했다.
`시스템 설정 따름 / 밝게 / 어둡게`.

`TracePhoneTheme`이 이미 `useDarkTheme` 매개변수를 받고 있어서 **테마 코드는 한 줄도 안 건드렸다.**
`MainActivity`가 저장된 값을 읽어 넘기는 것이 전부다.

### 진짜 문제는 시작 화면이었다

`themes.xml`이 정하는 시작 화면은 `values-night` 리소스 한정자라 **런타임에 못 바꾼다.**
저장만 하면 어둡게로 둔 사용자가 앱을 열 때마다 흰 화면을 먼저 보고 그 다음 어두운 화면을 본다.
콜드 스타트에서는 수백 ms라 그냥 넘길 수준이 아니다.

`UiModeManager.setApplicationNightMode`가 답인데 **API 31 이상 전용**이다(minSdk 26).
저장(DataStore)과 시스템 통보를 한 메서드 안에 묶었다. 떼어 놓으면 저장은 됐는데
시스템은 모르는 상태가 생기고, 그건 앱을 껐다 켜야만 드러난다.

### MODE_NIGHT_AUTO가 뭘 뜻하는지 확실하지 않았다

'시간 기반 자동'인지 '앱별 지정을 거두고 기기 설정으로 되돌림'인지 문서만으로는 갈렸다.
낮에 테스트하면 둘 다 밝게 나와서 **구분이 안 된다.**

'시스템 설정 따름'으로 둔 채 기기 야간 모드를 오가며 앱 구성을 봤다.

```
어둡게      + 시스템 no   -> 앱 구성에 night      (앱만 오버라이드)
시스템 따름 + 시스템 yes  -> 앱 구성에 night
시스템 따름 + 시스템 no   -> 없음
```

기기 설정을 따라간다. 시작 화면까지 맞는다는 것도 이 `night` 플래그가 증명한다.

### 곁가지

열거형 저장 값을 되돌리는 헬퍼가 `UsageViewPreferencesDataStore` 안에 사적으로 있었다.
두 번째 사용처가 생겨 `EnumPreference.kt`로 꺼냈다. "이름으로 저장한다"는 규칙도 거기로 옮겼다.

단위 테스트 145 → **149개**.

## 정리 한 판 (2026-09-04)

리뷰 네 갈래(재사용·단순화·효율·깊이)를 병렬로 돌렸다. 가장 아픈 지적은 **깊이** 쪽이었다.

### 저장소 안에 시스템 호출을 숨겨 두었다

`ThemePreferencesDataStore.setThemeMode()`가 저장과 `UiModeManager` 호출을 같이 했다.
"저장이 곧 적용이 되도록"이라는 이유를 붙였는데, 이 앱의 다른 설정들은 전부
**저장은 저장소가, 뒤따르는 일은 ViewModel이** 하고 있었다.
위젯 설정도 `setTextColor()` 다음에 `refresh()`를 부른다 — 잊을 위험은 똑같은데
거기서는 숨기지 않았다. 테마만 예외로 둔 게 특별 취급이었다.

증거도 있었다. `SettingsViewModel.selectThemeMode`에 "왜 applicationScope여야 하는지"를
설명하는 문단을 붙여야 했는데, **그 설명이 필요했던 이유가 곧 부수효과가 안 보였기 때문**이다.
`ThemeModeApplier`로 떼어내니 두 줄이 나란히 놓여 설명 없이도 읽힌다.

### 같은 catch 블록이 다섯 벌

DataStore 다섯 곳이 전부 `IOException -> 로그 -> emptyPreferences()`를 그대로 베껴 쓰고 있었다.
새 파일을 만들면서 여섯 번째를 보탠 셈이라 `recoveringFromReadFailure()`로 걷어냈다.
`SUBSCRIPTION_TIMEOUT_MILLIS = 5_000L`도 ViewModel 넷에 흩어져 있었다.

### getter가 목록을 훑고 있었다

`UsageSummaryUiState`의 `mobileTotalBytes`/`wifiTotalBytes`/`totalBytes`가 `get()`이라
읽을 때마다 목록을 다 셌다. 합계 카드 한 곳에서만 네 번, 목록 그릴 때 세 번 더 —
상태가 바뀔 때마다 같은 덧셈을 예닐곱 번 했다.

눈에 보일 만큼 느리지는 않았다(수백 개라도 1ms 미만). `by lazy`로 바꾼 건
빨라져서가 아니라 **"읽으면 훑는 getter"라는 함정을 없애려고**다.
목록 1위 값도 화면에서 세던 것을 이리로 옮겼다.

### 보류한 것

- **설정 화면 라디오 카드 공통화** — `DailyLimitCard`와 `ThemeModeCard`가 구조는 닮았지만
  한쪽엔 '비활성' 상태가 있다. 그 의미를 억지로 일반화하면 읽기가 더 나빠진다.
- **백분율 나눗셈 공통화** — `MonthlyLimitStatus`도 같은 버림 나눗셈을 쓰지만
  domain 모델이 UI 유틸에 기대게 만들 만한 크기가 아니다.

### 따로 남겨 둔 것

`DailyLimitCard`의 라디오 줄은 `clickable`을 써서 **스크린 리더가 라디오 버튼으로 읽지 못한다.**
새로 만든 `ThemeModeCard`는 `selectable(role = Role.RadioButton)`을 쓴다.
이번 범위 밖이라 손대지 않았다.

lint 지적 10 → **8건**. 단위 테스트 149개 유지.

## 15분을 5분으로 줄일 수 있나 (2026-09-07)

"데이터 체크가 15분 간격인데 5분으로 바꾸면 부하나 문제가 있나"에서 출발했다.
답을 찾다가 **질문의 전제 세 가지가 전부 틀렸다는 것**이 드러났다.

### 1. 15분 워커는 수집기가 아니다

DB에 쓰는 것은 6시간짜리 `DailyUsageSyncWorker`다.
15분짜리 `UsageAlertWorker`는 **Room 쓰기가 0행**이다.
주기를 바꿔도 기록되는 데이터의 정밀도는 조금도 달라지지 않는다.
빨라지는 것은 알림 시점과 위젯 숫자뿐이다.

### 2. 5분은 애초에 설정되지 않는다

`PeriodicWorkRequestBuilder`의 최소 주기가 15분이다. 더 작은 값을 넣으면 예외가 나지도,
그 주기로 돌지도 않고 `WorkSpec`이 조용히 900,000ms로 되돌린다.
게다가 등록이 `ExistingPeriodicWorkPolicy.KEEP`이라 **이미 설치된 기기는 상수를 바꿔도 반영조차 안 된다.**

우회로도 전부 막혀 있다.

| 방법 | 결론 |
|---|---|
| `NetworkStatsManager.registerUsageCallback` | 임계치가 **네트워크 종류 단위이지 UID 단위가 아니다.** 앱별로 걸 수 없고, 콜백은 프로세스가 살아 있는 동안만 온다 |
| 포그라운드 서비스 상주 | `targetSdk 37`이라 Android 15의 `dataSync` **6시간/24시간 상한**을 받는다. 초과하면 `onTimeout()`, 안 멈추면 ANR |
| `AlarmManager` 자체 재예약 | 값만 5분이 되고 Doze가 미룬다. 잦은 기상이 버킷 등급을 낮춰 **오히려 더 느려진다** |

### 3. 진짜 병목은 15분이 아니라 App Standby Bucket이었다

S23+(SM-S916N)의 `dumpsys jobscheduler`에서 이 기기가 실제로 쓰는
QuotaController 설정을 그대로 읽었다. 문서가 아니라 **이 기기의 살아 있는 값**이다.

| 버킷 | 창 크기 | 창당 최대 세션 | **실질 최소 간격** |
|---|---|---|---|
| EXEMPTED (배터리 최적화 예외) | 40분 | 75 | 제한 없음 |
| ACTIVE | 1시간 | 75 | 제한 없음 (15분 그대로) |
| WORKING_SET | 4시간 | 10 | 평균 **24분** |
| FREQUENT | 12시간 | 8 | 평균 **90분** |
| RARE | 24시간 | 3 | 평균 **8시간** |
| RESTRICTED | 24시간 | 1 | **하루 1회** |

우리 워커는 홀로 도니 실행 하나가 세션 하나다. 즉 **폰을 안 쓰는 동안 앱이 FREQUENT로만
떨어져도 90분이 상한**이고, RARE면 8시간이다. 5분은커녕 15분도 보장이 아니다.

`Minimum latency: +14m59s`, `Standby bucket: ACTIVE`, `Run time: earliest=+4m56s` —
폰을 쓰는 동안에는 의도대로 15분에 돈다. 문제는 안 쓸 때다.

### 실효성 있는 수단은 하나뿐이다

**배터리 최적화 예외.** 그러면 EXEMPTED 버킷이 되어 쿼터 제한이 사라진다.
그런데 `dumpsys deviceidle`의 화이트리스트 이력에 이런 기록이 남아 있었다.

```
[2026-09-03 01:29:35][add   ] com.dksystems.tracephone by com.android.settings
[2026-09-03 02:01:42][remove] com.dksystems.tracephone by package removed
```

**한 번 예외로 등록했는데 재설치 때 풀렸다.** 지금은 화이트리스트에 없다.
개발 중 재설치마다 조용히 풀리므로, 사용자 기기에서도 앱을 지웠다 깔면 같은 일이 벌어진다.

### 측정하며 알게 된 함정

- **USB로 연결해 두면 충전 상태라 Doze가 아예 동작하지 않는다.** 케이블을 꽂은 채
  야간 지연을 재려던 것은 처음부터 잴 수 없는 조건이었다.
  `adb shell dumpsys battery unplug`로 시스템에만 "뽑혔다"고 알리면 된다. 끝나면 `battery reset`.
- **주기 워커는 강제로 앞당길 수 없다.** `cmd jobscheduler run -f`를 걸어도 WorkManager가
  `Delaying execution ... because it is being executed before schedule`로 거부한다.
  (그리고 이 명령은 `-n androidx.work.systemjobscheduler` 네임스페이스를 줘야 작업을 찾는다.)
- 이 기기의 로그 링 버퍼는 **5 MiB에서 막혀 있고**(`-G`로 늘려도 거부) 약 35분이면 덮어쓴다.
  끊었다가 나중에 덤프하는 방식은 쓸 수 없다.

### 그래서 한 일 — 주기 대신 회당 비용을 줄였다

`UsageAlertWorker` 한 번에 오늘치 조회가 **3번 중복**되고 있었다.
`querySummary`는 `queryDay()` 한 번당 2회(MOBILE·WIFI)라 회당 **4 + 2N**회다(N = 위젯 개수).

| 진입점 | querySummary |
|---|---|
| `EvaluateUsageAlertsUseCase` | 2 |
| `EvaluateMonthlyLimitUseCase` → `readMobileUsageForPeriod` | 2 |
| `WidgetRefresher` → Glance → `GetWidgetUsageUseCase` | 2 × N |

워커만의 문제도 아니었다. `SettingsViewModel.applyMonthlyLimitMegabytes`는
한도를 한 번 저장할 때마다 최대 6회를 썼다.

**위젯이 결정적 제약이었다.** `WidgetRefresher.refresh()`는 Glance `updateAll()`을 부를 뿐이고
실제 로딩은 Glance가 자기 컴포지션 안에서 한다. 바깥에서 읽은 값을 건네줄 파라미터가 없다.
use case에 스냅샷 인자를 넘기는 안은 위젯·설정 경로를 못 덮어 6 → 4에 그치는데
인터페이스·use case·Fake·테스트가 전부 흔들린다. 교환비가 나쁘다.

세 경로가 **반드시 지나는 유일한 지점**인 `readTodayUsageFromSystem()` 안쪽에
짧은 수명의 메모(`TodayUsageMemo`, TTL 30초)를 두었다. **6회 → 2회, 위젯 2개면 8회 → 2회.**
고친 프로덕션 파일은 `UsageRepositoryImpl` 하나와 상수 하나뿐이고,
인터페이스·use case·ViewModel·위젯·기존 테스트는 한 줄도 바뀌지 않았다.

덤으로 위젯 숫자와 알림 판정이 이제 **같은 순간의 값**을 쓴다. 전에는 미세하게 어긋났다.

**숨긴 것은 상태가 아니라 의미 없는 재질문이다.** `NetworkStatsManager` 자체가
30초보다 촘촘하게 갱신되지 않으므로 정확도를 내주지 않는다.

지켜야 할 규칙 하나: **빈 목록은 기억하지 않는다.** 빈 목록은 값이 아니라
"권한 없음 또는 조회 실패"의 신호이고, 이를 기억하면 권한을 막 켠 사용자가 30초간 계속 0을 본다.
이 함정만 전용 테스트로 못 박았다.

### 진단 로그를 상설로 넣었다

전에는 `notifiedAppCount > 0`일 때만 로그가 남아 **워커가 돌았다는 사실 자체를 알 수 없었다.**
조건부 로그 둘을 무조건 남는 한 줄로 합쳤다.

```
[INFO ] Usage alert check finished: attempt=0, alertedApps=0, limitThreshold=none, elapsedMillis=347
```

`recordedAtEpochMillis`와 같은 결의 영구 진단 장치다. 실측 회당 **347ms**.

단위 테스트 149 → **154개**, lint 8건 유지.

### 아직 안 한 것

- **배터리 최적화 예외 안내** — 위 표대로라면 알림 지연을 실제로 줄일 수 있는 유일한 수단이다.
  설정 화면에서 현재 예외 여부를 보여주고 시스템 화면으로 보내는 안. **바로 아래에서 했다.**
- `strings.xml`의 "경고는 15분마다 확인합니다"는 그대로 두었다. 15분은 요청값으로는 사실이고,

## 배터리 최적화 예외를 화면에 드러냈다 (2026-09-07)

위 쿼터 표에서 알림 지연을 실제로 줄일 수 있는 수단은 **배터리 최적화 예외 하나뿐**이었다.
그런데 기존 `BackgroundRestrictionNotice`는 **예외 여부와 무관하게 늘 같은 말**을 하고 있었다.

그래서 사용자는 이미 해 두었는지 알 수 없었고, 더 나쁘게는
**앱을 지웠다 깔면 예외가 조용히 풀리는데** 그 사실을 알아챌 방법이 없었다.
실제로 이 앱도 그랬다.

```
[2026-09-03 01:29:35][add   ] com.dksystems.tracephone by com.android.settings
[2026-09-03 02:01:42][remove] com.dksystems.tracephone by package removed
```

### 한 일

`PowerManager.isIgnoringBatteryOptimizations()`로 실제 상태를 읽어 두 갈래로 보여준다.

| 상태 | 보이는 것 |
|---|---|
| 예외 적용됨 | "지금은 '제한 없음'으로 되어 있습니다. 경고가 제때 옵니다." — 차분한 색, 해결 방법 줄은 **숨김** |
| 최적화 대상 | "지금은 최적화 대상입니다. 폰을 오래 쓰지 않으면 경고가 몇 시간까지 밀릴 수 있습니다." — **error 색** + 해결 방법 |

값이 우리 화면 밖(시스템 설정)에서 바뀌므로 `ON_RESUME`마다 다시 읽는다.
같은 패턴이 `NotificationPermissionCard`에도 있어 `rememberSystemState`로 뽑았다.
`MutableState`를 돌려주는 이유는 알림 권한이 **요청 결과로 즉시 갱신**해야 하기 때문이다.

### 고르지 않은 것

예외를 곧바로 요청하는 대화상자(`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`)를 쓰지 않았다.
UX는 그쪽이 낫지만 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 권한이 필요하고
**Play 정책의 제한 목록**에 있어 배포 시 별도 심사를 받는다.
이 앱은 이미 `QUERY_ALL_PACKAGES`로 정당화 사유를 내야 하는데 하나 더 얹을 이유가 없다.
기존 코드도 같은 판단으로 앱 정보 화면을 골랐고 그 판단을 유지했다. 근거는 주석에 남겼다.

**색은 문제가 있을 때만 쓴다.** 적용된 상태를 초록으로 강조하지 않았다.
이 앱에서 초록은 이미 '직접 사용'이라는 뜻이 있고, 잘 된 상태까지 색을 쓰면
정작 문제가 있을 때 눈에 띄지 않는다.

### 실기기 확인 — 효과가 숫자로 증명됐다

S23+에서 예외를 부여하기 전후로 `dumpsys jobscheduler`를 읽었다.

```
예외 전:  Standby bucket: ACTIVE
예외 후:  Standby bucket: EXEMPTED
          exempted: com.dksystems.tracephone [RUN_ANY_IN_BACKGROUND allowed]
```

EXEMPTED는 40분 창에 75세션이라 사실상 제한이 없다.
**즉 예외를 두면 15분 주기가 실제로 지켜지고, 아니면 최대 8시간까지 밀린다.**
화면 문구가 이 차이를 그대로 말하고 있다.

문구 전환도 실기기에서 확인했다. 예외를 부여하고 홈으로 나갔다 돌아오니
빨간 경고가 차분한 확인 문구로 바뀌고 해결 방법 줄이 사라졌다.

단위 테스트 154개 유지, lint 8건 유지.

## 라디오 줄 접근성 — 그리고 보이는 것과 실제가 어긋나던 곳 (2026-09-07)

`DailyLimitCard`의 미리 정한 한도 줄이 `clickable`을 쓰고 있어
**스크린 리더가 라디오 버튼이 아니라 그냥 버튼으로 읽었다.** '선택됨/선택 안 됨'이 들리지 않는다.
같은 모양의 `ThemeModeCard`는 `selectable(role = Role.RadioButton)`을 쓰고 있어 대비가 명확했다.

고치려고 열어 보니 **더 큰 문제가 같이 있었다.**

```kotlin
.clickable { onPresetSelected(limitBytes) }          // 항상 누를 수 있음
RadioButton(enabled = !settings.usesCustomLimit)      // 그런데 회색으로 흐려 보임
```

직접 입력값을 쓰는 동안 줄은 **회색으로 흐려 보이는데 누르면 값이 조용히 바뀌었다.**
눈으로 보는 사람은 "비활성이구나" 하고 넘어가고, 실수로 눌러도 바뀐 줄 모른다.
스크린 리더에 역할만 붙였다면 이 어긋남이 그대로 남았을 것이다.

### 고른 답 — 보이는 대로 동작하게 한다

`selectable(selected, enabled, role = Role.RadioButton, onClick)`으로 바꾸면서
**`enabled`를 실제로 넘겼다.** 흐려 보이면 정말로 안 눌린다.

되돌리는 길이 막히지 않는다. 직접 입력 칸이 이미 "0을 넣으면 위에서 고른 값을 씁니다"라고
안내하고 있고, 단계 수도 전과 같다(둘 다 두 단계).

줄을 `PresetLimitRow`로 뽑아 `ThemeModeCard`의 `ThemeModeRow`와 같은 모양으로 맞췄다.
`DailyLimitCard`가 65줄이었던 것도 함께 줄었다.

> 이건 접근성 수정이면서 **동작 변경**이다. 전에는 흐린 줄도 눌렸다.
> 그 동작이 의도된 것이 아니라 `clickable`과 `RadioButton(enabled=)`가 따로 놀던 결과라고 판단했다.

### 안 고른 답

- **항상 누를 수 있게 두고 회색만 없애기** — "지금 적용 중이 아니다"라는 정보가 사라진다.
  카드 맨 아래 '현재 적용' 줄만으로는 어느 항목이 후보인지 알기 어렵다.
- **`stateDescription`으로 "지금은 적용 안 됨" 덧붙이기** — 이 값은 '선택됨/선택 안 됨'을
  **대체**한다. 라디오의 핵심 정보를 잃으면서 부가 정보를 얻는 교환이라 손해다.

단위 테스트 154개 유지, lint 8건 유지.

### 실기기 확인 — 접근성 트리를 직접 읽었다

TalkBack을 켜지 않고 `uiautomator dump`로 노드를 봤다. 줄 노드가 이렇게 바뀐다.

```
직접 입력 사용 중:  checkable="true" checked="true/false" enabled="false" focusable="false"
직접 입력 0:        checkable="true" checked="true/false" enabled="true"  focusable="true"
```

`checkable`/`checked`가 붙어 **선택 상태가 노출된다.** 전에는 그냥 눌리는 줄이라 이 정보가 없었다.
`enabled`가 화면의 흐림과 일치하는 것도 확인했다.

딸려 오는 결과 하나: 비활성일 때 `focusable="false"`라 **스크린 리더가 그 줄들을 건너뛴다.**
누를 수 없는 항목을 훑게 하지 않는 편이 낫다고 보고 그대로 두었다.
지금 무엇이 적용 중인지는 카드 맨 아래 '현재 적용' 줄이 말해 준다.

## 5분 주기 판정 — 되긴 된다, 조건부로 (2026-09-07)

앞에서 "5분은 불가능"이라고 적었는데 **그건 `PeriodicWorkRequest` 기준이었다.**
빠져나갈 길이 하나 있었다.

### 방법

**15분 하한은 `PeriodicWorkRequest`에만 걸린다.** `OneTimeWorkRequest.setInitialDelay()`에는 하한이 없다.
작업이 끝날 때 자기 자신을 5분 뒤로 다시 걸면 5분 주기가 된다.
`setInitialDelay`는 JobScheduler의 `Minimum latency`로 그대로 내려간다.

### 되는 건 배터리 최적화 예외 덕분이다

5분 주기(40분에 8회)를 쿼터에 대입하면 이렇다.

| 버킷 | 창당 세션 한도 | 5분 주기 |
|---|---|---|
| **EXEMPTED** | 40분에 75 | 통과 |
| ACTIVE | 1시간에 75 | 통과 |
| WORKING_SET | 4시간에 10 | **막힘** |
| FREQUENT | 12시간에 8 | **막힘** |
| RARE | 24시간에 3 | **막힘** |

**예외가 없으면 5분을 노리다 15분보다 나빠진다.** 쿼터를 몇 분 만에 태우고 남은 시간을 통째로 막힌다.
Doze도 같은 이유로 통과한다 — 화이트리스트 앱은 API 24 이상에서 job이 유예되지 않는다.

### 그래서 장치를 둘 붙였다

| 장치 | 역할 |
|---|---|
| **안전망** | 15분 `PeriodicWork`를 그대로 유지. 시스템이 관리하니 끊길 일이 없고, 빠른 연쇄가 끊기면 되살린다 |
| **자동 후퇴** | 예약할 때마다 예외 여부를 본다. 예외가 풀리면 빠른 작업을 **걷어내고** 15분에 맡긴다 |

두 번째가 핵심이다. 사용자가 시스템 설정에서 예외를 끄면 다음 판정 때 스스로 물러난다.
`ExistingWorkPolicy`는 앱 시작 때 `KEEP`(걸려 있으면 그대로), 판정 직후엔 `REPLACE`(지금부터 다시 셈)다.
두 갈래가 잇달아 돌아도 다음 확인까지의 간격이 항상 같아진다.

### 실기기 확인 — 세 번 연속 정확히 5분

```
등록:  안전망   Minimum latency: +2m28s246ms   (이전 주기의 잔여)
       빠른 판정 Minimum latency: +4m59s979ms
       둘 다 Standby bucket: EXEMPTED

실행:  16:29:38.385  elapsedMillis=217
       16:34:38.763  elapsedMillis=284   (+5분 0.378초)
       16:39:39.134  elapsedMillis=305   (+5분 0.371초)
```

한 주기당 0.37초씩 밀리는데, 이는 판정에 걸린 시간만큼 다음 예약이 늦게 시작되기 때문이다.
누적되지 않고 매번 그만큼만 밀리므로 무시해도 된다.

**확인의 한계**: USB로 연결한 채 쟀으므로 **Doze에 들어간 상태는 재지 못했다.**
예외가 있으면 job이 유예되지 않는 것이 문서상의 동작이고 `RUN_ANY_IN_BACKGROUND allowed`도 확인했지만,
실제 깊은 잠에서의 간격은 아직 관측하지 않았다.

### 곁다리로 고친 것

`strings.xml`에 **"15분"이 하드코딩**되어 상수와 끊어져 있었다. 주기를 바꿔도 화면이 따라오지 않는다.
예외 여부에 따라 실제 값이 그대로 보이도록 `%1$d`로 바꿨다.

배터리 예외 확인도 화면과 예약이 같은 판단을 쓰도록 `core/BatteryOptimization.kt` 하나로 모았다.

### 비용

하루 기상 96회 → **288회**, 하루 CPU 약 30초 → **약 86초**.
회당 비용을 미리 줄여 둔 것(`querySummary` 6회 → 2회)이 여기서 값을 한다.
실측 회당 217~305ms로 이전 347ms보다도 낮다.

단위 테스트 154개 유지, lint 8건 유지.

## 야간 실측 — 예외로도 깊은 Doze는 못 넘는다 (2026-09-08)

어제 "충전 중 5분"까지만 확인하고 남겨 둔 것을 밤새 쟀다.
기기 링 버퍼가 35분이면 덮어써지므로 `logcat -f`를 `nohup`으로 분리해
`/data/local/tmp/tp_alert.log`에 쌓았다. 부모 PID가 1로 떨어져 나가 연결이 끊겨도 살아남았다.
**폰은 뽑아 두었다** — 충전 중에는 Doze가 아예 안 걸려 측정이 무의미하다.

### 결과 — 157회 / 15.0시간

| 구간 | 중앙값 | 평균 | p90 | 최악 |
|---|---|---|---|---|
| 낮·저녁 (16~01시) | **5.0분** | 5.0분 | 5.7분 | 8.0분 |
| 새벽 (00~07시) | 5.0분 | 7.0분 | 20.0분 | **30.0분** |

시간대별로 보면 나빠지는 구간이 정확히 드러난다.

```
00시 5.0    01시 6.1    02시 23.1   03시 5.8
04시 13.3   05시 10.5   06시 5.0    07시 5.0
16~23시 전부 5.0 (최악 8.0)
```

**02~06시만 무너진다.** 30.0분짜리 간격이 두 번 연속(03:59→04:29→04:59) 나온 것이
Doze 유지보수 창의 모양 그대로다.

### 결론 — 문서와 실제가 다르다

"화이트리스트 앱은 API 24 이상에서 job이 유예되지 않는다"가 문서상의 동작이고
`RUN_ANY_IN_BACKGROUND allowed`도 확인했지만, **이 기기에서는 깊은 Doze에 들어가면 밀린다.**
삼성이 자체 절전 계층을 얹은 것으로 보인다. 예외는 만능이 아니라 **완화**다.

그래도 얻은 것이 크다. 전체의 63.5%가 5분이고, 최악이 30분이다.
예외가 없었다면 RARE 등급의 24시간에 3회 상한에 걸려 **하루 세 번**이었을 것이다(쿼터 표 기준).

간격이 4.5분 미만인 것이 14.1% 있는데, 15분 안전망이 5분 판정 직후에 겹쳐 도는 경우다.
중복 조회는 저장소 메모가 막아 주므로 해로울 것은 없다.

### 배터리 — 0.26%

`dumpsys batterystats --charged`:

```
UID u0a512: 11.9 mAh
  fg 0.114 (1m 55s) / bg 0.738 (1h 42m 57s) / cached 5.57 (13h 20m)
전체 소모 4541 mAh 중 11.9 mAh = 0.26%
```

실제로 일한 몫(bg)은 0.738 mAh다. 대부분은 프로세스가 캐시에 떠 있던 값이다.
**5분 주기로 올려도 배터리에서 보이지 않는다.**

### 회당 소요의 이상치 — 겁먹을 것은 아니었다

```
중앙값 250ms / 평균 1201ms / 최대 113,225ms
```

처음에는 "중앙값의 450배"라며 문제로 적었는데, 따져 보니 **두 가지를 잘못 봤다.**

**하나. `elapsedMillis`는 CPU 시간이 아니다.** `SystemClock.elapsedRealtime()` 차이라
기기가 잠든 시간과 락을 기다린 시간까지 전부 센다. "113초 동안 CPU를 잡았다"가 아니라
"끝나기까지 벽시계로 113초"다. 실제 CPU 몫은 배터리 통계의 `bg 0.738 mAh / 1시간 42분`이다.

**둘. 113초는 측정하다 내가 만든 상황이었다.** 로그를 붙이면 원인이 그대로 보인다.

```
17:50:37  TracePhone started          ← install -r 직후 프로세스 재시작
17:51:01  Package not found uid=0
17:51:01  Package not found uid=1051
17:52:14  Package not found uid=2904  ← 연속된 UID 조회 사이에서 73초 정지
17:52:54  finished elapsedMillis=113225
```

앱을 막 설치해 PackageManager가 새 APK를 스캔·최적화하느라 바빴고 `getPackagesForUid()`가
그 락을 기다렸다. 5분 뒤 실행은 356ms로 돌아왔다. **정상 동작에서 생기는 일이 아니다.**

진짜 위험은 배터리가 아니라 **WorkManager의 10분 한도**다. 넘기면 워커가 강제 종료되고
5분 연쇄가 끊긴다. 113초는 그 19%이고, 끊겨도 15분 안전망이 되살린다.
**고칠 것이 없다.**

### 다만 하나 — 조용히 건너뛴 판정이 있었다

```
05:29:34  조회 로그 있음 → finished 로그 없음
05:35:30  finished (elapsed 29592)
```

05:29:34에 시작한 판정이 **완료 로그를 남기지 못했다.** 예외였다면 에러 로그가 남았을 텐데
아무것도 없으니 프로세스가 도중에 정리된 것으로 보인다. 새벽 Doze 구간이라 앞뒤가 맞는다.

157회 중 1회고 다음 판정이 6분 뒤에 정상으로 돌았으니 실해는 없다.
다만 **"판정이 조용히 건너뛰어질 수 있다"**는 사실은 기록해 둔다.
알림이 한 주기 늦는 것 이상은 아니다 — 배수 판정이 멱등이라 놓친 것이 사라지지는 않는다.

### 정리

측정 후 기기의 logcat 프로세스를 죽이고 로그 파일을 지웠다.
배터리 최적화 예외와 EXEMPTED 버킷은 유지한다.

## 위젯 색 충돌을 확인하러 갔다가, 앱에서 더 큰 것을 찾았다 (2026-09-11)

### 처음 의심한 것

"위젯은 모바일만 보여주는데 막대가 파랑이다. 앱에서 파랑은 Wi-Fi다."

재 보니 우연이 아니었다. OKLab으로 옮기니 위젯 `#3A78E8`과 앱 Wi-Fi는
**색상 차 0.5°, 채도 차 0.001**이었다. 명도만 라이트/다크 Wi-Fi 사이에 놓인다.

경위도 찾았다. 예전 Wi-Fi 색이 `#3A78E8`이었고, 대비 때문에 앱 쪽만
`#1F5FCC`/`#7AABFF`로 옮기면서 위젯이 원래 값에 남은 것이다. 그때
"색상과 채도는 유지한 채 명도만" 옮겼으니 색상이 같은 게 당연하다.
이 문서 앞부분에 **"값이 같아 보였던 건 우연"**이라고 적어 두었는데, 틀린 기록이었다.

### 그런데 이건 고칠 가치가 없었다

위젯에는 Wi-Fi가 아예 나오지 않는다. 오독해도 도달할 틀린 결론이 없다.
형태도 다르다 — 앱의 회선 색은 *범례 붙은 분할 막대*, 위젯 것은 *트랙 깔린 진행 막대*다.

그리고 고치는 값이 더 나빴다. 모바일 주황 `#A04B00`으로 바꾸면 벽지 대비 여유가
4.17 → 3.50으로 깎이고, 다크 모바일 `#F5904A`는 흰 벽지에서 2.34라 아예 못 쓴다.
**절반만 맞추려고 물리적 안전 여유를 버리는 거래**였다.

### 진짜 문제는 앱 쪽에 있었다

레이아웃을 보다가 찾았다. `UsageSummaryScreen`이 한도 카드와
`UsageTotalsCard`(모바일/Wi-Fi 이름표 붙은 분할 막대)를 **카드 하나 간격으로** 붙여 놓는다.

그런데 한도 막대가 `colorScheme.primary`다. `Theme.kt`가 동적 색상을 타므로
**이 색은 배경화면에서 나온다.** 벽지가 따뜻하면 한도 막대가 주황이 되고,
바로 아래에 '모바일'이라고 적힌 주황 막대가 놓인다. **같은 화면에서 뜻이 겹친다.**

`design.md`는 "동적 색상에는 휩쓸리지 않는다"고 적고 있었다. 그 보호는 `LocalUsageColors`
(회선·상태 색)에만 걸려 있었고 한도 막대는 밖에 있었다. **문서가 사실이 아닌 불변식을 적고 있었다.**

### 초과색은 멀쩡했다 — 바이트코드로 확인

`colorScheme.error`도 동적이면 같은 문제일 텐데, 아니었다.
`dynamicLightColorScheme31`이 `lightColorScheme$default`를 마스크 `62914560`으로 부른다.
`62914560 = 60 × 2^20`이므로 비트 22·23·24·25가 서 있고, 그 자리가
error·onError·errorContainer·onErrorContainer다. **네 값을 기본값에 맡긴다 = 벽지를 안 탄다.**

즉 초과 구간은 원래 안전했고 정상 구간만 문제였다. 고칠 범위가 절반으로 줄었다.

### 고치려다 기존 결함을 찾았다

정상 구간을 중립색으로 내리려 했더니, '오늘' 눈금이 걸렸다. 톤으로 재 보니
**눈금은 채움 안에 들어가면 이미 안 보이고 있었다** — 라이트 2.65, 다크 1.32.
색상 차이로만 버티던 것이라, 채움을 중립으로 내리면 그 버팀목마저 사라진다.

한 색으로는 풀 수 없다는 것도 계산으로 확인했다. 라이트에서 채움이 트랙(tone 90)과
눈금(tone 10) 양쪽과 3:1이려면 tone 44~54여야 하는데, **다크에서는 트랙(tone 30)과
눈금(tone 90) 사이에 그런 톤이 아예 없다.**

그래서 눈금이 **자기가 놓인 바닥의 반대색**을 쓰게 했다. 채움 안이면 트랙 색,
트랙 위면 채움 색. 그러자 세 대비가 `onSurfaceVariant` 대 `surfaceVariant` 한 쌍으로
환원되면서 라이트 7.24 / 다크 5.49가 되었다.

### Gemini와 갈린 지점

Gemini는 위젯 파랑을 "명백한 에러"라며 모바일 주황 `#A04B00`으로 바꾸라고 했다.
대비가 "검정 4.1 / 흰색 5.0"이라고 했는데 검산하니 **3.50 / 6.00**이었다.
통과는 하지만 여유가 줄고, 다크 값은 못 쓴다는 점을 Gemini는 보지 못했다. 받아들이지 않았다.

반대로 채움색으로 `onSurface`(라이트 거의 검정, 다크 거의 흰색)를 쓰려던 내 안은
Gemini가 **다크 모드 눈부심과 위계 교란**을 근거로 `onSurfaceVariant`를 권했고,
계산상 둘 다 통과하므로 부드러운 쪽을 택했다. **이건 받아들였다.**

Gemini가 짚은 것 중 내가 놓친 것이 하나 있다 — 위젯 `progressTrack`이 글자색 알파 0.25라,
배경 투명도를 올리면 중간 밝기 벽지에서 막대 끝이 묻힐 수 있다. 기본값은 불투명이라
당장 문제는 아니고, 이번 사안과 별개라 손대지 않았다.

### 위젯은 함께 못 고친다 — 수학이 막았다

앱과 색을 맞추고 싶었지만 위젯에서는 중립색이 불가능했다.
위젯 트랙은 '글자색 alpha 0.25를 배경 위에 합성'한 값이라 여유가 없다.

야간 AUTO 모드에서 트랙 휘도가 0.080이니 채움이 트랙과 3:1이려면 **Y ≥ 0.340**인데,
흰 배경화면과 3:1이려면 **Y ≤ 0.300**이다. 겹치지 않는다. 주/야로 나눠도 야간이 안 풀린다.

그래서 위젯은 색상 차이로 끝을 드러낼 수밖에 없다. **앱과 위젯이 다른 색인 데에는
이유가 있다**는 기존 설계 주장이 여기서도 그대로 성립했다.

### 남겨 둔 것

위젯 막대를 회선·상태 어느 쪽도 아닌 색상(청록 ~200° 등)으로 옮기는 안은 후보로만 적어 뒀다.
이번 요청 범위가 아니었고, 단독으로는 값어치가 크지 않다.

### 배운 것

**문서에 적은 단언은 범위를 같이 적어야 한다.** "동적 색상에 휩쓸리지 않는다"는
회선·상태 색에 대해서는 참이었지만, 읽는 사람은 화면 전체로 읽는다.
범위를 적지 않은 단언은 시간이 지나면 거짓말이 된다.

그리고 **눈에 띄는 쪽이 더 나쁜 쪽은 아니다.** 위젯 파랑은 바로 보였지만 무해했고,
앱 한도 막대는 벽지에 따라서만 드러나 여태 아무도 보지 못했지만 실제로 뜻이 겹쳤다.

## 앱별 목록을 모바일 중심으로 바꿨다 (2026-09-15)

### 요구는 다섯 줄이었는데 결정할 것은 일곱 가지였다

"모바일 데이터를 얼마만큼 사용했는지 보는 게 주 목표이니 사용량에는 모바일만 표시하고,
그래프의 MAX는 하루사용량 기준으로 하되 넘는 앱이 있으면 가장 큰 사용량을 MAX로,
자리가 남으면 와이파이는 작게."

읽고 바로 구현할 수 없었다. **'하루 사용량'이 무엇인지가 정해져 있지 않았다.**
후보가 셋이었고 셋 다 그럴듯했다.

| 후보 | 성질 |
|---|---|
| 한도 ÷ 주기 일수 | 주기 내내 고정. 어제와 오늘을 견줄 수 있다 |
| 남은 양 ÷ 남은 날수 | 한도 카드가 쓰는 값. 많이 쓴 다음 날 기준이 줄어든다 |
| 따로 지정 | 한도를 안 쓰는 사람도 기준이 생긴다 |

물어서 **한도 ÷ 주기 일수**로 정했다. 물어보길 잘했다 — 나는 한도 카드와 같은 값
(남은 양 ÷ 남은 날수)을 쓰려던 참이었는데, 그러면 **같은 사용량인데 막대가 날마다 달라진다.**
기준이 움직이는 자는 자가 아니다.

### 기간이 주·월일 때가 두 번째 함정이었다

하루치를 자로 대면 주·월에서는 거의 모든 앱이 기준을 넘는다. 그러면 `maxOf` 규칙에 따라
결국 '가장 큰 앱' 기준으로 되돌아간다. **기준이 있는 척하면서 실제로는 없는 상태**가 된다.

사용자가 '일 보기에서만 쓴다'를 골랐다. 코드가 정직해졌다 — 주·월에서는 하루 기준이 0이고,
0이라는 것은 '기준 없음'이라고 함수 이름과 주석에 적혀 있다.

### 크기 표시가 이미 둘이었다는 것을 늦게 알았다

줄 뒤에 깔린 배경 띠(합계/가장 큰 앱)와 모바일:Wi-Fi 분할 막대. 둘 다 '크기'를 말하는데
재는 대상이 달랐다. 여기에 새 막대를 더하면 셋이 된다.

사용자는 **둘 다 만들고 설정에서 고르게** 하자고 했다. 처음엔 중복 같았는데, 짜 보니
맞바꿈 관계가 분명했다 — 진한 막대는 비교가 쉽고 2줄, 옅은 띠는 1줄이라 두 배로 들어온다.
어느 쪽이 나은지는 목록 길이와 눈에 달렸고, 그건 내가 정할 일이 아니었다.

**대신 한 화면에 둘 다 두지는 않았다.** 같은 값을 두 번 그리는 것이라 정보가 늘지 않는다.

### Gemini와 갈린 곳

Gemini는 세 가지를 강하게 권했고 둘을 받지 않았다.

1. **"설정 대신 목록 상단 토글"** — 발견성 논리는 맞지만 사용자가 "설정에서 선택"을
   명시적으로 요청했다. 사용성 일반론이 구체적 지시를 이기지 않는다.
2. **"ViewModel에서 combine해라"** — `AppUsageRowContext`는 **지금도 화면에서 만든다.**
   규칙(`appListScaleOf`, `dailyReferenceBytesOf`)을 순수 함수로 빼 테스트하면
   화면에 남는 것은 값을 건네는 일뿐이다. ViewModel에 흐름을 하나 더 만드는 값이 없었다.
3. **"정렬이 Wi-Fi순일 때 큰 숫자가 모바일이면 UX가 붕괴한다"** — 지적 자체는 옳다.
   하지만 큰 숫자를 정렬 기준값으로 바꾸는 쪽이 더 나쁘다. `MOBILE_BACKGROUND` 정렬에서
   `sortKeyOf`는 포그라운드 구분이 없는 앱에 0을 돌려주므로 **데이터를 분명히 쓴 앱에
   커다랗게 `0 B`가 찍힌다.** 이건 예전에 이미 겪고 적어 둔 함정이었다. 그대로 두고 보고했다.

### 낭독이 어긋날 자리를 없앴다

예전 구조는 화면과 스크린 리더가 **각자 조건문을 들고 있었다.** 어느 줄에 Wi-Fi를 적고
어느 줄에 백그라운드를 적는지가 두 벌로 존재했고, 한쪽만 고치면 보이는 것과 들리는 것이
어긋난다. 그것을 잡으려고 테스트가 두 조건을 나란히 검사했다.

이번에 낭독이 **화면이 만든 글자를 그대로 받게** 했다. 조건이 한 벌이라 어긋날 자리가 없다.
테스트로 잡는 대신 **구조로 막았다.** 다만 그러면서 조건이 Composable 안으로 들어가
테스트가 닿지 않게 되어, 판단만 `showsBackgroundValue`로 다시 떼어냈다.

### 검증

조건을 뒤집어 테스트가 실제로 잡는 것을 확인했다.

| 주입 | 결과 |
|---|---|
| `maxOf` → `minOf` | 3건 실패 |
| `hasKnownPortion` 조건 제거 | 1건 실패 |

### 배운 것

**요구를 그대로 받아쓰면 안 되는 낱말이 있다.** '하루 사용량'은 다섯 글자인데 후보가 셋이었고,
셋의 동작이 서로 크게 달랐다. 물어보는 데 든 비용보다 잘못 만들었을 때의 비용이 훨씬 컸다.

### 고친 뒤 — 실기기가 설계를 뒤집었다 (2026-09-15)

`maxOf(가장 큰 앱, 하루 기준)` 규칙을 그대로 구현하고 S23+에 올렸더니 이렇게 나왔다.

```
TMAP              54%  7.37 MB
▌░░░░░░░░░░░░░░░░░░░░░░   ← 3.7%
카카오톡           16%  2.30 MB
▌░░░░░░░░░░░░░░░░░░░░░░   ← 1.2%
```

한도 6 GB / 30일이면 하루 기준이 **200 MB**인데 그날 가장 많이 쓴 앱이 **7.37 MB**였다.
자가 200 MB로 잡혀 모든 막대가 4% 이하가 됐다. **"각 앱별 비교가 가능하도록"이라는
요구의 목적 자체가 무너졌다.**

Gemini가 검토에서 "하루 기준보다 한참 적게 쓴 날에는 시각적으로 너무 비어 보일 수 있다"고
짚었던 바로 그 지점이다. 그때는 '인지해야 한다' 정도로 받아들였는데, 실제 수치로 보니
예상보다 훨씬 심했다. **경고를 읽는 것과 화면을 보는 것은 다르다.**

고침은 방향을 뒤집는 것이었다. 자는 **언제나 가장 큰 앱**으로 두고,
하루 기준은 **눈금 하나**로 옮겼다. 비교는 언제나 되고 기준도 함께 보인다.

눈금이 필요해지면서 한도 진행 막대가 이미 쓰던 규칙(자기가 놓인 바닥의 반대색)을
그대로 쓸 수 있었다. `ui/component/BarMarker.kt`로 옮겨 두 막대가 함께 쓴다.
**며칠 전 한도 막대를 고치며 만든 것이 여기서 그대로 쓰였다.**

#### 기준이 자를 넘을 때

눈금을 오른쪽 끝에 붙이면 '가장 큰 앱이 곧 하루치'로 읽히는데, 실제로는
아무도 근처에 가지 못했다는 뜻이라 정반대다. **그릴 수 없으면 그리지 않는다.**
눈금이 없는 것 자체가 '오늘은 아무도 하루치에 닿지 않았다'는 말이 된다.

#### 실기기 확인

오늘(9/15)은 가장 큰 앱이 7.37 MB라 눈금이 없다. 눈금이 실제로 그려지는지 보려고
DB 사본을 떠서 가장 많이 쓴 날을 찾았다 — **9월 1일, 해리포터 507 MB.**

| 줄 | 눈금 | 바닥 |
|---|---|---|
| 해리포터 507 MB | 어두운 홈 | 채움 안 (트랙 색) |
| 다음 254 MB | 어두운 홈 | 채움 안 |
| 카카오맵 21 MB 이하 | 밝은 선 | 트랙 위 (글자색) |

두 색 규칙이 한 화면에서 동시에 보였다. 모든 줄의 눈금이 같은 x 자리에 선다.

#### 배운 것

**설계 검토에서 받은 경고를 '알아 두기'로 넘기면 안 된다.** Gemini가 정확히 이 문제를
지적했고 나는 수긍했는데, 그러고도 그대로 구현했다. 경고가 실제로 얼마나 나쁜지는
숫자를 넣어 봐야 안다 — 이 기기의 한도와 하루 사용량을 대입해 봤다면
코드를 쓰기 전에 알 수 있었다.

### 세 번째 자 — 사용자가 모순을 짚었다 (2026-09-15)

눈금으로 고친 화면을 보고 사용자가 말했다.
"맥스를 모바일 전체 사용량으로 하고 각각의 앱 사용량을 그래프로 표시하면 가독성이 좋아질 것 같은데?"

맞는 지적이었다. 내 구현에는 **한 줄 안에 분모가 둘** 있었다.

```
TMAP    54%  7.37 MB      ← 숫자는 전체(13.58 MB) 대비
████████████████████      ← 막대는 가장 큰 앱(7.37 MB) 대비 = 100%
```

같은 줄에서 `54%`와 가득 찬 막대가 나란히 놓인다. **예전 `sizeFractionOf` 주석이
정확히 이 실수를 경고하고 있었는데**("띠·몫·합계 셋 다 같은 기준을 두어 함께 늘고 함께 준다"),
내가 회선을 모바일로 바꾸면서 그 규칙을 깼다.

#### 상대 비교는 똑같다

전체 기준으로 바꾸면 모든 막대에 같은 배수(가장 큰 앱 ÷ 전체)가 곱해질 뿐이라
**앱끼리의 비율은 조금도 달라지지 않는다.** 대신 막대가 뜻을 갖는다 —
전에는 긴 막대가 '1등'만 말했고 조용한 날의 2 MB짜리 앱도 꽉 찼다.
이제는 '오늘 모바일의 절반을 이 앱이 썼다'가 된다.

#### 하루 기준 때와 뭐가 다른가

둘 다 "막대가 짧아진다"는 위험이 있는데 성질이 다르다.

| 자 | 1등 막대의 하한 |
|---|---|
| 하루 기준(외부 상수) | 없음. 실제로 3.7%까지 떨어졌다 |
| 전체 합계(데이터에서 나옴) | `1 / 앱 수`. 실측 54%(9/15) · 62%(9/1) · 77%(9/9) |

**데이터와 무관한 상수는 자가 될 수 없다**는 것이 이번 교훈이다.

#### 실기기 확인

9월 1일(모바일 822 MB, 하루 기준 200 MB)에서 세 가지가 한 화면에 다 나왔다.

- 막대와 숫자 일치: 해리포터 61%/61%, 다음 30%/30%
- 눈금이 모든 줄에서 같은 자리(24.3% = 200÷822)
- 눈금 색 두 가지: 해리포터·다음은 채움 안이라 어두운 홈, 나머지는 트랙 위라 밝은 선

#### 배운 것

**내가 깬 규칙을 사용자가 찾았다.** 주석에 경고까지 적혀 있었는데 회선을 바꾸는 데만
집중하느라 못 봤다. 표시를 하나 바꿀 때는 그 표시와 분모를 나눠 쓰던 것들을
같이 훑어야 한다.

### 한도 카드가 사라지던 이유, 그리고 합계 카드의 주인공 (2026-09-15)

#### 근거가 남아 있지 않은 조건

`monthlyLimitStatus?.takeIf { uiState.selection.isCurrent }` — 한 줄인데 **주석도 문서도
없었다.** 왜 숨겼는지 코드에서 되짚어야 했다.

되짚은 결과는 이렇다. 한도 카드는 청구 주기를 보는 것이라 화면의 기간 선택과 무관하게
늘 '지금'을 계산한다. 과거로 가면 '그때 데이터' 위에 '지금 데이터'가 얹힌다.
**말이 되는 걱정이지만, 카드가 스스로 기간을 적고 있다는 것을 놓친 판단이었다.**

`요금제 한도 · 9월 1일 ~ 9월 30일 · 50% 지남` — 이렇게 적혀 있으면 위의 `2026년 8월`과
헷갈릴 수가 없다. 조건을 지웠다.

지난 주기의 한도를 대신 계산해 보여주는 길도 있었지만 택하지 않았다.
`남음 1.8 GB · 0일 남음 · 하루 0 MB` — 끝난 주기에서는 이 카드의 낱말들이 전부 뜻을 잃는다.

#### 가장 큰 숫자가 Wi-Fi로 부풀려져 있었다

합계 카드의 큰 숫자가 `2.57 GB`(전체)였다. 그런데 바로 아래 목록의 큰 숫자는 모바일이다.
**한 화면에서 위아래로 눈을 옮기는 순간 기준이 바뀐다.** 게다가 이 기기는
Wi-Fi가 2.55 GB, 모바일이 13.59 MB라 전체는 사실상 Wi-Fi 값이다.

큰 자리를 모바일에 주고(24sp) 전체는 오른쪽에 Wi-Fi와 같은 크기로 붙였다.
색 점은 붙이지 않았다 — 점은 막대의 어느 칸인지 알리는 표시인데 합계에는 해당하는 칸이 없다.

큰 숫자는 스크린 리더에서 뺐다. 같은 값이 아래 범례 줄에 이름과 함께 적혀 있어
두 번 듣게 된다. `SegmentedUsageBar`가 이미 같은 이유로 쓰던 규칙이다.

#### 배운 것

**조건문에 근거를 안 적으면 나중에 그 조건을 지울지 말지 판단할 수 없다.**
이번엔 되짚을 수 있었지만, 그 되짚기가 맞는지 확신할 방법이 없었다.
`if` 하나에도 "왜 이 경우를 뺐는가"를 적어야 한다.

### 스와이프로 기간 옮기기 — 내 시험 순서가 나를 속였다 (2026-09-15)

#### Gemini가 짚은 둘을 받고 셋을 흘렸다

가로 스와이프를 세로 목록 위에 얹는 설계를 검토받았다.

| 지적 | 판단 |
|---|---|
| 거리만 보면 **툭 튕기는 동작**이 무시된다 | **받음** — 속도(fling) 조건을 더했다 |
| 드래그 취소 시 누적값을 리셋해야 한다 | **받음** — `onDragStopped`에서 항상 0으로 |
| 드래그 중 화면이 안 움직이는 건 나쁜 UX다 | 안 받음 — 실제로 페이지가 넘어가지 않는데 따라 움직이면 더 이상하다 |
| 경계에서 진동·튕김 피드백을 줘야 한다 | 안 받음 — 그 방향 화살표가 이미 흐려져 있다 |
| **기간이 바뀌면 스크롤 위치가 남는다 (가장 위험)** | 실측으로 확인 → 문제 없었다 |

마지막 것은 실기기에서 직접 봤다. 기간이 바뀌는 동안 목록이 잠깐 '불러오는 중' 칸으로
줄었다가 다시 채워지면서 **스크롤이 저절로 위로 잘린다.** 맞추려고 한 게 아니라
`isLoading` 처리가 부수적으로 해결하고 있었다.

#### 있지도 않은 버그를 한 시간 쫓을 뻔했다

첫 실기기 확인에서 이런 걸 봤다.

```
가로 스와이프 → 9월 14일   (맞음)
세로 스와이프 → 9월 9일    (???)
```

순수 세로 스와이프인데 날짜가 5칸 밀렸다. `draggable`이 매 리컴포지션마다 새로 만들어지면서
진행 중인 제스처가 끊기고 그게 여러 번 '손을 뗀 것'으로 세어지는 것 아닌가 — 그럴듯한
가설까지 세웠다.

**격리해서 재현이 안 됐다.**

| 시험 | 결과 |
|---|---|
| 세로 스와이프만 1회 | 날짜 그대로 |
| 가로 스와이프만 1회 | 정확히 1칸 |
| 가로 → 세로 (원래 순서) | 14일 → 14일 |
| 가로 스와이프 6회 | 15일 → 9일, 정확히 6칸 |

마지막 줄이 답이었다. **15일에서 9일은 스와이프 6번 거리다.** 내가 앞선 확인에서 실행한
스와이프 횟수를 잘못 세고 있었던 것이지, 앱이 틀린 게 아니었다.

가설이 그럴듯했기 때문에 위험했다. 코드를 고치고 "고쳤다"고 말할 뻔했다.
**재현되지 않는 버그는 고치지 않는다** — 격리 시험이 그 규칙을 지켜 줬다.

#### 배운 것

**측정 도구가 틀릴 수 있다는 것을 제일 먼저 의심해야 한다.** 이번엔 측정 도구가
`adb shell input swipe`를 몇 번 보냈는지 세는 나 자신이었다.

### 머리말을 고정했다 — 예전 결정을 뒤집으며 (2026-09-15)

"위아래 스와이프는 상단/중단의 정보는 계속 표시하고 앱목록만 위아래로 스크롤 되도록 하자."

**이건 예전에 내가 반대로 정해 둔 것이었다.** `design.md`에 이렇게 적혀 있었다.

> 머리말을 `LazyColumn`의 칸으로 넣어 함께 올라가게 하면 한 번 내릴 때 그 자리를 목록이
> 넘겨받는다. 보여주는 정보를 하나도 버리지 않고 목록만 넓히는 방법이다.

그 논리는 지금도 맞다. 머리말이 2340px 중 1100px을 차지하므로, 고정하면 자세히 보기에서
**다섯 줄 남짓**만 보인다. 그래서 바꾸기 전에 대가를 분명히 적어 두었다.

다만 사용자의 근거가 더 강하다고 봤다. 한도·기간·합계는 목록을 읽는 **동안** 견주는 값이다.
"어떤 앱이 많이 썼나" 보려고 내린 순간 "무엇에 견주는 중이었나"가 사라지면
스크롤을 올렸다 내렸다 하게 된다.

그리고 **지금은 대가를 치를 수단이 생겼다.** 며칠 전 넣은 '간단히 보기'가 한 줄을 절반으로
줄인다. 예전이었다면 다섯 줄이 전부였겠지만 지금은 고를 수 있다.
결정을 뒤집을 수 있게 된 것은 그 사이에 선택지가 늘었기 때문이다.

#### 스와이프가 먹지 않는 띠를 찾았다

머리말을 고정하고 가로 스와이프를 위치별로 재 봤다.

| y (기기 px) | 무엇 | 결과 |
|---|---|---|
| 400 | 한도 카드 | 됨 |
| 700 / 760 | **기간 칩** | **안 됨** |
| 950 / 1100 | 합계 카드 | 됨 |
| 1200 | **정렬 칩** | **안 됨** |
| 1500 | 목록 | 됨 |

칩 두 줄이 `horizontalScroll`을 쓰기 때문이다. 칩이 화면에 다 들어오는 기기에서는
밀 것이 없어 아무 일도 일어나지 않는다.

**고치지 않았다.** 두 줄을 합쳐 화면의 7% 남짓이고, 칩이 넘치는 기기에서는 칩을 미는 것이
맞는 동작이다. `horizontalScroll`을 떼면 그 기기에서 칩이 잘린다.

#### 배운 것

**자기가 적어 둔 결정을 뒤집을 때는 그 근거가 아직 유효한지부터 본다.** 이번엔 유효했다 —
목록이 짧아지는 대가는 실제로 발생한다. 근거가 틀려서 바꾼 게 아니라
**더 중요한 것이 생겨서** 바꾼 것이고, 그 차이를 문서에 적어야 다음 사람이 또 뒤집지 않는다.

# 주기 이력 화면과 마지막 확인 시각 (2026-10-02)

## 후보를 어떻게 골랐나

"추가로 넣으면 좋은 기능"을 찾으면서 **먼저 기각 기록부터 훑었다.**
VPN 실시간 감시, 5분 주기, 위젯 색 맞추기, Preferences 제네릭 래퍼, domain/model 병합은
전부 수치 근거와 함께 이미 거부돼 있어 후보에서 뺐다.

남은 셋을 제안했다.

| 후보 | 근거 |
|---|---|
| 백업·복원 | 유일한 자산이 복구 불가. 문서가 "먼저 만들어야 할 이유가 늘었다"고 적은 **유일한 적극적 미구현** |
| 주기 이력 | 한도를 정할 근거가 화면에 없다 |
| 마지막 확인 시각 | `recordedAtEpochMillis`가 쌓이기만 하고 안 읽힌다 |

사용자가 뒤의 둘을 골랐다. **백업·복원은 하지 않았다** — 누적 DB는 여전히 복구 불가다.

## 자를 정하는 규칙이 또 갈렸다

앱 목록의 자(`AppListScale`)는 "기준이 자를 넘으면 눈금을 지운다". 주기 이력은 반대로
**한도를 자에 집어넣는다**(`maxOf(peak, limit)`). 한도가 넉넉하면 자에서 빠져
기준선 자리가 사라지는데, 그러면 정작 알고 싶은 '얼마나 여유인가'가 없어지기 때문이다.

규칙이 다르므로 `AppListScale`을 재사용하지 않았다. 같은 이름을 쓰면 다음에 한쪽을
고치다 다른 쪽이 조용히 깨진다.

## 과거 주기에 현재 한도로 비율을 적지 않기로 한 이유

한도 이력을 저장하지 않으므로 **지난 주기의 한도를 알 방법이 없다.**
`5.24 / 6.0 GB · 87%`는 "그 주기에 한도가 6 GB였다"는 주장이고 근거가 없다.
더 나쁜 것은 **한도를 바꾸면 과거 숫자가 바뀐다**는 점이다.

검토한 대안:

- **한도 이력을 새로 저장** — 과거는 영원히 공백이라 '아는 줄'과 '모르는 줄'이 섞여 분기가
  **늘고**, **주기 중간에 한도를 바꾸면 한 주기에 한도가 둘**이어서 근본 해결도 아니다.
  지금 안이 이 길을 막지는 않는다(선 하나 → 주기별 선으로 가는 증분 변경).
- **각주를 달고 비율은 적는다** — 각주는 안 읽히고 숫자는 읽힌다.
- **한도를 아예 안 보여준다** — 비교 기준이 사라져 목적을 반쯤 버린다.

채택한 방식의 핵심은 **모델에 비율을 만들 수단을 두지 않은 것**이다.
`BillingCycleHistory`에는 한도로 나누는 연산이 없다. 주석이 아니라 타입이 막는다.

**추천 한도값을 계산해 주지 않는다**(`평균 × 1.2` 같은 것). 검증할 수 없는 조언이고,
"가장 많이 쓴 주기 8.95 GB"가 이미 결정에 필요한 전부다.

## 실기기가 문구 하나를 잡아냈다

처음 적은 문구는 "주기 전체가 기록된 것만 **최대 %d개까지** 보여줍니다"였고
`history.finished.size`를 넣었다. 실기기에서 "최대 **3개**까지"로 떴다.

**3은 상한이 아니라 마침 있는 개수였다.** 상한은 12이고, 6월이 빠진 진짜 이유는
기록이 6월 6일부터라 그 주기가 반쪽이기 때문이다. 문구는 "앱이 3개로 제한한다"로 읽힌다.

빠진 이유가 둘인데 목록 길이를 적으면 그 길이가 상한처럼 읽힌다. **숫자를 뺐다.**

> 경고를 읽는 것과 화면을 보는 것은 다르다 — 또 한 번.

## 확인 시각: 설계를 두 번 뒤집은 기록

이 작업에서 **가장 값진 것은 결론이 아니라 두 번 뒤집힌 경로**다.

1차 안은 `MAX(recordedAtEpochMillis)` 전역. 동기는 "컬럼이 이미 있으니 가장 싸다"였다.
→ `RECENT_BACKFILL_DAYS = 7`이라 7일보다 오래된 행은 다시 쓰이지 않는다.
   9월을 보면 화면 숫자는 3주 전 것인데 전역 MAX는 오늘을 가리킨다. **거짓.**

2차 안은 쿼리를 보고 있는 기간으로 한정. 문장이 참이 되고 `usageDate` 인덱스도 탄다.
→ Gemini 독립 검토가 두 구멍을 더 지적했고, 코드로 확인하니 맞았다.

3차 안은 **질문을 바꾼 것**이다.

> **"이 집계는 몇 시 것인가"라는 질문 자체에 답이 없다.**
> `upsertAll`이 날짜마다 호출되고 실패한 날짜는 건너뛰므로, 한 달치 합계 안에는
> 서로 다른 시각에 쓰인 기록이 섞인다. `MAX`는 과장하고 `MIN`은 늘 기간 끝을 가리킨다.

그래서 **데이터의 나이** 대신 **앱이 마지막으로 확인한 시각**을 적는다.
"3시간 전에 확인함"은 실제로 일어난 사건이라 언제나 참이다.

대가를 분명히 적어 둔다 — **이 기능의 원래 동기였던 컬럼을 결국 쓰지 않는다.**
`recordedAtEpochMillis`는 여전히 미사용이고, DataStore가 6개로 늘었다.
싼 것이 옳은 것을 이기지 않는다.

## Gemini 검토: 받은 것과 받지 않은 것

| 지적 | 판정 |
|---|---|
| 부분 실패로 나이가 섞인다 | **받음.** 다만 단위가 다르다 — 앱 단위가 아니라 **날짜 단위**다 |
| "안 썼다"와 "확인 못 했다"를 구별 못 한다 | **받음** |
| 백필이 과거 행 시각을 인위적으로 전진시킨다 | **안 받음.** 5일 전 행이 오늘 다시 쓰였다면 그 숫자는 실제로 오늘 조회한 값이다. 정확하고 오히려 유용하다 |
| 과거 기간에선 라벨을 숨겨라 | **받음** |
| '시도'와 '성공'을 나눠 저장하라 | **절반 받음.** 별도 테이블은 과하고 DataStore로 충분. 다만 이 지적이 **내 기각 근거를 무너뜨렸다** |
| 1분 틱 대신 동적 지연 | **받음.** 근거("리컴포지션 낭비")는 과장이지만 결론은 낫다 |

내가 "DataStore 안은 권한 미허용에도 전진해서 위험하다"고 기각한 것이 **틀렸다.**
`UsageSyncResult`가 `Success`/`PermissionRequired`/`Failure`로 갈리므로 성공에만 쓰면 된다.

### Gemini가 놓친 것

`Success`는 **모든 날짜가 건너뛰어진 경우에도 반환된다**(`syncedDayCount = 0`).
조건을 `Success`만으로 두면 단 하루도 읽지 못한 동기화가 "방금 확인함"을 적는다.
`syncedDayCount > 0`이 반드시 필요하다. 테스트로 고정했다.

## 테스트가 실제로 잡는지 확인했다

`fullyRecordedCyclesBefore`의 "기록이 주기 전체를 덮는가" 조건을 **일부러 지우고** 돌렸다.
3건이 실패했다. 조건을 되돌렸다.

이 규칙은 틀려도 화면이 멀쩡히 그려지고 반쪽 주기가 섞여 들어갈 뿐이라,
눈으로는 확인되지 않는 종류의 오류다. 뒤집어 보지 않으면 테스트가 지키는지 알 수 없다.

## 남은 것

- **백업·복원** — 제안했으나 선택되지 않았다. 누적 DB는 여전히 복구 불가다
- **`recordedAtEpochMillis`** — 계속 미사용. 3차 안이 쓰지 않는다
- **위젯에는 확인 시각이 없다** — 위젯 숫자도 DB 기반이라 같은 질문이 남는다
- **'마지막 시도' 시각** — 기각이 아니라 **보류**. 되살릴 조건: 실기기에서
  "시도는 도는데 성공이 안 되는" 사례가 관측되면
- **DataStore가 6개** — 재검토 조건("설정 10개 초과")에 한 칸 가까워졌다

# 후보를 넓게 본 조사와 그 결과 (2026-10-02)

## 조사 방법

"재료는 이미 있는데 쓰지 않는 것"을 두 갈래로 전수 조사했다 —
데이터 유입부터 화면까지의 소비 경로, 그리고 알림·워커·위젯·설정의 공백.
여기에 **백업해 둔 실기기 DB로 수치를 댔다**(`backup/20261002_103958/`,
15,738행 / 2026-06-06~10-02 / **119일 연속, 빠진 날 0** / 앱 233개).

추측으로 고르지 않고 **데이터가 고르게 한 것**이 이번 조사의 요점이다.

## 실측이 만든 결정 네 가지

### 1. 목록의 32%가 잡음이었다

최근 30일 192개 앱 중 **61개가 모바일 0**. 모바일순으로 보면 아래 3분의 1이 `0 B`다.
"목록이 길다"는 체감의 정체가 이것이었다.

### 2. 페이스 알림은 1일째에 울린다

`pace()`의 `FASTER`를 알림 조건으로 쓰려 했다가 실측에서 무너졌다.

| 주기 | `FASTER` 최초 | 80% 알림 | 실제 |
|---|---|---|---|
| 6월 | **1일째** | 15일째 | 9.42 GB 초과 |
| 7월 | 30일째 | 26일째 | 6.56 GB 초과 |
| 8월 | **1일째** | 11일째 | 8.95 GB 초과 |
| 9월 | **1일째** | 24일째 | 5.55 GB |

주기 초에는 분모가 작아 하루만 평소대로 써도 '빠름'이 된다. **거짓 경보 기계다.**

조건을 "7일 이상 지났고 지금 속도면 한도 초과"로 바꿔 보니 6월 12일 / 7월 9일 / 8월 7일에
적중했으나 **9월 7일째에 8.7 GB를 예상하고 실제는 5.55 GB였다 — 네 번 중 한 번 오보.**

> **알림은 틀리면 대가가 크고, 화면에 숫자로 적으면 대가가 없다.**
> 그래서 알림으로 만들지 않고 한도 카드에 적었다. 조건을 사람이 보고 판단하게 둔다.

### 3. 네 주기 중 세 주기가 한도를 넘겼다

6월 9.42 / 7월 6.56 / 8월 8.95 / 9월 5.55 GB, 한도 6 GB.
80% 하나로는 늦다는 근거가 됐다(8월은 11일째에야 80%에 닿았는데 최종은 한도의 1.5배).

### 4. 보관 상한은 둘 이유가 없다

하루 132행, 행당 160 B → **연 7.7 MB, 10년 77 MB.**
`doc/idea.md`의 열린 질문을 "하지 않기로" 닫는다. 조건이 바뀌면(예: 시간대별을 저장하기 시작)
다시 본다.

## 데이터가 반대한 후보들

조사에서 "재료가 있다"고 나왔지만 **실측이 가치를 부정한 것들**이다.
근거를 남겨 두지 않으면 같은 제안이 또 올라온다.

| 후보 | 반대 근거 |
|---|---|
| **수신/송신 추이** | `observeDailyTotals`가 4열을 읽어 오는데 `DailyTrendChart`가 버리는 것은 사실이다. 그러나 송신 비중 상위를 뽑아 보니 **최고가 56%이고 그마저 시스템 앱**(`com.sec.android.app.wlantest`)이다. 뚜렷한 업로드형 앱이 없어 "어느 날 업로드가 터졌나"라는 질문 자체가 이 기기에서 성립하지 않는다 |
| **동기화 실패 배너** | `WorkInfo`를 관찰하는 코드가 **0건**인 것은 사실이다. 그러나 **119일 연속 빠진 날이 0**이다. 일어나지 않는 문제에 UI를 붙이면 영영 안 보이는 코드가 된다. 되살릴 조건은 그대로 둔다 |
| **보관 상한·prune** | 위 4번 |
| **시간대별 영구 저장** | 근사치를 영구 보존하면 "시스템 설정 화면과 대조 가능"이라는 신뢰성 근거를 잃는다 |
| **로밍·종량 Wi-Fi(`metered`)** | 핵심 질문("요금이 붙는가")에 Wi-Fi 쪽에서도 답할 수 있어 **후보로는 가장 매력적이었다.** 그러나 스키마 변경 + 마이그레이션이 들고, 이 사용자가 로밍·테더링을 쓰는지 확인되지 않았다. **되살릴 조건: 해외 사용이나 테더링 핫스팟 사용이 생기면** |

## 바로잡은 것

`SettingsScreen.kt`가 **487줄이라고 알고 있었으나 실제 491줄**이고,
487은 문서에 적힌 적이 **없다.** `doc/design.md`의 패키지 줄 수 표에 있던
`data/system | 6 | 487`을 내가 잘못 옮겨 적어 여러 차례 되풀이했다.
(그 표 자체도 `ui/settings 1122줄`로 적혀 있으나 실측은 1098줄이라 낡았다.)

출처를 확인하지 않은 숫자를 반복해 인용하면 그것이 사실이 된다.

## 함정 — 같은 것이 세 번째다

`UsageSortOrder.sortKeyOf`는 `MOBILE_BACKGROUND`에서 포그라운드 구분이 없는 앱에 **0**을
돌려준다. 이 성질이 세 번째로 발목을 잡았다.

1. "큰 숫자를 정렬 기준값으로 바꾸기" 기각 — 데이터를 쓴 앱에 `0 B`가 찍힌다
2. Wi-Fi순 정렬의 어긋남을 의도적으로 남긴 근거
3. **이번**: 필터를 정렬 키로 걸면 그 앱들이 통째로 사라진다

그래서 `visibleBytesOf`를 따로 뒀고, **뮤테이션으로 확인했다** —
`visibleBytesOf = sortKeyOf(usage)`로 되돌리자 테스트 한 건이 정확히 실패했다.

## 열거형 이름이 저장 키였다

`MonthlyLimitThreshold`에 지점을 더하면서 이름을 정리하고 싶었다
(`WARNING`/`ALMOST`는 결이 다르다). **하면 안 된다** —
`MonthlyLimitPreferencesDataStore`가 '이미 알린 지점'을 **이름 문자열로 저장**하므로,
이름을 바꾸면 저장된 값이 고아가 되어 이번 주기에 이미 알린 지점을 다시 알린다.

테스트로 못 박았다(`지점의 이름과 퍼센트가 짝을 유지한다`).
**더하는 것은 안전하고 바꾸는 것만 위험하다**는 비대칭을 KDoc에 적었다.

## 남은 것

- **백업·복원** — 세 번째로 제안했으나 선택되지 않았다. 누적 DB는 여전히 복구 불가다
- **`recordedAtEpochMillis`** — 계속 미사용
- **`SettingsScreen.kt` 491줄** — 분할 기준 초과. 쪼갤 경계는 뚜렷하다(시스템 상태 안내 185줄, 하루 한도 125줄)
- **위젯**: 새로고침 액션 없음(탭 = 앱 실행 하나), 경과율 눈금 없음, `TRACK_ALPHA = 0.25` 고정
- **주 시작 요일 월요일 고정** — `UsagePeriod.of`가 이미 파라미터로 받으므로 설정 키 하나면 된다
- **청구 주기 마감 알림** — `GetBillingCycleHistoryUseCase`가 재료를 갖고 있으나 '주기가 끝났다'는 사건을 받는 코드가 없다
- **알림이 주기당 4번이 될 수 있다** — 지점이 넷으로 늘었고 이 사용자는 자주 초과한다. 많다고 느껴지면 `HALF`를 한 줄 지우는 것이 가장 쉬운 되돌림이다

## 실기기가 내가 낸 버그를 잡았다

목록 거르기를 `GetAppUsageUseCase`에 넣고 단위 테스트 264건을 모두 통과시킨 뒤
기기에 올렸다. 정렬 칩을 눌러 보다가 발견했다.

```
모바일순   전체 5.74 GB · Wi-Fi 5.49 GB
Wi-Fi순    전체 6.63 GB · Wi-Fi 6.38 GB   ← 같은 10월인데
```

합계 카드가 `appUsages`를 더해 만드는데, 내가 그 목록을 정렬별로 걸러
**합계까지 정렬에 끌려가게 만들었다.**

> **합계는 기간의 사실이고 목록은 보는 방식이다.** 둘을 같은 값에서 뽑으면 안 된다.

거르는 자리를 `UsageSummaryUiState.visibleAppUsages`로 옮겼다 — 합계보다 **뒤**에서
파생되므로 합계에 닿지 않는다. 그리고 그 사실 자체를 테스트로 고정했다
(`합계는 정렬을 바꿔도 달라지지 않는다`). 뮤테이션으로 확인했을 때 두 건이 실패한다.

**단위 테스트 264건이 이것을 못 잡았다.** 유스케이스 테스트는 "거르는가"만 물었고,
"거른 것이 다른 값에 번지는가"는 묻지 않았다. 두 값이 서로 다른 레이어에 있어
한 테스트가 둘을 함께 보지 않았기 때문이다.

실기기 확인이 형식적 절차가 아니라는 증거다. 화면에서 두 숫자를 나란히 보는 일은
테스트가 흉내 내기 어렵다.

## 기기에서 확인한 것

| 확인 | 결과 |
|---|---|
| 모바일순 목록 끝 | `9 KB / 9 KB / 8 KB / 80 B` — **`0 B` 줄이 사라졌다** |
| Wi-Fi순 | Wi-Fi만 쓴 앱이 `0 B`를 달고 되돌아온다 (의도) |
| **백그라운드순** | `모바일 백그라운드 0 B`인 앱(삼성 헬스·해리포터·TMAP·Mi Fitness)이 **남아 있다** ← 함정 |
| 합계 | 네 정렬 모두 `6.63 GB / Wi-Fi 6.38 GB`로 같다 |
| 지운 앱 | `알 수 없는 앱 (uid 2904)` 아래 **`설치되지 않음`** |
| 낭독 | `알 수 없는 앱 (uid 2904), 모바일 0 B, 설치되지 않음, 전체의 0%, Wi-Fi 568.15 MB` |
| 예상 사용량 | 10월 2일째라 7일 미만 — **안 뜨는 것이 정상** |
| 위젯 | `253.26 MB / 6 GB · 4%` 변경 없음 |

알림(작업 D)은 기기에서 재현하지 못했다. 지점을 넘기는 상황을 만들려면 실제로 데이터를
써야 한다. 단위 테스트로 대신했다 — 지점별 경계, 가장 높은 지점 선택, 이름·퍼센트 짝.

# 배포 구성 (2026-10-20)

절차는 `doc/deploy.md`에 있다. 여기에는 **왜 그렇게 골랐는지와 조사에서 드러난 사실**만 남긴다.

## 설계를 두 번 바꿨다

처음에는 **Firebase App Distribution**으로 배포하려 했다. 그 안은 **Google Cloud 접근이
어렵다**는 제약에서 무너졌다. CI가 App Distribution에 올리려면 서비스 계정 JSON이 필요하고,
그 키는 Google Cloud 콘솔에서만 만들 수 있다.

그래서 역할을 쪼갰다.

| | 맡는 일 |
|---|---|
| **GitHub** | 소스, 빌드, 서명, **APK 파일 보관과 전달**(Release) |
| **Firebase** | **"지금 최신이 무엇인가"라는 한 줄의 기록**(Realtime Database) |

이 쪼개기의 이점은 **CI가 쓰는 토큰이 GitHub가 실행마다 만들어 주는 `GITHUB_TOKEN`
하나로 줄어든다**는 것이다. 발급받아 보관할 외부 키가 없다. 시크릿은 7개에서 4개로,
그중 Google 쪽은 0개가 됐다.

치르는 대가는 **Firebase `latest` 갱신이 수동**이라는 것이다. 쓰기에 또 서비스 계정이
필요하기 때문이다. 그 대가를 줄이려고 **CI가 붙여 넣을 JSON을 만들어 Release 설명과
실행 요약에 출력**하게 했다. 손으로 적으면 `versionCode`를 잘못 쓰거나 주소에 오타가 나고,
그러면 앱이 "최신입니다"라고 거짓을 말한다.

## 고른 것과 기각한 것

| 갈림길 | 고른 것 | 근거 |
|---|---|---|
| 파일 전달 | **GitHub Release** | 서비스 계정이 필요 없다. 공개 저장소면 로그인 없이 받는다 |
| 버전 확인 | **SDK 없는 HTTPS GET** | Realtime Database는 경로 뒤에 `.json`을 붙이면 평범한 GET으로 읽힌다. SDK·`google-services.json`·플러그인 모두 0 |
| 저장소 공개 범위 | **공개** | 비공개 저장소의 Release 파일은 로그인 없이 받을 수 없다 |
| 서명 키 | **기존 debug 키 재사용** | 서명이 바뀌면 삭제 후 재설치만 가능해지고 누적 DB가 사라진다 |
| 배포 트리거 | **`v*` 태그** | 푸시마다 배포하면 Release가 쌓여 최신을 구별할 수 없다 |
| 버전 비교 기준 | **`versionCode`만** | 이름으로 비교하면 `0.10.0` < `0.9.0`으로 뒤집힌다 |
| 확인 시점 | **설정 화면이 열려 있을 때만** | 배경 주기 확인은 사용자가 보지 않는 때에 통신한다. 사용 기록 앱에서 그 성질을 바꾸는 선택이라 지금은 보이는 자리로 제한했다 |
| JSON 파서 | **`org.json`** (프레임워크 내장) | 새 런타임 의존성 0. APK 크기 변동 없음(2.5 MB 그대로) |

기각한 것: Crashlytics(SDK와 네트워크 전송이 들어온다), Firebase App Distribution(서비스 계정),
Play Store(지금 키로는 불가), 앱 내 APK 자동 설치(`REQUEST_INSTALL_PACKAGES` 권한 부담).

## INTERNET 권한을 들였다 — 이 앱 성격의 첫 변경

지금까지 이 앱은 네트워크를 전혀 쓰지 않았다. 버전 확인을 위해 처음으로 권한이 들어왔다.
그 성질을 지키려고 세 가지를 못 박았다.

* **네트워크 코드가 파일 하나다** (`HttpLatestReleaseSource`). 보내는 것은 요청 주소뿐이고
  기기나 사용량 정보는 실리지 않는다
* **배경 작업이 없다.** 설정 화면이 열려 있는 동안에만 일어난다
* **주소가 비면 기능 자체가 없다.** `gradle.properties`의 `tracephone.updateManifestUrl`이
  비어 있으면 카드를 그리지 않고 요청도 하지 않는다

권한 선언 바로 위에 이 이유를 주석으로 적었다. 나중에 "왜 INTERNET이 있지"를 물을 때
매니페스트 안에 답이 있어야 한다.

## 신뢰 경계를 코드에 그었다

버전 기록은 **공개 읽기**로 둔 저장소에서 오고, 값은 **사람이 콘솔에 손으로 적는다.**
즉 앱이 받는 것은 사실이 아니라 "누군가 적어 둔 주장"이다. 두 가지로 막았다.

1. **파싱이 틀린 입력을 조용히 메우지 않는다.** 항목이 없거나 `versionCode`가 숫자가
   아니거나 0 이하면 형식 오류로 던진다. 기본값으로 메우면 "최신입니다"라고 거짓을 말한다
2. **내려받기 주소가 `https://github.com/`으로 시작해야 열린다.** 접두사만 보면
   `https://github.com.evil.example/...`이 통과하므로 그 뒤가 끝이거나 `/`여야 한다는
   조건을 함께 둔다. **뮤테이션으로 확인했다** — 뒷조건을 `true`로 되돌리면 테스트가 실패한다

실패 이유를 `NETWORK` / `MALFORMED` / `UNTRUSTED_DOWNLOAD_URL` 셋으로 나눈 이유는
**사용자가 할 수 있는 일이 다르기 때문**이다. 첫째만 다시 눌러 볼 가치가 있다.
`Unavailable`(기능 없는 빌드)과 `Failed`(확인 실패)를 섞으면 둘이 같은 문구를 받게 된다.

## 서명이 누적 DB와 충돌한다 — 이번 작업의 핵심

안드로이드는 **서명이 다른 APK로 덮어쓰기를 거부**한다. 새 release 키를 만들면 기기의 앱을
지워야 하고, 지우면 119일 누적 기록이 사라진다. 복구 수단이 없다.

그래서 `~/.android/debug.keystore`로 release를 서명한다. 실측으로 확인했다.

* 기기의 debug 키 지문 `0A:49:F1:4E:...:46:7E`
* 빌드한 release APK 지문 `0a49f14ece7d3dbe70e9ebb5e9797f753e81467e` — **같다**
* 유효기간 2056-08-26까지 (30년) — 시한폭탄이 아니다

대가는 **Play Store 업로드 불가**. 되살릴 조건: Play Store가 필요해지면, 그 전에 앱에
DB 내보내기/가져오기 기능을 먼저 만든다.

워크플로에 `EXPECTED_SIGNER_SHA1` 검사를 넣었다. 서명이 바뀐 APK가 기기로 흘러가는 사고를
CI에서 멈추는 장치다. **시크릿이 아니라 변수(Variables)에 둔다** — 지문은 비밀이 아니고,
시크릿에 넣으면 로그가 `***`로 가려져 어긋났을 때 무엇과 달랐는지 읽을 수 없다.

## 발견 — release로 옮기면 백업 경로가 막힌다

지금까지 DB를 뽑은 `adb exec-out run-as`는 앱이 디버그 가능할 때만 동작한다.
병합된 매니페스트를 비교해 확인했다.

* debug: `android:debuggable="true"`
* release: 그 속성이 **없다**

즉 기기를 release로 바꾸면 **DB를 꺼낼 방법이 사라진다.** 내보내기 기능이 없는 현재는
되돌릴 수 없는 손실이다. 그래서 운용을 나눴다 — **내 S23+는 debug 유지**, release는
다른 기기·다른 사람용. 이것이 "백업·복원 기능"을 미뤄 온 대가다.

## 발견 — R8이 열거형 이름을 바꾸면 DB를 못 읽는다

`RoomTypeConverters.networkKindToText`가 `NetworkKind`의 **이름 문자열을
`daily_app_usage`의 열에 그대로 저장**한다. DataStore도 테마·정렬·기간·위젯 색·알림 지점을
이름으로 저장한다(6곳).

R8이 이름을 바꾸면 **저장된 값을 되읽을 수 없다.** DB 쪽은 복구 불가다.
release dex를 직접 뜯어 확인한 결과 `MOBILE_BACKGROUND`, `ALMOST`, `DETAILED` 등 고유한
이름들이 모두 남아 있었다 — 지금 R8은 바꾸지 않는다.

그래도 `proguard-rules.pro`에 명시했다. **AGP를 올릴 때 조용히 깨지는 것이 이 프로젝트에서
가장 비싼 실패이기 때문이다.** 규칙 4줄로 R8의 판단에 대한 의존을 끊는다.

## 처음 성공한 release 빌드

`:app:assembleRelease`를 **이 프로젝트에서 처음** 돌렸다(`app/build/outputs/apk/`에
`debug`와 `androidTest`만 있었다). R8 축소가 Hilt·Room·Glance·WorkManager를 깨지 않았다.

* 3분 3초, APK **2.5 MB**. 버전 확인 코드를 넣은 뒤에도 2.5 MB 그대로
* `FastAlertCheckPlanKt`는 R8이 완전히 제거했다(`R8$$REMOVED$$CLASS$$657`) — 전부 인라인됐다
* Worker 클래스 이름은 유지됐다. WorkManager가 자체 DB에 클래스 이름을 저장하므로 이름이
  바뀌면 이미 등록된 주기 작업이 조용히 멈춘다 — androidx.work의 consumer 규칙이 막아준다

**다만 R8은 빌드가 아니라 런타임에 깨진다.** 빌드 성공은 동작을 보장하지 않는다.
기기에서 Hilt 주입·Room 조회·주기 동기화·위젯을 눈으로 확인해야 한다. 아직 못 했다.

## 저장소를 공개로 두는 대가

`backup/`에 실기기 DB **4.8 MB**가 들어 있다. 개인 데이터다. `keystore.properties`도
새로 생겼다. 둘 다 `.gitignore`에 넣고, 프로젝트를 건드리지 않는 임시 저장소로
`git check-ignore`를 돌려 실제로 제외되는지 확인했다. 올라갈 파일은 226개다.

공개 저장소에서는 **Actions 로그도 공개**된다. 시크릿은 `***`로 가려지지만 그 밖의 출력은
그대로 보인다. 그리고 **키스토어가 새면 누구나 이 앱의 '업데이트'를 만들 수 있다.**
서명이 같은 APK는 기기가 정상 업데이트로 받아들이기 때문이다.

## 계측 테스트를 CI에도 넣지 않는다

`build.yml`에 그 이유를 주석으로 적었다. 나중에 누군가(나 포함) "CI에 계측 테스트를
추가하자"고 할 때 근거가 파일 안에 있어야 한다.

## Gemini 검토를 받지 못했다

세 번 호출해 세 번 모두 503(과부하)이었다. 그래서 Gemini에게 물으려던 질문을 직접
따졌고 **고칠 것 세 가지**를 찾았다.

1. **주소 검사가 대소문자를 구분했다.** URL의 스킴과 호스트는 대소문자를 구분하지 않는다.
   콘솔에 `Https://GitHub.com/...`으로 적으면 앱이 "신뢰할 수 없다"고 거부해, 적은 사람이
   자기가 뭘 틀렸는지 찾을 수 없다. 소문자로 바꿔 비교한다(여는 주소는 원본).
   덤으로 `https://github.com@evil.example/...`(userinfo로 호스트를 가린 주소)도
   테스트로 고정했다 — 뒷조건이 이미 막고 있었지만 적어 두지 않았다
2. **응답 상한을 디코딩 뒤에 재고 있었다.** 문자열로 바꾼 뒤 다시 인코딩해 길이를 재면,
   잘린 UTF-8 꼬리가 치환 문자로 바뀌며 원본과 길이가 달라진다. 디코딩 **전** 바이트 수로
   재도록 바꾸고 읽기 루프를 함수로 뽑았다
3. **`versionCode` 미증가를 아무도 못 잡고 있었다.** 태그-`versionName` 검사는 이걸
   통과시킨다. 직전 태그의 `build.gradle.kts`를 `git show`로 읽어 비교하는 검사를 넣었다
   (`checkout`에 `fetch-depth: 0`이 필요하다)

리다이렉트는 따져 본 결과 손댈 것이 없었다. `HttpURLConnection`은 HTTPS→HTTP 리다이렉트를
따라가지 않고 3xx를 그대로 돌려주므로, 응답 코드 검사에서 `IOException`이 되어 막힌다.
gzip은 `Accept-Encoding`을 직접 설정하지 않으면 투명하게 풀리고, 그 결과물에 8 KB 상한이
걸리므로 압축 폭탄도 막힌다.

## 워크플로 검증 방법 — 눈으로 읽지 않는다

YAML 블록 안의 셸 스크립트는 들여쓰기와 줄 연결이 쉽게 깨진다. 실제로 이번에
**줄 연결 백슬래시 두 개가 전달 과정에서 사라져** 명령이 한 줄로 붙어 버렸다.

그래서 YAML을 파싱해 각 `run` 값을 꺼내고, `${{ }}`를 자리표시자로 바꾼 뒤
**`bash -n`에 통과시키는** 검사를 돌렸다. 15개 전부 통과. heredoc 종결자가 YAML 들여쓰기
제거 뒤 열 0에 오는지도 같은 방법으로 확인했다. 눈으로 읽어서는 둘 다 못 잡는다.

## 테스트를 위해 들인 유일한 의존성

`org.json`은 안드로이드 프레임워크에 들어 있지만 **JVM 단위 테스트에서는 빈 껍데기**라
호출하면 예외가 난다. 파싱이 틀린 입력을 어떻게 다루는지가 이번 작업에서 테스트할 가치가
가장 큰 부분이었으므로 `testImplementation`으로만 실제 구현을 넣었다.
런타임 의존성은 늘지 않았고 APK 크기도 그대로다.
