# TracePhone 설계 문서

확정된 설계를 정리한 문서. 의사결정의 배경과 과정은 `doc/idea.md`를 참고한다.

- **플랫폼**: Android 8.0 (API 26) 이상
- **언어/UI**: Kotlin + Jetpack Compose (Material 3)
- **최종 수정**: 2026-09-11

### 빌드 환경

주요 라이브러리: Compose BOM 2026.08.00, Hilt 2.60.1, androidx.hilt 1.4.0,

코루틴은 `kotlinx-coroutines-bom` 1.11.0을 앱과 테스트 양쪽에 적용한다.
AGP가 androidTest 클래스패스를 앱 APK에 맞춰 `strictly`로 고정하기 때문에,
앱 쪽 버전을 올려두지 않으면 `coroutines-test`만 신버전이 되어 계측 테스트가
`NoSuchMethodError`로 전부 실패한다.

같은 이유로 `kotlinx-serialization-bom` 1.8.1도 앱과 계측 테스트 양쪽에 적용한다.
`room-testing`이 스키마 JSON을 읽을 때 kotlinx-serialization을 쓰는데,
앱 쪽이 낮은 버전으로 고정되면 마이그레이션 테스트가 `AbstractMethodError`로 실패한다.

> 계측 테스트에서 낯선 `NoSuchMethodError` · `AbstractMethodError`가 나면
> 대체로 이 고정 때문이다. `:app:dependencies --configuration debugAndroidTestRuntimeClasspath`로
> `{strictly ...}` 표시를 확인하고, 해당 라이브러리의 BOM을 앱 쪽에도 적용한다.

## 1. 시스템 개요

TracePhone은 Android 시스템의 네트워크 통계를 주기적으로 스냅샷 떠서 자체 데이터베이스에 누적하고,
앱별·기간별 데이터 사용량을 모바일/Wi-Fi로 구분해 보여주는 앱이다.

```
[시스템 NetworkStatsManager]
        |
        |  DailyUsageSyncWorker (6시간 주기 + 앱 진입 시 1회)
        v
  NetworkStatsDataSource  -- 최근 N일을 하루 단위로 조회
        |
        |  upsert (덮어쓰기)
        v
  Room: daily_app_usage
        |
        |  Flow
        v
  UsageRepositoryImpl  -- 기간 합산 + AppIdentityResolver로 앱 이름 부여
        |
        |  Flow<List<AppUsage>>
        v
  UseCase -> ViewModel -> Compose UI
```

### 단일 소스 원칙

**UI는 오직 Room만 읽는다.** 시스템 API를 직접 호출하지 않는다.

당일 최신값은 "화면 진입 시 즉시 동기화 → DB 갱신 → Flow가 UI에 자동 반영"으로 확보한다.
DB와 시스템 두 소스를 실시간 합성하는 분기를 없애기 위한 선택이며, 가독성을 성능보다 우선한다는 원칙에 따른다.

### 사용량 창구를 셋으로 나눈 이유 (2026-09-11)

한때 `UsageRepository` 하나에 12개 메서드가 있었고 구현은 403줄이었다.
읽기·쓰기·시스템 조회가 한 타입에 섞여 있어 **이 함수를 불러도 안전한지**를 매번 확인해야 했다.

| 인터페이스 | 만지는 것 | 메서드 |
|---|---|---|
| `UsageRepository` | Room만 | 8 |
| `SystemUsageReader` | NetworkStats · PackageManager만 | 3 |
| `UsageSynchronizer` | 둘 다 (**유일한 쓰기**) | 1 |

이제 **타입만 보고 어디서 온 값인지 알 수 있다.** 저장소는 마지막 동기화 시점까지만 알고,
시스템은 지금 값을 주지만 과거는 모른다.

구현 클래스도 함께 쪼갰다. 인터페이스만 나누고 구현을 한 덩어리로 두면
파일은 그대로 403줄이고 **호출부의 시야만 좁아질 뿐** 아무것도 읽기 쉬워지지 않는다.

`readMobileUsageForPeriod`는 저장소에서 빼내 `GetMobileUsageForPeriodUseCase`로 올렸다.
"과거는 저장소, 오늘은 시스템"은 저장 방식이 아니라 **업무 규칙**이고,
한도 화면과 위젯이 똑같이 쓴다. 올라온 덕분에 규칙을 단위 테스트로 고정할 수 있게 됐다.

### 화면 파일을 나누는 기준 (2026-09-11)

한 파일이 커지면 화면 하나를 고치려고 스크롤로 조각을 찾아다니게 된다.
**컴포저블이 열 개를 넘거나 400줄을 넘으면 나눈다.** 판단 기준은 하나다 —
**파일명이 안에 든 것을 설명하는가.**

| 원래 | 나눈 결과 |
|---|---|
| `ui/summary/UsageSummaryScreen.kt` 666줄 | `UsageSummaryScreen.kt` 184 (스캐폴드·목록 조립) · `AppUsageRow.kt` 302 · `SummarySelectors.kt` 89 · `UsageTotalsCard.kt` 80 · `PeriodTopBar.kt` 74 |
| `ui/component/UsageBarChart.kt` 526줄 | `UsageBarChart.kt` 263 (재기·순서 정하기) · `UsageBarChartDrawing.kt` 203 (`DrawScope` 확장) · `UsageBarChartModel.kt` 90 (공개 타입, **Compose 없이 읽힌다**) |

나눌 때 걸리는 것이 하나 있다. 코틀린의 최상위 `private`는 **파일 스코프**라
옮기는 함수는 `internal`로 올려야 컴파일된다. 뒤집어 말하면 **승격한 것만이 파일 사이의 계약**이다.
옮기고 나서 `internal` 목록이 길면 아직 덜 나뉜 것이다.

## 3. 도메인 모델

```kotlin
enum class NetworkKind { MOBILE, WIFI }

data class UsageBytes(
    val receivedBytes: Long,
    val transmittedBytes: Long
) {
    val totalBytes: Long get() = receivedBytes + transmittedBytes
    operator fun plus(other: UsageBytes): UsageBytes
    companion object { val ZERO = UsageBytes(0, 0) }
}

data class AppIdentity(
    val uid: Int,
    val packageName: String?,   // 매핑 실패 시 null
    val label: String           // 항상 표시 가능한 값
)

data class AppUsage(
    val app: AppIdentity,
    val mobile: UsageBytes,
    val wifi: UsageBytes
) {
    val totalBytes: Long get() = mobile.totalBytes + wifi.totalBytes
}

data class DailyUsagePoint(
    val date: LocalDate,
    val mobile: UsageBytes,
    val wifi: UsageBytes
)

enum class PeriodUnit { DAY, WEEK, MONTH, ALL }

/**
 * 보고 있는 기간을 '단위 + 지금으로부터 몇 칸 전인지'로 표현한다.
 * 날짜를 직접 들고 있지 않으므로 자정을 넘겨도 선택이 자동으로 따라온다.
 */
data class PeriodSelection(
    val unit: PeriodUnit,
    val offset: Int = 0    // 0 = 현재, -1 = 직전. 미래가 없어 양수가 되지 않는다.
)

data class UsagePeriod(
    val startDate: LocalDate,
    val endDateInclusive: LocalDate
)

// PeriodSelection -> 실제 날짜 범위
UsagePeriod.of(selection, today, firstDayOfWeek)

sealed interface UsageSyncResult {
    data class Success(val syncedDayCount: Int, val recordCount: Int) : UsageSyncResult
    data object PermissionRequired : UsageSyncResult
    data class Failure(val cause: Throwable) : UsageSyncResult
}
```

### 왜 복합 기본키 + REPLACE 인가

시스템이 반환하는 값은 **해당 날짜의 누적치**이지 마지막 조회 이후의 증분이 아니다.
같은 날을 여러 번 스냅샷 떠도 항상 최신 값으로 **덮어써야** 한다.

증분처럼 더하면 동기화 횟수만큼 수치가 부풀려진다.
`(usageDate, uid, networkKind)`를 기본키로 두고 `OnConflictStrategy.REPLACE`를 쓰면
구조적으로 이 실수가 불가능해진다.

> 이 프로젝트에서 가장 실수하기 쉬운 지점이다. 검증 항목 5번(같은 날 3회 동기화)이 이것을 잡는다.

### 왜 포그라운드 구분을 기본키가 아니라 열로 넣는가 (DB v2)

`(usageDate, uid, networkKind, state)`로 기본키를 늘리는 방법도 있었다. 두 가지 이유로 쓰지 않았다.

**첫째, 같은 날이 두 번 세어진다.** 마이그레이션에서 기존 행은 `state='UNKNOWN'`이 된다.
그 날짜를 다시 동기화하면 `FOREGROUND`/`BACKGROUND` 행이 새로 생기고 `UNKNOWN` 행은 그대로 남는다.
위의 덮어쓰기 규칙이 상태별로 갈라지면서 더 이상 중복을 막지 못한다.

**둘째, 이를 막으려면 아카이브를 위험에 빠뜨려야 한다.** 중복을 없애려면 '날짜별 삭제 후 삽입'으로
바꿔야 하는데, 시스템 보관 기간이 지난 과거 날짜를 동기화하면 조회 결과가 비어 있어
그 날의 기록을 통째로 지우게 된다. 그 기록은 다시 만들 수 없다.

기본키를 그대로 두고 열만 더하면 두 문제가 모두 사라진다.
마이그레이션도 `ALTER TABLE ADD COLUMN` 두 번이라 테이블을 다시 만들지 않는다.

**기본값을 주지 않는 것이 핵심이다.** 0으로 채우면 지난 기록이 전부 백그라운드 사용이었던 것처럼
보인다. 그것은 사실이 아니라 **모르는 것**이고, null이 그 사실을 그대로 말한다.

백그라운드는 저장하지 않고 `총합 − 포그라운드`로 계산한다.
실기기에서 두 상태의 합이 총합과 바이트까지 일치함을 확인했다.

### 마이그레이션 규칙

`TracePhoneMigrations.ALL`에 순서대로 등록한다. 파괴적 마이그레이션은 쓰지 않는다.
버전마다 `TracePhoneMigrationTest`로 **기존 행이 그대로 남는지**와
**예전 행의 새 열이 null인지**를 검증한다.

## 5. 수집 전략

모든 수치는 `core/Constants.kt`에 상수로 둔다. 매직넘버를 코드에 직접 쓰지 않는다.

| 상수 | 값 | 의미 |
|---|---|---|
| `SYNC_INTERVAL_HOURS` | 6 | 주기 동기화 간격 |
| `RECENT_BACKFILL_DAYS` | 7 | 매 동기화마다 다시 훑는 최근 일수 |
| `INITIAL_BACKFILL_DAYS` | 90 | 최초 실행 시 긁어올 최대 과거 일수 |

### 세 가지 수집 시점

1. **주기 동기화** — `PeriodicWorkRequest`, 6시간 간격.
   매 실행마다 오늘 포함 최근 7일을 다시 조회해 덮어쓴다.
   기기가 며칠 꺼져 있었거나 Worker가 지연돼도 구멍이 자동으로 메워진다.

2. **최초 백필** — 권한 획득 직후 `OneTimeWorkRequest`로 최대 90일치를 수집.
   시스템에 기록이 없는 날짜는 0이 반환되므로 별도 처리가 필요 없다.

3. **화면 진입 시** — expedited `OneTimeWorkRequest` 1회.
   당일 진행 중인 사용량을 최신 상태로 반영한다.

### 작업 제약을 걸지 않는 이유

이 작업은 네트워크를 사용하지 않고 로컬 시스템 통계만 조회한다.
배터리나 네트워크 제약을 걸면 실행이 미뤄지기만 할 뿐 얻는 이득이 없다.

### `NetworkStatsDataSource` 구현 주의점

- `querySummary(networkType, subscriberId, startMillis, endMillis)`를 **하루 단위로 반복 호출**한다.
  긴 범위를 한 번에 조회하면 일자별로 쪼갤 수 없다.
- `subscriberId`는 **항상 `null`**을 전달한다.
  Android 10(API 29)부터 앱은 `getSubscriberId()`를 얻을 수 없고, `null`이면 모든 가입자 합산이 반환된다.
- `ConnectivityManager.TYPE_MOBILE`과 `TYPE_WIFI`를 각각 조회해 `NetworkKind`로 매핑한다.
- `NetworkStats`는 반드시 닫는다 (`use { }`).
- `SecurityException`은 권한 미허용 신호다. 크래시가 아니라 `PermissionRequired`로 변환한다.

## 6. 화면

### 화면 모드는 설정에서 고른다

`시스템 설정 따름 / 밝게 / 어둡게`. 기본은 시스템을 따른다.

기기 전체 설정과 따로 둘 수 있게 한다. 이 앱은 숫자와 색으로 읽는 화면이라
보기 편한 밝기가 기기 전체의 선택과 다를 수 있다.

`TracePhoneTheme`이 이미 `useDarkTheme` 매개변수를 받고 있어 **테마 코드는 손대지 않았다.**
`MainActivity`가 저장된 값을 읽어 `ThemeMode.resolvesToDark(isSystemInDarkTheme())`을 넘긴다.

#### 저장이 곧 적용이다

`themes.xml`이 정하는 **시작 화면은 리소스 한정자**(`values-night`)라 런타임에 바꿀 수 없다.
저장만 하면 어둡게로 둔 사용자가 앱을 열 때마다 흰 화면을 먼저 보고 그 다음 어두운 화면을 본다.
콜드 스타트에서는 수백 ms라 눈에 띈다.

`UiModeManager.setApplicationNightMode`로 시스템에 함께 알린다.
그러면 앱의 `Configuration`이 바뀌어 시작 화면까지 맞는다. **API 31 미만에는 이 방법이 없어**
그 기기에서는 시작 화면 한 번의 어긋남이 남는다.

저장(`ThemePreferences`)과 시스템 통보(`ThemeModeApplier`)는 **따로 둔다.**
한쪽은 값을 남기는 일이고 다른 쪽은 액티비티 재생성까지 부르는 일이라 무게가 다르다.
저장소 안에 숨기면 그 무게가 호출하는 자리에서 보이지 않는다.

순서는 설정 화면이 정한다. 위젯 설정이 `setTextColor()` 뒤에 `refresh()`를 부르고,
한도 설정이 저장 뒤에 판정을 부르는 것과 **같은 모양**이다.

```kotlin
themePreferences.setThemeMode(mode)
themeModeApplier.apply(mode)
```

**DataStore가 단일 진실이다.** 시스템 호출은 적용 수단일 뿐이라 값을 읽을 때는 보지 않는다.

> `MODE_NIGHT_AUTO`가 '시간 기반 자동'이 아니라 **'앱별 지정을 거두고 기기 설정으로 되돌림'**인지는
> 실기기에서 확인했다. '시스템 설정 따름'으로 둔 채 `cmd uimode night yes/no`를 오갔을 때
> 앱 구성의 `night` 플래그가 함께 바뀌었다.

### 사용량 색은 라이트/다크로 나눈다

#### 배경을 잘못 잡고 있었다

막대와 범례는 대부분 `Card` 안에 있다. Material3 카드의 바탕은 `surfaceContainerHighest`인데
`TracePhoneTheme`이 그 토큰을 지정하지 않아 **M3 기본값이 그대로 쓰인다**
(라이트 `#E6E0E9`, 다크 `#36343B`). 화면 바탕색이 아니라 이 값이 실제 배경이다.

그 배경으로 잰 비텍스트 대비(기준 3:1):

| 색 | 라이트 카드 | 다크 카드 |
|---|---|---|
| 모바일 주황 `#E8833A` | 2.09 | 4.52 |
| Wi-Fi 파랑 `#3A78E8` | 2.94 | 2.94 |
| 직접 사용 초록 `#3AA76D` | 2.34 | 4.05 |
| 백그라운드 보라 `#8A5CC7` | 3.65 | 2.59 |
| 구분 없음 회색 `#9AA0A6` | 2.04 | 4.65 |

**라이트에서 넷, 다크에서 둘이 미달이었다.** 요금이 붙는 쪽인 모바일이 가장 안 보였다.

#### 하나의 값으로는 양쪽을 만족시킬 수 없다

라이트 카드(휘도 0.760)에서 3:1이려면 색 휘도가 **0.207 이하**,
다크 카드(0.035)에서 3:1이려면 **0.207 이상**이어야 한다.
두 구간이 한 점에서 겨우 스치므로 테마 분기는 선택이 아니라 필수다.

| 의미 | 라이트 | 다크 |
|---|---|---|
| 모바일 | `#A04B00` | `#F5904A` |
| Wi-Fi | `#1F5FCC` | `#7AABFF` |
| 직접 사용 | `#00713F` | `#52BD82` |
| 백그라운드 | `#7A4BB5` | `#C095FF` |
| 구분 없음 | `#5E6469` | `#A4AAB1` |

원본을 OKLab으로 옮겨 **색상과 채도는 유지한 채 명도만** 재조준했다.
색상 이동은 최대 2°라 '따뜻한 색 = 모바일'이라는 구분이 그대로다.
이 불변식은 테스트가 채널 순서(`red > green > blue`)로 고정한다.

#### 동적 색상에는 휩쓸리지 않는다

`LocalUsageColors`는 `colorScheme`이 아니라 `useDarkTheme`을 보고 고른다.
API 31+에서 동적 색상 경로를 타더라도 사용량 색은 흔들리지 않는다.
`surfaceContainerHighest`는 배경화면에 따라 색조만 바뀌고 톤은 고정이라(tone 90 / 22)
최악을 잡아도 4.4:1이 나온다. **`Theme.kt`의 동적 색상 로직은 손대지 않았다.**

> **이 보호에는 구멍이 있었다 (2026-09-11 발견·수정).**
> `LocalUsageColors`가 지키는 것은 회선·상태 색뿐이고, **한도 진행 막대는 그 밖에 있었다.**
> `MonthlyLimitProgressCard`가 `colorScheme.primary`를 쓰고 있어서 막대 색이 배경화면에서 나왔다.
> 아래 「한도 막대는 분류 색의 언어를 쓰지 않는다」에 경위와 조치를 적었다.

#### 대가 — 칸 사이 1dp 틈

다섯 색을 같은 휘도로 맞추면 팔레트 내부 상호 대비가 1.0~1.04가 된다.
맞붙여 그리면 색상 차이만 남아 색각 이상 사용자에게는 경계가 사라진다.

휘도를 어긋나게 배치해 푸는 건 불가능하다 — 라이트에서 Y ≤ 0.207 제약 아래
다섯 색이 서로 3:1을 만족할 수 없다. 칸 사이를 1dp 띄워 트랙 색이 비치게 한다.
그래프의 쌓은 막대도 두 회선을 모두 쓴 막대만 띄운다.

#### 위젯은 팔레트를 쓰지 않는다

위젯 막대는 배경화면 위에 놓여 **흰 벽지와 검은 벽지 양쪽에서** 읽혀야 한다.
현행 파랑(휘도 0.20)은 4.17 / 5.03으로 둘 다 통과하지만,
새 라이트 Wi-Fi는 검은 벽지에서 3.56, 새 다크 Wi-Fi는 흰 벽지에서 2.31이다.
**제약이 다르다.** 값이 같아 보이더라도 별칭으로 묶으면 앱 색을 손볼 때 위젯이 깨진다.

`PROGRESS_COLOR` → `LIMIT_PROGRESS_COLOR`로 이름을 바꿔 'Wi-Fi'가 아님을 드러냈다.

### 한도 막대는 분류 색의 언어를 쓰지 않는다

#### 같은 화면에서 뜻이 겹쳤다

요약 화면은 `MonthlyLimitProgressCard`(한도 진행 막대)와 `UsageTotalsCard`
(모바일/Wi-Fi 분할 막대 + 이름표)를 **카드 하나 간격으로** 세로로 붙여 놓는다.

한도 막대의 정상 구간 색이 `colorScheme.primary`였다. `Theme.kt`가 API 31+에서
동적 색상을 타므로 **이 값은 사용자의 배경화면에서 나온다.** 벽지가 따뜻한 색이면
한도 막대가 주황이 되고, 바로 아래에 '모바일'이라고 적힌 주황 막대가 놓인다.

색으로 뜻을 구분해 놓고선, 정작 그 규칙 밖에 있는 막대가 같은 화면에서 규칙을 흉내 냈다.

#### 한도 진행은 분류가 아니다

회선(모바일·Wi-Fi)과 상태(직접 사용·백그라운드)는 **분류**다. 한도 진행은 분류가 아니라
**진행**이다. 분류 색의 언어를 빌려 쓸 이유가 없고, 빌리면 이렇게 충돌한다.

정상 구간을 `onSurfaceVariant`로 내렸다. M3는 중립 계열의 채도를 낮게 묶어 두므로
배경화면이 무엇이든 회색 언저리에 머문다. **분류 색과 겹칠 수가 없다.**

초과 구간의 `colorScheme.error`는 그대로 두었다. 동적 색상을 타지 않기 때문이다 —
`dynamicLightColorScheme31`이 `lightColorScheme$default`를 마스크 `62914560`
(비트 22~25 = error·onError·errorContainer·onErrorContainer)으로 호출해
그 네 값을 기본값에 맡긴다. 바이트코드로 확인했다.

#### 고치려다 기존 결함을 찾았다

'오늘' 눈금(`onSurface`, 폭 3dp)은 채움 위에 놓일 수도 트랙 위에 놓일 수도 있다.
톤으로 대비를 재 보니 **채움 안에 들어가면 이미 안 보이고 있었다.**

| 눈금 vs 채움 | 라이트 | 다크 |
|---|---|---|
| 고치기 전(채움 = primary) | 2.65 | 1.32 |

색상 차이로만 겨우 버티고 있었고, 채움을 중립색으로 내리면 그 마지막 버팀목마저 사라진다.

**한 가지 색으로는 풀 수 없다.** 라이트에서 채움이 트랙(tone 90)·눈금(tone 10)
양쪽과 3:1이려면 tone 44~54여야 하고, 다크에서는 트랙(tone 30)과 눈금(tone 90) 사이에
그런 톤이 **아예 없다.**

그래서 눈금이 **자기가 놓인 바닥의 반대색**을 쓰게 했다. 채움 안이면 트랙 색(`surfaceVariant`),
트랙 위면 글자색(`onSurface`)이다. 판정은 `markerRestsOnFill` 순수 함수가 한다.

**이 규칙은 나중에 앱 목록 막대도 함께 쓰게 되어 `ui/component/BarMarker.kt`로 옮겼다.**

| | 라이트 | 다크 |
|---|---|---|
| 채움 vs 트랙 | 7.24 | 5.49 |
| 눈금(채움 안) vs 채움 | 7.24 | 5.49 |
| 눈금(트랙 위) vs 트랙 | 13.27 | 7.24 |
| 초과 채움(error) vs 트랙 | 5.00 | 5.49 |

#### 위젯은 함께 고칠 수 없다

같은 뜻의 막대가 홈 위젯에도 있고 고정 파랑 `#3A78E8`을 쓴다. 색을 맞추고 싶었지만
**위젯에서는 중립색이 수학적으로 불가능하다.** 위젯 트랙은 '글자색 alpha 0.25를 배경 위에
합성한' 값이라 휘도 여유가 없다.

| 야간 AUTO 모드 | 값 |
|---|---|
| 트랙 휘도 | 0.080 |
| 채움이 트랙과 3:1이려면 | Y ≥ 0.340 |
| 흰 배경화면과 3:1이려면 | Y ≤ 0.300 |

구간이 겹치지 않는다. 주/야로 나눠도 야간이 풀리지 않는다.
그래서 위젯 막대는 색상(hue) 차이로 끝을 드러낼 수밖에 없고, 중립화 대상이 아니다.

**남은 사안:** 위젯 막대 `#3A78E8`은 앱 Wi-Fi와 색상 차 0.5°, 채도 차 0.001이다
(옛 Wi-Fi 값이 그대로 남은 것이다). 위젯에 Wi-Fi가 나오지 않아 틀린 값으로 이어지지는
않지만, 학습된 규칙과는 어긋난다. 고친다면 회선·상태 어느 쪽도 쓰지 않는 색상
(예: 청록 ~200°)으로 옮기는 것이 후보다. **이번에는 하지 않았다.**

#### 테스트로 고정한 것과 못 한 것

`LimitProgressBarTest`가 눈금 위치 판정과 위 대비를 고정한다. 조건을 `<=`에서 `<`로,
중립색 자리를 `primary`로 바꿔 넣어 테스트가 실제로 잡는 것을 확인했다.

**막지 못하는 것이 있다.** Composable이 어느 토큰을 고르는지는 계측 테스트 없이 볼 수 없어,
누군가 `limitStatusColor`를 다시 `primary`로 되돌리는 것은 테스트로 잡히지 않는다.
테스트가 고정하는 것은 그 선택이 기대는 **전제**다.

### 숫자와 단위를 다르게 적는다

값을 통째로 고정폭으로 적으면 단위 앞 공백까지 숫자 한 자리만큼 벌어져
`146.96  MB`처럼 값과 단위가 갈라져 보인다.

`ByteText`가 숫자와 단위를 나눠 그린다.
숫자는 고정폭 그대로 두어 세로로 늘어놓았을 때 자릿수가 맞고,
단위는 한 단계 작은 일반 글꼴로 적어 숫자가 먼저 읽힌다.

나누는 일은 `ByteFormatter.split`이 한다. 표시 규칙이 한 곳에 모여 있어야
`format`과 어긋나지 않는다.

문장 안에 값이 끼어드는 곳(`남은 양 %s · %d일 남음`)에는 쓰지 않는다.
그런 자리에서는 값이 문장의 일부이지 표가 아니다.

### UsageSummaryScreen (메인)

#### 머리말은 제자리에 두고 목록만 움직인다 (2026-09-15)

```
[고정]  한도 카드 · 기간 칩 · 합계 카드 · 정렬 칩
[스크롤] 앱별 목록
```

한도·기간·합계는 목록을 읽는 **동안 계속 견줘야 하는 값**이다. 함께 스크롤되면
어떤 앱이 많이 썼는지 보려고 내린 순간 '무엇에 견주는 중이었는지'가 화면에서 사라진다.

바깥을 `Column`으로 두고 목록만 `LazyColumn`에 담아 `weight(1f)`로 남는 자리를 준다.
머리말이 더 이상 흘러가지 않으므로 **`stickyHeader`도, 그 뒤에 깔던 바탕색도 지웠다.**

> **한때 반대로 했다.** 머리말을 `LazyColumn`의 칸으로 넣어 목록과 함께 올라가게 두면
> 한 번 내릴 때 그 자리를 목록이 넘겨받는다. 화면이 좁은 기기에서 앱을 더 보여주려는
> 선택이었고, 그 자체로는 옳았다. 바꾼 이유는 위에 적은 '견주기'가 더 중요하다고 본 것이다.

##### 대가 — 목록이 짧아진다

머리말이 2340px 중 **약 1100px**을 늘 차지한다. 자세히 보기에서는 다섯 줄 남짓만 보이고
그 이상은 스크롤해야 한다. 더 보고 싶으면 설정에서 **간단히 보기**로 바꾼다
(한 줄이 절반 높이라 열 줄 넘게 들어온다). 두 모양을 고르게 해 둔 것이 여기서 값을 한다.

**머리말은 늘 한 화면에 들어가야 한다.** 넘치면 `weight(1f)`가 0이 되어 목록이 사라진다.
지금은 기본 글꼴에서 절반을 쓰므로 여유가 있지만, 머리말에 무언가를 더할 때 확인해야 한다.

`LazyColumn` 안에서는 높이가 정해지지 않은 칸이 배치를 무너뜨리므로,
'불러오는 중'과 '기록 없음' 안내는 화면 전체가 아니라 정해진 높이의 칸에 담는다.

##### 칩 두 줄은 가로 스와이프가 먹지 않는다

기간 칩과 정렬 칩은 좁은 화면에서 잘리지 않도록 `horizontalScroll`을 쓴다.
그래서 그 줄 위에서는 가로 드래그를 칩 줄이 가져간다 — 칩이 다 보이는 기기에서는
아무 일도 일어나지 않는 셈이다.

**그대로 두었다.** 두 줄을 합쳐 화면의 7% 남짓이고, 칩이 넘치는 기기에서는
칩을 미는 것이 맞는 동작이다. 스와이프는 나머지 영역에서 모두 듣는다.

- 기간 단위 선택: 일 / 주 / 월 / 전체 누적
- 기간 이동: 앱 바의 `<   2026년 9월 3일   >` — 한 칸씩 과거·현재로 이동

이동 규칙

| 상황 | 동작 |
|---|---|
| 다음(오른쪽) | 현재 칸이면 비활성. 미래에는 기록이 없다. |
| 이전(왼쪽) | 저장된 가장 오래된 날짜에 걸치는 칸까지만 활성 |
| 전체 누적 | 이동 개념이 없어 양쪽 모두 비활성 |
| 단위 변경 | 항상 현재 칸에서 다시 시작한다. 단위마다 offset의 의미가 다르기 때문이다. |

**한 주는 월요일에 시작한다.** 기기 로케일을 따르지 않고 고정한다.
로케일에 맡기면 같은 데이터를 보고도 기기마다 '이번 주'의 범위가 달라져 수치를 비교할 수 없다.

현재 칸의 주·달은 **오늘까지만** 포함하고, 지난 칸은 그 주/달 전체를 포함한다.

#### 앱 바가 기간 이동을 맡는다

앱 바 제목이 `데이터 사용량`이라는 **고정 문구**였다. 화면이 하나뿐인 앱에서
그 줄은 아무것도 알려주지 않는다. 그러면서 정작 계속 바뀌는 값(보고 있는 기간)은
목록 위에 48dp짜리 줄을 따로 쓰고 있었다.

자리를 맞바꾼다. 기간 라벨이 제목이 되고 화살표가 앞뒤에 붙는다.

```
  <   2026년 9월 4일        >   설정
  [일] [주] [월] [전체 누적]
```

목록이 시작되는 자리가 48dp 올라가고, 잃는 정보는 없다.
갈 수 없는 방향의 화살표를 숨기지 않고 비활성화하는 규칙은 그대로 가져왔다 —
숨기면 제목의 위치가 흔들려 어느 쪽으로 갈 수 있는지 오히려 알기 어렵다.

#### 앱 행은 보여 줄 값이 있을 때만 늘어난다

한 행에 이름·합계·막대·회선별 값·백그라운드를 모두 적으면 네 줄이 된다.
그런데 실기기에서 대부분의 앱은 한쪽 회선만 쓴다.

```
다음                      111.44 MB   <- 합계
▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬   <- 100% 주황, 단색
111.44 MB           7 KB   <- 합계와 같은 숫자
모바일 백그라운드 26 KB      <- 전체의 0.02%
```

**같은 숫자가 두 번 나오고 막대는 단색이다.** 네 줄 중 세 줄이 값을 되풀이한다.

한쪽 회선이 전체의 1%에 못 미치면 막대와 회선별 값 줄을 접는다.
판단은 `NetworkUsageSplit.isDominatedBySingleKind`가 한다.
데이터에 대한 질문이므로 화면이 아니라 도메인에 둔다.

행 높이가 앱마다 달라지지만 그것을 노린다.
**두 회선을 섞어 쓰는 앱만 커지므로 그 자체가 눈에 띄는 신호가 된다.**
실기기에서 한 화면에 두 줄 보이던 목록이 아홉 줄로 늘었다.

#### 한 줄을 두 칸으로 나눈다

이름·막대·회선별 값이 각각 한 줄을 쓰면 섞어 쓰는 앱의 행이 3줄이 된다.
왼쪽 칸(이름·막대)과 오른쪽 칸(합계·회선별 값)으로 나누면 **아이콘 높이 안에 다 들어간다.**

```
[아이콘]  카카오톡                      <1%  4.22 MB
          ==========-----          2.54 MB  1.67 MB
```

- 아이콘이 이름 줄 안에 있으므로 행 높이와 무관하게 이름과 나란하다
- 합계는 오른쪽 칸의 끝에 정렬되므로 행 높이가 달라도 세로로 줄이 맞는다
- 섞어 쓰는 앱의 행이 3줄에서 2줄로 줄어든다

**회선별 두 값은 막대와 같은 색으로 적는다.** 좁은 칸에 라벨을 다시 넣을 자리가 없어
순서만으로는 매번 왼쪽 막대와 견줘 봐야 한다. 색이 그 일을 대신한다.
팔레트는 카드 배경에서 본문 글자 기준(4.5:1)을 넘도록 고른 값이라 글자로 써도 읽힌다.

#### 48dp가 행 높이의 바닥이다

아이콘 40dp에 위아래 여백 10dp면 행이 60dp다. 아이콘 주위가 대부분 빈 공간이다.

아이콘을 **32dp**, 여백을 **8dp**로 줄여 48dp로 맞춘다.
**여기가 바닥이다.** 더 낮추면 터치 대상이 권장 최소 크기에 못 미쳐,
화면에는 더 들어오지만 정작 누르기 어려운 목록이 된다.
값을 상수로 빼고 그 이유를 옆에 적어 두었다.

#### 행 배경에 크기를 나타내는 띠를 깐다

막대는 **그 앱 안에서의 비율**이라 항상 폭이 100%다. 952 MB 앱과 5 MB 앱의 막대가 같다.

행 배경에 옅은 띠(`onSurface` 알파 0.07)를 **행 높이 전체로** 깐다.
길이는 목록 1위 대비 크기다. 두 가지를 한꺼번에 해결한다.

- 크기 비교가 된다
- **띠가 행 높이를 통째로 덮으므로 행 경계가 눈에 보인다** — 구분선이 필요 없다

높이가 하나도 늘지 않으므로 앞서 얻은 압축 효과를 그대로 유지한다.
구분선을 넣지 않는 이유는 띠 + 구성 막대 + 구분선이 겹치면 가로선이 셋이 되기 때문이다.

#### 띠·몫·합계는 모두 같은 값을 기준으로 삼는다

띠 길이를 처음에는 **정렬 기준값**으로 잡았다. 목록이 그 값으로 줄 서 있어
띠가 위에서 아래로 단조 감소해 계단처럼 읽히기 때문이었다.

그 위에 몫(%)을 얹자 **한 줄 안에서 두 숫자가 어긋났다.** 모바일순으로 볼 때
Instagram은 `65%`인데 띠는 거의 비어 있었다 — 띠는 모바일을, 몫은 합계를 재고 있었다.

셋(띠·몫·합계) 다 **합계**를 기준으로 통일한다.
목록의 순서는 정렬 칩이 말해 준다. 한 줄 안의 표시들이 서로 어긋나는 쪽이 훨씬 나쁘다.

#### 몫을 백분율로 함께 적는다

띠는 '목록 1위 대비'라 아래로 갈수록 짧아진다는 것만 알려 준다.
`18%`를 합계 왼쪽에 적으면 **전체 중 얼마인지**가 숫자로 잡힌다. 행 높이는 늘지 않는다.

- **버림으로 센다.** 0.9%를 1%로 올리면 그런 앱이 수십 개일 때 합이 100%를 훌쩍 넘는다.
- 0이 된 몫은 `<1%`로 적는다. `0%`로 적으면 '쓰지 않았다'로 읽힌다.
- **몫은 합계 왼쪽에 둔다.** 오른쪽에 두면 `5%`와 `<1%`의 폭이 달라 줄마다 합계의
  오른쪽 끝이 어긋나고, 고정폭 글꼴로 자릿수를 맞춰 온 이유가 없어진다.

#### 정렬 기준이 되는 값만 적는다

백그라운드 줄은 정렬 기준이 `MOBILE_BACKGROUND`일 때만 보여준다.

무엇을 기준으로 줄을 세웠는지는 보여야 한다. 백그라운드순으로 정렬해 놓고
그 값을 감추면 순서를 읽을 수 없다. 반대로 합계순으로 보는 사람에게
백그라운드 값은 순위와 무관한 곁가지다.

#### 정렬 칩에서 '순'을 뗀다

`모바일 백그라운드순`은 폭을 맞추려고 `모바일 백그`로 줄여 두었는데,
줄인 말이 되고도 화면 밖으로 잘렸다.

네 칩에서 '순'을 떼면 `합계 · 모바일 · Wi-Fi · 백그라운드`가 되어 넷이 모두 들어가고
말도 온전해진다. 라벨이 합계 카드의 범례와 같은 낱말이 되는 것도 이득이다.

### 조회 조건 기억

마지막으로 고른 **기간 단위와 정렬**, 그리고 **목록 모양**을 DataStore에 저장한다.
'주 + 모바일순'으로 보던 사람은 앱을 다시 열어도 같은 화면에서 시작한다.

**'몇 칸 전인지'는 저장하지 않는다.** 3주 전을 보다가 앱을 껐다고 다음에도 3주 전이 나오면
사용자는 지금이 언제인지부터 다시 파악해야 한다. 시작은 항상 현재 칸이다.

저장 값은 열거형의 **이름 문자열**이다. 순서(ordinal)를 쓰면 나중에 항목을 끼워 넣었을 때
저장해 둔 값이 엉뚱한 항목을 가리키게 된다.

저장된 값은 앱을 열 때 한 번만 읽어 초기값으로 삼고, 이후에는 화면 조작이 원본이다.
계속 관찰하면 칩을 누를 때마다 저장소를 한 바퀴 돌고 와야 화면이 바뀌어 반응이 굼떠진다.

**목록 모양만은 계속 관찰한다.** 이 값은 설정 화면에서 바꾸므로, 한 번만 읽으면
설정을 고치고 돌아왔을 때 목록이 그대로여서 바뀐 줄 모른다.
이동할 수 없는 화살표는 숨기지 않고 비활성화한다. 숨기면 가운데 라벨 위치가 흔들려
어느 쪽으로 갈 수 있는지 오히려 알기 어려워진다.

- 요약 카드: 모바일 합계, Wi-Fi 합계, 전체 합계
- 정렬: 합계순 / 모바일순 / Wi-Fi순 / 백그라운드순 (**기본값 모바일순**)

#### 기간은 좌우로 밀어서도 옮긴다 (2026-09-15)

앱 바의 `<` `>` 화살표와 **같은 일**을 손가락으로 한다. 오른쪽으로 밀면 과거(`<`와 같은 방향),
왼쪽으로 밀면 미래다. 두 조작이 반대 뜻을 가지면 어느 쪽이 맞는지 매번 생각해야 한다.

**화살표는 그대로 둔다.** 스와이프는 스크린 리더에 보이지 않아, 화살표를 치우면
그 사용자에게는 기간을 옮길 방법이 사라진다.

##### 거리와 속도를 함께 본다

```
거리가 72dp를 넘었나            -> 그 방향으로
아니면 속도가 200dp/s를 넘었나   -> 그 방향으로
아니면                          -> 아무 일도 안 함
```

**거리를 먼저 본다.** 천천히 충분히 끌었다면 손을 뗄 때 속도가 0이어도 옮겨야 한다.
반대로 사람은 끝까지 끌지 않고 **툭 튕겨서** 넘기려 하므로, 거리만 보면 짧고 빠른 동작이
통째로 무시되어 앱이 반응하지 않는 것처럼 느껴진다.

끈 방향과 튕긴 방향이 어긋나면 **끈 거리**를 따른다. 손을 떼며 손가락이 되돌아오는
흔한 동작에서 방향이 뒤집히면 안 된다.

판정은 `periodSwipeOf` 순수 함수가 한다. 스와이프는 눌렀는지 아닌지가 화면에 남지 않아,
판정이 틀려도 사용자는 '가끔 안 먹는다'고만 느끼고 원인을 짚지 못한다.

##### 세로 스크롤을 건드리지 않는다

`draggable`은 **가로 방향의 터치 슬롭을 넘은 뒤에야** 포인터를 가져간다.
세로로 훑으면 슬롭을 세로로 먼저 넘어 목록이 가져가고, 슬롭 전의 탭은 아무도 소비하지 않아
줄의 `clickable`에 그대로 닿는다. 실기기에서 넷을 따로 확인했다.

| 확인 | 결과 |
|---|---|
| 세로 스와이프 | 목록이 스크롤되고 날짜는 그대로 |
| 가로 스와이프 6회 | 정확히 6칸 (다중 이동 없음) |
| 줄 탭 | 상세 화면 열림 |
| 오늘에서 왼쪽으로 밀기 | 아무 일 없음 |

**기간이 바뀌면 목록이 맨 위로 돌아온다.** 따로 맞춘 것이 아니라, 바뀌는 동안 잠깐
'불러오는 중' 칸으로 줄었다가 다시 채워지면서 스크롤이 위로 잘린다.

##### 경계에서는 아무 일도 하지 않는다

갈 수 없는 방향으로 밀면 반응이 없다. 그 방향의 화살표가 이미 흐려져 있어
왜 안 되는지는 화면이 말하고 있다. 진동이나 튕김 효과는 넣지 않았다.

#### '오늘'은 현재 칸이 아닐 때만 나온다 (2026-09-15)

과거로 여러 칸 들어간 사용자가 같은 횟수만큼 `>`를 눌러 돌아오지 않아도 되게 한다.
현재 칸에서는 할 일이 없으므로 **자리를 비워** 제목이 넓게 쓰도록 둔다.

나타나는 조건이 `>` 화살표가 켜지는 조건(`isNavigable && !isCurrent`)과 **같다.**
판단할 값을 따로 두지 않고 `canGoNext`를 그대로 썼다.

#### 한도 카드는 기간을 옮겨도 남는다 (2026-09-15)

한때 `selection.isCurrent`일 때만 보였다. 근거는 코드에도 문서에도 없었다.
기술적 사정은 있다 — 이 카드는 **청구 주기**를 보는 것이라 화면의 기간 선택을 따라가지 않고
늘 '지금'을 계산한다. 과거로 가면 '그때 데이터' 위에 '지금 데이터'가 얹히는 셈이었다.

그래도 남기기로 했다. 이 카드가 답하는 질문("이번 달 요금제를 넘기겠는가")은 사용자가
어느 날짜를 들여다보든 달라지지 않고, 카드가 스스로 `9월 1일 ~ 9월 30일`이라고
**기간을 적고 있어** 위의 날짜와 헷갈리지 않는다.

**지난 주기의 한도를 대신 보여주는 방법은 택하지 않았다.** '남은 날수'와 '하루 권장량'이
끝난 주기에서는 뜻이 없어(`0일 남음 · 하루 0 MB`) 카드의 말투 전체가 거짓이 된다.
이 카드는 처음부터 '지금 이 속도면 괜찮은가'를 묻는 도구다.

#### 합계 카드의 큰 숫자는 모바일이다 (2026-09-15)

```
13.59 MB                    전체 2.57 GB
████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
● 모바일 13.59 MB        ● Wi-Fi 2.55 GB
```

여기만 합계를 크게 적으면 **화면에서 가장 큰 숫자가 Wi-Fi로 부풀려진 값**이 되어,
바로 아래 목록으로 눈을 옮기는 순간 기준이 바뀐다. 목록의 큰 숫자는 모바일이다.

합계는 오른쪽에 **Wi-Fi와 같은 크기로** 붙인다. 두 회선을 더한 값이라 어느 쪽 편도 아닌데,
회선 값들보다 크게 적으면 그것이 이 카드의 결론처럼 보인다. 이 앱의 결론은 모바일이다.
색 점도 붙이지 않는다 — 점은 막대의 어느 칸인지 알리는 표시인데 합계에 해당하는 칸이 없다.

큰 숫자에는 스크린 리더 노드를 만들지 않는다(`clearAndSetSemantics`).
같은 값이 아래 범례 줄에 이름과 함께 적혀 있어 두 번 듣게 된다.

#### 앱별 목록은 모바일이 주인공이다 (2026-09-15)

이 앱의 목적은 요금이 붙는 모바일을 얼마나 썼는지 보는 것이다.
그런데 목록의 큰 숫자가 **합계**였다. Wi-Fi로 부풀려진 숫자가 먼저 읽혀 판단을 흐린다.

큰 숫자를 모바일로 바꾸고, 몫(%)도 전체 모바일을 분모로 센다. 한 줄 안의 세 표시
(막대·몫·큰 숫자)가 모두 같은 회선을 재므로 서로 어긋나지 않는다.
Wi-Fi는 작은 글자로 참고만 남긴다.

정렬 기본값도 모바일순으로 옮겼다. 큰 숫자만 모바일로 바꾸면 목록 순서와 숫자가 어긋난다.
**이미 쓰던 기기는 바뀌지 않는다** — 저장된 값이 있으면 그것을 읽으므로 사용자의 선택을
덮어쓰지 않는다.

##### 자는 그 기간의 모바일 합계, 하루 기준은 눈금으로

```
maxBytes           = 그 기간의 모바일 합계
referenceFraction  = 하루 기준 ÷ maxBytes   (기준이 자를 넘으면 null - 눈금을 안 그린다)
하루 기준           = 한도 ÷ 청구주기 일수    (일 보기 + 한도 사용 중일 때만, 그 외 0)
```

가득 찬 막대가 '이 기간에 쓴 모바일 전부'를 뜻하므로 **막대 길이가 곧 그 앱의 몫**이고,
줄에 적히는 백분율과 분모가 같다. 둘이 같은 말을 한다.

자를 정하는 데 두 번 실패했다.

| 자 | 무엇이 잘못됐나 |
|---|---|
| `maxOf(가장 큰 앱, 하루 기준)` | 한도 6 GB/30일이면 기준이 200 MB인데 그날 가장 많이 쓴 앱이 7.37 MB. **모든 막대가 4% 이하**가 되어 비교라는 목적이 사라졌다 |
| 가장 큰 앱 | 1등 줄이 늘 가득 찬다. 막대가 순위만 말하고 크기는 말하지 않는다. 게다가 몫을 함께 적으면 **한 줄 안에서 `54%`와 가득 찬 막대가 어긋난다** |

**데이터와 무관한 외부 상수는 자가 될 수 없다.** 합계를 쓰면 1등 막대가 구조적으로
`1 / 앱 수` 밑으로 내려가지 않는다. 하루 기준은 **눈금 하나**로 옮겼다 —
한도 진행 막대가 이미 쓰던 방식이라 새 어휘도 아니다.

눈금 길이만큼 자란 막대는 하루치를 혼자 다 쓴 앱이라는 뜻이다.

**기준이 자를 넘으면 눈금을 그리지 않는다.** 그 날은 앱을 다 합쳐도 하루치에 못 미쳤다는 뜻이라
눈금을 세울 자리가 없다. 오른쪽 끝에 붙이면 '오늘 쓴 만큼이 곧 하루치'로 읽혀 정반대가 된다.

**'남은 양 ÷ 남은 날수'를 쓰지 않는다.** 그러면 많이 쓴 다음 날 기준이 줄어들어,
같은 사용량인데도 눈금이 왼쪽으로 옮겨 간다. 어제와 오늘을 견줄 수 없게 된다.

**하루 기준은 '일' 보기에서만 쓴다.** 주나 월에 하루치에 눈금을 세우면 맨 앞에 붙은 채
아무것도 말하지 않는다. 기준이 있는 척하면서 실제로는 없는 상태가 가장 나쁘다.

##### 눈금 색 규칙은 두 막대가 함께 쓴다

눈금은 **자기가 놓인 바닥의 반대색**을 쓴다. 채움 안이면 `surfaceVariant`,
트랙 위면 `onSurface`다. 한 가지 색으로 양쪽에서 보이게 하는 것은 불가능하다.

`ui/component/BarMarker.kt`에 규칙을 두어 한도 진행 막대와 앱 목록 막대가 함께 쓴다.
따로 두면 두 막대의 눈금이 서로 다른 조건에서 사라진다.
바닥이 될 수 있는 색이 넷(한도 정상·한도 초과·목록 모바일·트랙)이라 `BarMarkerTest`가 넷 모두를 잰다.

##### 두 가지 모양을 설정에서 고른다

```
DETAILED (자세히)                     COMPACT (간단히)
[아이콘] 카카오톡      22%  800 MB     [아이콘] 카카오톡  Wi-Fi 440 MB  22% 800 MB
         ███████░░░  Wi-Fi 440 MB     [아이콘] 유튜브    Wi-Fi 0 B     27% 980 MB
```

막대를 또렷이 보는 것과 한 화면에 많이 보는 것이 맞바꿈 관계라 한쪽을 고를 수 없었다.
DETAILED는 진한 막대로 비교가 쉽고 줄이 2줄이다. COMPACT는 줄 뒤에 깔린 옅은 띠(alpha 0.07)가
크기를 말하고 1줄이라 두 배로 들어온다.

**띠와 막대를 함께 두지 않는다.** 같은 값을 두 번 그리는 셈이다.
COMPACT에서는 띠가 줄 높이를 통째로 덮어 줄 경계 역할도 겸한다.

##### 보조 값은 정렬 기준을 드러낸다

작은 글자 자리는 평소 Wi-Fi지만, **백그라운드순으로 정렬했을 때는 백그라운드 값**을 적는다.
백그라운드순으로 세워 놓고 그 값을 감추면 순서를 읽을 방법이 없다.
포그라운드 구분이 기록되기 전의 값은 0으로 꾸미지 않고 Wi-Fi로 돌아간다.

`showsBackgroundValue(sortOrder, hasKnownPortion)` 순수 함수가 정하고,
화면과 스크린 리더가 **그 결과를 함께 쓴다.** 예전에는 두 벌의 조건문이 있어
한쪽만 고쳐지면 보이는 것과 들리는 것이 어긋났다. 이제 어긋날 자리 자체가 없다.

##### 남은 어긋남

정렬을 **Wi-Fi순**으로 바꾸면 순서와 큰 숫자가 어긋난다. 큰 숫자를 정렬 기준값으로 바꾸는 쪽이
더 나쁘다 — `MOBILE_BACKGROUND` 정렬에서 `sortKeyOf`는 포그라운드 구분이 없는 앱에 0을 돌려주므로,
데이터를 분명히 쓴 앱에 커다랗게 `0 B`가 찍힌다. 목록의 순서는 정렬 칩이 말해 준다.

### AppDetailScreen

앱 하나의 일자별 추이. 모바일/Wi-Fi 구분, 송신/수신 분리 표시.

그래프 세로축에 눈금 용량과 옅은 점선 격자선을 그린다.
막대 높이를 격자선에 대어 보면 대략적인 용량을 읽을 수 있다.

```
  6.00 GB |- - - - - - - - - - - -
          |          #
  4.00 GB |- - - - - # - - - # - -
          |    #     #       #
     0 B  +------------------------
          6/6                  9/3
```

**눈금 값은 실제 최댓값을 그대로 쓰지 않는다.** 최댓값이 `5,131,204,915`바이트라면
축 맨 위에 `5.13 GB`가 찍혀 중간 높이 막대를 암산해야 한다.
`core/ChartAxis.kt`가 눈금 간격을 1·2·5 × 10ⁿ 꼴로 골라
`0 / 2.00 GB / 4.00 GB / 6.00 GB`처럼 읽히는 값만 남긴다.

축 최댓값이 데이터 최댓값보다 높아 위쪽에 여백이 생기는데, 막대가 천장에 붙지 않아 오히려 읽기 좋다.

축 라벨은 `ByteFormatter.formatCompact`로 의미 없는 소수점 이하 0을 떼어 `2 GB`, `600 MB`로 적는다.
소수점을 **전부** 없애지는 않는다. 눈금 간격에 따라 1.5 GB 지점에 격자선이 그어질 수 있는데,
이를 `2 GB`로 적으면 선의 위치와 라벨이 어긋나 그래프를 잘못 읽게 된다.

빈 날짜를 0으로 채울 때는 **저장소 전체의 첫 기록일**을 하한으로 쓴다.
앱별 첫 기록일로 자르면 그 앱이 늦게 쓰이기 시작한 경우 그래프가 선택한 기간보다 늦게 시작해,
화면에 적힌 기간과 그래프 범위가 어긋난다.

바이트를 사람이 읽는 문자열로 바꾸는 변환은 `core/ByteFormatter.kt` 한 곳에 두고 모든 화면이 재사용한다.

### HourlyUsageScreen (시간대별)

앱 상세 화면의 **일자별 막대를 누르면** 그 날을 시간대별로 보여준다.
0시부터 23시까지 24개 막대와, 고른 시간대의 값을 함께 적는다.

#### 막대를 눌러 그 시간대를 읽는다

막대 높이는 세로축 격자선에 대어 봐야 대략적인 값이 나온다.
24개가 나란히 선 시간대별 그래프에서는 그 어림조차 어렵다.
**막대를 누르면 그 시간대의 합계·모바일·Wi-Fi를 숫자로 적는다.**

누르기 전에는 **가장 많이 쓴 시간대**를 골라 둔다. 세 가지를 한꺼번에 해결한다.

- 24개 막대에서 가장 높은 것을 눈으로 찾는 수고를 던다
- 카드가 처음부터 채워져 있어 첫 탭에서 화면이 밀리지 않는다
- 그래프에 칠해진 칸이 있으니 누를 수 있다는 사실이 드러난다

고른 칸은 **위아래로 길게 칠하고 바닥에 밑줄을 긋는다.** 둘 다 필요하다.

- 막대에 테두리를 두르면 사용량이 적은 시간대는 테두리가 실선 하나로 뭉쳐 보이지 않는다.
  칸 전체를 칠하면 값이 0이어도 어디를 골랐는지 보인다.
- 칠한 자리는 막대보다 뒤에 깔리므로 막대가 높을수록 위쪽 자투리만 남고,
  축 꼭대기까지 닿으면 아예 보이지 않는다. 밑줄은 막대 위에 그으므로 높이와 무관하게 남는다.

두 표시 모두 **글자색**을 쓴다. 강조색을 쓰면 Wi-Fi 계열색과 닮아
막대 아래쪽에 Wi-Fi를 조금 쓴 것처럼 보인다. 실기기에서 확인하고 바꿨다.

**한 번 고른 뒤에는 되돌릴 수 없게 두었다.** 같은 막대를 다시 눌러 선택을 푸는 방식은
"눌렀는데 왜 값이 바뀌지" 하는 혼란만 만든다. 다른 막대를 누르면 그쪽으로 옮겨 갈 뿐이다.

선택은 `BarSelection`으로 묶어 `UsageBarChart`에 넘긴다.
고를 막대와 골랐을 때 할 일을 따로 받으면, 누른 막대와 화면에 적힌 값이 어긋난 채로도
컴파일이 통과한다. 탭 판정과 칠하기가 `slotWidthOf` 하나를 함께 쓰는 이유도 같다.

일자별 그래프는 누르면 곧바로 다른 화면으로 넘어가므로 고른 상태로 남지 않는다.
그쪽은 `selectedIndex`를 비워 둔다.

**시스템은 사용량을 시간 단위로 기록하지 않는다.** 기기마다 다르지만 보통 두 시간짜리
구간으로 묶어 두므로, 한 구간이 여러 시간대에 걸친다.
`HourlyBucketSplitter`가 겹친 시간에 비례해 나눠 담는다.

따라서 **시간별 값은 근사치다.** 화면에 그 사실을 밝힌다.
밝히지 않으면 사용자가 정확한 시각으로 오해한다.

나눈 값의 합은 원래 값과 정확히 같다. 정수 나눗셈에서 버려지는 나머지를
가장 많이 겹친 시간대에 몰아주기 때문이다. 그렇게 하지 않으면
시간별 합계와 하루 합계가 어긋나 보인다.

#### 가로축을 몇 곳 짚어 둔다

막대가 24개인데 가로축 라벨이 `0시`와 `23시` 둘뿐이면
`7시~8시`가 어느 막대인지 눈으로 찾을 수 없다. 세어야 안다.

`0 · 6 · 12 · 18 · 23시`에 라벨을 적고 그 자리에 세로 격자선을 긋는다.
라벨만 있고 선이 없으면 그 라벨이 어느 막대를 가리키는지 여전히 세어야 한다.

일자별 그래프도 같은 문제를 안고 있었다. 한 달치면 막대가 서른 개다.
처음과 끝을 포함해 **넷**을 고르게 뽑아 적는다(`9/1 · 9/10 · 9/20 · 9/30`).

`UsageBarChart`는 위치와 글자를 담은 `BarAxisLabel` 목록을 받는다.
그리는 쪽은 어디에 무엇을 적을지 정하지 않는다. 시각인지 날짜인지는 부르는 쪽이 안다.

조회는 `queryDetailsForUid`를 쓴다. 시간이 나뉜 구간들을 한 번에 돌려주므로
하루를 두 번의 호출(모바일/Wi-Fi)로 훑는다. 시간마다 따로 조회하면 48번을 호출해야 하고,
그렇게 해도 시스템이 내부적으로 같은 구간을 비례 배분할 뿐이라 더 정확해지지 않는다.

저장소에는 하루 합계만 쌓으므로 시간별은 시스템에서 직접 읽는다.
시스템의 상세 기록 보관 기간을 벗어난 날짜는 전부 0으로 돌아오며, 이때는 안내 문구를 보여준다.

## 6-1. 사용량 경고

앱 하나가 하루에 쓸 수 있는 **모바일** 데이터 한도를 정하고, 넘으면 알림을 보낸다.
Wi-Fi는 통상 종량이 아니라 경고 대상이 아니다.

```
[빠른 판정 5분 연쇄]  [안전망 15분 주기]  +  [설정 변경 시]  +  [요약 화면 진입 시]
          \_______________/
                  |
         EvaluateUsageAlertsUseCase
                  |
   설정 확인 -> 시스템에서 오늘치 직접 조회 -> 한도 초과 앱 추출
   -> 오늘 이미 알린 UID 제외 -> 알림 + 알린 UID 기록
```

### 판정 주기는 두 갈래다

`PeriodicWorkRequest`의 하한이 15분이라 그보다 촘촘히 돌려면 **일회성 작업이 스스로를 다시 거는**
수밖에 없다. 그래서 둘을 함께 건다.

| 갈래 | 주기 | 역할 |
|---|---|---|
| `FAST_ALERT_CHECK` | 5분 | 실제로 촘촘히 도는 쪽. 판정을 마칠 때마다 자기를 다시 건다 |
| `PERIODIC_ALERT_CHECK` | 15분 | 시스템이 관리하므로 끊기지 않는다. 위 연쇄가 끊기면 되살린다 |

**빠른 갈래는 배터리 최적화 예외일 때만 건다.** 예외가 없으면 App Standby Bucket의
세션 상한을 금세 태우고 남은 시간을 통째로 막혀 **15분보다 나빠지기** 때문이다.
사용자가 설정에서 예외를 끄면 다음 판정 때 스스로 걷힌다.

그 판단은 `work/FastAlertCheckPlan.kt`의 `planFastAlertCheck()`에 **순수 함수로 따로 두었다.**
`work` 패키지에서 조용히 실패할 수 있는 유일한 지점이라서다 —
화면이 깨지면 바로 보이지만 여기가 뒤집히면 아무 일도 일어나지 않고,
며칠 뒤 "알림이 안 왔다"로만 드러난다. `UsageSyncScheduler`는 그 결과를
WorkManager의 말로 옮기기만 한다.

### 한도는 목록과 직접 입력 두 갈래

```kotlin
data class UsageAlertSettings(
    val isEnabled: Boolean,
    val presetLimitBytes: Long,      // 목록에서 고른 값 (100 / 200 / 300 MB)
    val customLimitMegabytes: Long   // 0이면 쓰지 않음
) {
    val effectiveLimitBytes: Long
        get() = if (customLimitMegabytes > 0) customLimitMegabytes * BYTES_PER_MEGABYTE
                else presetLimitBytes
}
```

목록만 두면 원하는 값이 없을 때 막히고, 입력만 두면 매번 숫자를 쳐야 한다.
**직접 입력이 0보다 크면 그쪽이 우선한다.** 지금 무엇이 적용되는지 헷갈리기 쉬우므로
설정 화면 맨 아래에 실제 적용 값을 적어준다.

직접 입력은 **적용 버튼을 누를 때만** 저장한다.
글자를 칠 때마다 저장하면 "1"을 친 순간 1MB 한도로 판정이 돌아 알림이 쏟아진다.

### 저장소를 거치지 않고 시스템에서 직접 읽는다

판정에는 가장 최신 값이 필요한데 저장소는 6시간 주기로만 갱신된다.
같은 이유로 판정 경로에서는 **저장소에 쓰지 않는다.**
15분마다 140여 행을 쓰면 하루 1만 3천 번의 쓰기가 되는데 판정에 쓰기는 필요 없다.

### 한도를 넘길 때마다 다시 알린다

한도가 50MB면 50MB에서 한 번, 100MB에서 또 한 번, 150MB에서 또 한 번 알린다.
하루 한 번만 알리면 첫 알림 뒤로는 얼마나 더 썼는지 알 길이 없다.
경고의 목적이 "지금 멈출지 판단하게 하는 것"이라면 한 번으로는 부족하다.

**한도의 몇 배를 넘겼는지**를 기준으로 삼는다. `사용량 / 한도`의 몫이 그 값이고,
앱마다 마지막으로 알린 배수를 기억해 그 값이 커졌을 때만 알린다.
같은 구간 안에서 더 써도(50MB → 90MB) 배수가 그대로라 다시 알리지 않는다.

한 번에 여러 배수를 뛰어넘어도 알림은 한 번이다. 15분 사이에 40MB에서 210MB로 뛰었다고
알림 네 개를 쏟아 낼 이유는 없다.

Room에 테이블을 추가하는 대신 DataStore에 **날짜 하나 + `uid:배수` 문자열 집합**을 둔다.
저장된 날짜가 오늘과 다르면 없는 것으로 취급하므로 기록이 날짜별로 쌓여 커지지 않는다.
누적 사용량 DB는 잃으면 복구할 수 없어 파괴적 마이그레이션을 금지해 두었으므로,
테이블 추가는 그만큼 무거운 결정이 된다.

> 한도를 **올리면** 배수가 내려가지만 기록은 낮추지 않는다.
> 낮추면 이미 알린 구간을 다시 알리게 된다.

### 알림 ID는 앱의 UID를 쓴다

고정 ID를 쓰면 나중에 한도를 넘긴 앱의 알림이 앞 알림을 덮어써 사용자가 놓치게 된다.

### 판정 시점을 세 곳에 둔 이유

주기 워커만 두면 설정을 바꾼 뒤 최대 15분 동안 아무 일도 일어나지 않아
설정이 먹히지 않는 것처럼 보인다. 설정 변경 직후와 화면 진입 시에도 판정한다.
같은 앱은 하루 한 번만 알리므로 판정을 여러 번 해도 알림이 쏟아지지 않는다.

### 받아들인 제약

- **Doze**: 화면을 끄고 폰이 정지 상태면 시스템이 작업을 유지보수 창으로 미룬다.
  15분이 보장되지 않는다. 포그라운드 서비스를 쓰면 해결되지만 상시 알림과 배터리 대가가
  얻는 것보다 크다고 판단했다.
- **제조사 절전**: 삼성 등은 백그라운드 작업을 공격적으로 중단시킨다.
  코드로 해결할 수 없어 설정 화면에 안내와 앱 정보 바로가기를 둔다.

### domain에는 로그를 두지 않는다

`EvaluateUsageAlertsUseCase`는 결과 개수만 돌려주고 로그를 남기지 않는다.
`AppLog`는 `android.util.Log`를 감싼 것이라 domain이 여기 의존하면
JVM 단위 테스트에서 `Method i in android.util.Log not mocked`로 실패한다.
결과 기록은 호출부인 `UsageAlertWorker`가 맡는다.

## 6-2. 포그라운드/백그라운드 구분

"내가 안 보고 있을 때 이 앱이 얼마나 썼는가"를 보여준다.

### 추가 조회 없이 얻는다

`querySummary`는 같은 UID라도 **포그라운드 여부에 따라 버킷을 나눠서** 돌려준다.
실기기에서 확인한 값이다.

```
querySummary가 돌려준 state 종류: [DEFAULT(=백그라운드), FOREGROUND]
UID 수 36, UID당 버킷 수 분포: {2=15, 1=19, 4=1, 3=1}
state별 합 = querySummary 합 (차이 0)
```

이전에는 이 정보를 UID 단위로 합치면서 버리고 있었다.
`bucket.state`를 읽어 포그라운드 몫을 따로 세면 되므로 **조회 횟수가 늘지 않는다.**

`queryDetailsForUidTagState`로 상태별 조회를 따로 하는 방법도 있으나
(36 UID × 2 상태 = 72회에 85ms) 같은 값을 더 비싸게 얻을 뿐이라 쓰지 않는다.

### 상태를 알 수 없는 버킷은 '모름'으로 남긴다

기기에 따라 `STATE_ALL`처럼 구분되지 않은 버킷이 올 수 있다.
그때 포그라운드를 0으로 기록하면 화면에 "전부 백그라운드"라는 사실이 아닌 값이 나온다.
UID의 버킷 중 하나라도 구분되지 않으면 그 UID의 포그라운드 몫을 null로 남긴다.

### 세 갈래로 보여준다

| 표시 | 뜻 |
|---|---|
| 직접 사용 | 앱 화면을 보고 있을 때 쓴 양 |
| 백그라운드 | 그렇지 않을 때 쓴 양 |
| 구분 없음 | 이 구분을 기록하기 전에 쌓인 기록 |

'구분 없음'을 감추지 않는다. 감추면 나머지 두 몫이 100%처럼 보여
실제보다 많이 측정된 것으로 오해하게 된다.

### 회선을 합치지 않는다

행이 `(날짜, uid, 회선)` 단위이므로 포그라운드 몫도 처음부터 회선별로 저장돼 있다.
집계에서 합치지 않고 끝까지 나눠서 들고 간다.

요금이 붙는 쪽은 모바일뿐이다. 합치면 Wi-Fi로 크게 받는 앱에 가려
정작 요금이 새는 앱이 순위에서 밀린다. 실측(2026년 8월)이 그대로 보여준다.

| 앱 | 모바일 백그 | 모바일 합 | Wi-Fi 백그 | Wi-Fi 합 |
|---|---|---|---|---|
| 토스 | 52.5 MB | 96.5 MB | 145.1 MB | 390.1 MB |
| 카카오톡 | 43.7 MB | 142.8 MB | 107.1 MB | 762.0 MB |

토스는 **모바일로 쓴 양의 절반 이상**을 화면을 보지 않을 때 쓴다.
합산 기준으로는 Wi-Fi 390 MB에 묻혀 이 사실이 드러나지 않는다.
반대로 합산 기준 상위였던 인스타그램은 그 대부분이 Wi-Fi라 모바일 기준에서는 대상이 아니다.

정렬 칩도 `MOBILE_BACKGROUND` 하나만 둔다. 경고 알림이 모바일만 보는 것과 기준을 같게 맞춘다.

### 목록에는 백분율을 적지 않는다

상세 화면은 회선별로 세 몫을 모두 보여주므로 **전체 대비** 비율을 적을 수 있고,
세 값의 합이 100%가 된다. 목록에는 '구분 없음' 몫을 보여줄 자리가 없다.
전체 대비로 적으면 '모름'이 비율을 희석해 실제보다 낮게 보이고,
측정된 몫 대비로 적으면 같은 항목에 상세 화면과 다른 백분율이 찍힌다.
둘 다 사용자가 하나를 오류로 읽게 만든다.

> 실제로 겪었다. 같은 인스타그램이 목록에서는 2%, 상세에서는 1%로 나왔다.

그래서 목록은 `모바일 백그라운드 1.69 MB`처럼 **바이트만 적는다.**
바이트 값은 어느 화면에서나 같다.

### 목록에는 모바일 백그라운드만 적는다

처음에는 두 회선을 한 줄에 적었다. 실기기에서 값이 커지자 줄이 넘쳐
`Wi-Fi 14.74` / `MB`로 숫자와 단위가 갈라졌다.

목록의 순위 자체가 모바일 백그라운드 기준이므로, 위에 있는 앱은 이미 모바일 몫이 크다는 뜻이다.
Wi-Fi 값이 없어도 그 줄을 해석하는 데 부족하지 않다. 회선별 전체 그림은 상세 화면이 보여준다.

### 지난 기록 채우기

포그라운드 구분이 기록된 행이 하나도 없으면 최초 백필(90일)을 한 번 더 수행해,
시스템이 아직 보관 중인 기간만큼 지난 기록에 구분값을 채운다.
별도의 '완료 표시'를 저장하지 않고 자료 자체로 판단하므로
한 번이라도 구분값이 저장되면 다시 수행되지 않는다.

## 6-3. 요금제 한도

"이번 달 요금제 10 GB 중 얼마나 남았나"에 답한다. 모바일만 센다.

### 청구 주기는 달력 월이 아니다

통신사 청구일은 1일이 아닌 경우가 많다. 달력 월로 계산하면 정작 중요한 주기 말에
틀린 숫자를 보여준다. 시작일을 입력받아 그 날짜부터 다음 달 같은 날 전날까지를 한 주기로 본다.

**시작일이 그 달에 없을 때**가 이 계산에서 가장 틀리기 쉽다. 31일 시작인데 2월이 오면
그 달의 마지막 날로 줄여 잡는다. 그러면 `1/31 ~ 2/27`, `2/28 ~ 3/30`처럼 이어져
빈틈도 겹침도 생기지 않는다. 건너뛰거나 다음 달로 미루면 하루가 어느 주기에도 속하지 않거나
두 주기에 겹쳐, 그 하루의 사용량이 사라지거나 두 번 세어진다.
1년치를 하루씩 훑으며 이 성질을 단위 테스트로 고정했다.

요약 화면의 '월'은 달력 그대로 둔다. 한도 카드와 위젯에만 주기 날짜를 명시한다.

### 사용량은 저장분 + 시스템의 오늘치

저장된 값은 6시간마다 갱신되므로 그것만 쓰면 최대 6시간 묵은 숫자가 나온다.
한도는 "지금 얼마나 썼는가"가 전부라 그 값으로는 쓸모가 없다.

`readMobileUsageForPeriod`가 저장분(어제까지)과 시스템의 오늘치를 합친다.
오늘치를 저장분에서 빼 두어 두 번 세지 않는다.
권한이 없어 시스템을 읽지 못하면 저장된 오늘치로 물러선다. 0을 돌려주면 한도가 갑자기
줄어든 것처럼 보인다.

**화면과 위젯이 이 함수 하나를 함께 쓴다.** 각자 계산하면 홈 화면과 앱 안의 숫자가 달라지고,
어느 쪽이 맞는지 사용자가 판단할 방법이 없어 둘 다 믿지 못하게 된다.

### 막대에 '오늘' 눈금을 긋는다

`1.19 GB / 6 GB · 19%`만으로는 이 속도가 괜찮은지 알 수 없다.
9월 4일이면 주기의 13%가 지났으니 19%는 빠른 것인데,
그것을 알려면 날짜를 세어 나눠 봐야 한다.

진행 막대의 **주기가 지난 만큼의 자리**에 눈금을 긋는다.
막대가 눈금을 넘어섰으면 빠른 것이고 못 미치면 여유가 있는 것이다. 계산이 필요 없다.

`LinearProgressIndicator`로는 눈금을 그을 수 없어 막대를 직접 그린다.

눈금이 무엇인지는 주기 줄의 `13% 지남`이 설명한다.
눈금만 그어 두면 그게 무엇을 가리키는지 알 수 없다.

판단은 `MonthlyLimitStatus.pace()`가 한다. 세 갈래다.

| 값 | 조건 |
|---|---|
| `FASTER` | 사용 비율이 주기 진행보다 5%p 넘게 앞섬 |
| `ON_TRACK` | 차이가 5%p 이내 |
| `SLOWER` | 사용 비율이 주기 진행보다 5%p 넘게 뒤짐 |

**5%p의 여유를 두는 이유**는 하루 이틀 치의 출렁임에 문구가 바뀌면
그 말을 믿지 않게 되기 때문이다.

지난 날수는 **오늘을 포함해** 센다. 오늘 쓴 양이 이미 `usedBytes`에 들어 있으므로
견주는 두 값의 기준일이 같아야 한다. 어긋나면 매일 아침 '빠름'으로 읽힌다.

한도를 이미 넘겼으면 속도를 적지 않는다. 넘겼다는 사실이 속도보다 앞선다.

### 카드는 네 줄이다

```
요금제 한도            9월 1일 ~ 9월 30일 · 13% 지남
1.19 GB / 6 GB                        19% · 빠름
================|-------------------------
남음 4.81 GB · 27일 · 하루 178.26 MB
```

한때 여섯 줄이었다. 남은 양·하루치·속도가 각각 한 줄을 쓰면서
**이 카드 혼자 화면의 4분의 1을 먹었다.** 셋 다 한 줄에 들어갈 만큼 짧은 문장인데도.

**줄마다 한 가지만 말하도록 묶는다.**

| 줄 | 말하는 것 |
|---|---|
| 1 | 주기 — 언제부터 언제까지, 얼마나 왔나 |
| 2 | 사용 — 얼마나 썼나, 속도는 어떤가 |
| 3 | 막대 |
| 4 | 남은 것 — 양·날수·하루치 |

경과율을 주기 줄로 올린 것이 핵심이다. 넷을 한 줄에 몰아넣었을 때는
좁은 기기에서 `하루 178.26 MB`의 단위가 잘렸다. 이제 남은 것 줄이 가로폭을 통째로 쓴다.

**예상보다 빠르면 2번 줄이 경고색이 된다. 막대는 그대로 둔다.**
막대의 빨강은 '한도를 넘겼다'는 뜻으로 아껴 두어야 두 상태가 구분된다.

사용 비율에는 고정폭 글꼴을 쓰지 않는다. 세로로 나열되는 값이 아니라 자릿수를 맞출 이유가 없고,
고정폭에서는 구분점과 공백까지 숫자 한 자리 폭을 차지해 `19%  ·  빠름`처럼 벌어진다.

### 한도는 GB로 입력받는다

요금제가 GB로 표기되므로 그대로 옮겨 적을 수 있다. MB로 받으면 10 GB 요금제에
10000을 넣어야 해서 자릿수를 세다 틀린다. 저장은 MB로 하고 화면에 보일 때만 GB로 되돌린다.
`5.5` 같은 요금제가 있어 소수점 하나를 허용한다.

### 80%와 100%에서 각각 한 번

다 쓰고 나서 알리면 늦다. 지점마다 주기당 한 번만 알리고, 주기가 바뀌면 다시 알린다.
'이미 알린 지점'은 **주기 시작일 + 지점 이름 집합**으로 남긴다.
저장된 시작일이 지금 주기와 다르면 없는 것으로 보므로 지난 주기 기록이 쌓이지 않는다.

알림 ID는 하나만 쓴다. 앱별 경고와 달리 한도는 기기에 하나뿐이라 80% 알림이 100% 알림으로
대체되는 것이 자연스럽다. 둘이 나란히 남으면 이미 지난 80% 알림이 지금 상태처럼 보인다.
앱별 경고가 알림 ID로 UID를 쓰므로 겹치지 않게 정수 범위 끝(`Int.MIN_VALUE`)을 쓴다.

## 6-4. 홈 화면 위젯

Glance(`androidx.glance:glance-appwidget` 1.2.0)로 만든다. 1.3.x는 아직 alpha라 쓰지 않는다.

### 크기에 따라 담는 양을 달리한다

기본 크기는 4x2다. 진행률만이면 한 칸으로 충분하지만 많이 쓴 앱까지 보여주려면 두 칸이 필요하고,
사용자가 직접 늘려야 목록이 나온다면 있는 줄도 모르고 지나친다.
한 칸으로 줄이면 진행률만 남는다. 좁은 위젯에 목록까지 넣으면 글자가 잘려 아무것도 읽히지 않는다.

한도를 정하지 않았어도 사용량은 보여준다. 위젯을 올려 둔 사람은 숫자를 보려는 것이지
설정하라는 안내를 보려는 것이 아니다.

### 의존성은 Hilt EntryPoint로 얻는다

`GlanceAppWidget`은 시스템이 만들기 때문에 Hilt가 생성 시점에 개입할 수 없다.
`EntryPointAccessors.fromApplication`으로 애플리케이션 컴포넌트에서 필요한 것만 꺼내 쓴다.

### 갱신 시점

| 시점 | 이유 |
|---|---|
| 15분 주기 경고 워커 | 앱이 꺼져 있어도 위젯이 최신을 유지하는 주된 경로 |
| 6시간 주기 동기화 | 저장된 값이 바뀌었으므로 |
| 설정에서 한도를 바꿀 때 | 방금 바꾼 값이 곧바로 보여야 한다 |
| 시스템 주기(30분) | 위 셋이 모두 실패했을 때의 마지막 안전장치 |

### 글자색과 투명도는 사용자가 고른다

위젯은 배경화면 위에 놓인다. **기기 테마는 배경화면이 밝은지 어두운지 알지 못한다.**
어두운 배경화면에 밝은 테마를 쓰면 검은 글자가 묻힌다. 배경화면을 아는 것은 사용자뿐이다.

| 설정 | 값 |
|---|---|
| 글자색 | 자동(테마 따름) / 흰색 / 검정 |
| 배경 투명도 | 0 ~ 100%, 5% 간격 |

'투명도'라는 이름 그대로 저장한다. 화면에서는 투명도로 말하고 코드에서는 불투명도로 계산하면
어느 쪽이 100인지 매번 되짚어야 한다. 그리기 직전에 한 번만 뒤집는다.

**야간 모드를 직접 판단한다.** Glance의 `ColorProvider`는 색 하나 또는 색 리소스만 받는데,
투명도를 적용하려면 실제 색 값이 필요하고 리소스는 런타임에 알파를 바꿀 수 없다.
`provideGlance`가 받은 `Context`에서 야간 모드 여부를 읽어 색을 고른다.

**진행 막대만 고정색이다.** 글자색을 따라 바뀌면 '넘겼는지 아닌지'를 색으로 알 수 없게 된다.
어떤 배경화면 위에서도 읽히는 진한 파랑·빨강을 쓴다.
다만 막대의 빈 부분은 글자색을 옅게 깐다. 고정색으로 두면 배경을 투명하게 했을 때
배경화면과 겹쳐 막대의 끝이 어디인지 알 수 없다.

슬라이더는 **손을 뗄 때만 저장한다.** 끄는 내내 저장하면 한 번 끌 때마다 수십 번을 쓰고
그때마다 위젯을 다시 그리게 된다.

### 설정 변경은 화면 수명과 분리한다

설정 저장 뒤에는 판정과 위젯 갱신이 이어지는데, 이 둘은 시스템 조회를 포함해 시간이 걸린다.
`viewModelScope`에서 돌리면 사용자가 적용을 누르고 곧바로 뒤로 나갈 때 화면과 함께 취소된다.
**실기기에서 실제로 겪었다.** 화면에는 바뀐 값이 보이는데 위젯은 옛 값이 남았다.

`@ApplicationScope`(SupervisorJob)를 두고 설정을 바꾸는 일은 모두 그 스코프에서 실행한다.
값을 읽는 쪽(StateFlow)은 화면이 살아 있는 동안만 필요하므로 그대로 `viewModelScope`를 쓴다.

## 6-5. 접근성

막대를 눌러 값을 보는 기능을 만들어 놓고 **스크린 리더로는 그 막대를 고를 수조차 없었다.**
`Modifier.semantics`가 프로젝트 전체에 한 번도 없었다.

### 막대를 개별 노드로 만든다

"24개면 스와이프를 24번 해야 한다"는 걱정은 전제가 틀렸다.
**손가락으로 훑으면 제스처 한 번으로 24개를 쭉 듣는다.**
이것이 눈으로 막대를 훑는 것과 대응하는 유일한 경험이고,
요약 하나로는 "저녁에 몰려 있다"를 전달할 수 없다.

24번 스와이프가 실제로 아픈 경우는 **그래프를 지나 아래로 가려는 사람**뿐이다.
그건 노드를 없앨 문제가 아니라 건너뛸 길을 주는 문제다.

- 섹션 제목에 `heading()` — 제목 단위 이동으로 그래프를 한 번에 건너뛴다
- 막대 수 상한 31 — '전체 누적'은 오래 쓰면 막대가 수백 개다.
  그만큼 많으면 막대 하나가 1픽셀도 안 되어 **눈으로도 고를 수 없다**

### 투명 겹칩으로 트리를 만든다

캔버스는 그대로 두고 같은 자리에 **아무것도 그리지 않는 칸**을 겹친다.
배경도 테두리도 없으니 화면에 보이는 모습은 달라지지 않는다.

**`clickable`을 쓰지 않고 `semantics { onClick }`만 쓴다.**
`clickable`은 최소 터치 크기(48dp)를 강제해서, 칸 하나가 13dp인 그래프에서는
이웃 칸의 터치 영역이 겹쳐 **지금 잘 도는 탭 판정이 깨진다.**

> 실기기 덤프로 확인: 막대 노드의 폭이 36px(≈13dp)로 유지됐다.
> `clickable`이었다면 132px로 부풀어 겹쳤을 자리다.

이 때문에 접근성 검사기가 '터치 대상이 작다'고 경고한다.
화면 모습을 바꾸지 않으려고 **일부러 남긴 것**이니 `clickable`로 되돌리면 안 된다.

### 탐색과 선택을 타입으로 나눈다

일자별 그래프는 누르면 다른 화면으로 넘어가 선택 상태가 남지 않는다.
거기에 "선택 안 됨"을 서른 번 읽어 주면 안 된다.
`BarInteraction`을 `Navigate`와 `Select`로 나눠 이 차이를 타입으로 드러낸다.

### 축 눈금은 노드로 만들지 않는다

눈금이 있는 이유는 **막대 높이를 값으로 환산하기 위해서**다.
막대마다 정확한 값을 직접 읽어 주므로 스크린 리더에게 눈금은 환산할 대상이 없는 숫자다.
대신 축이 정하는 문맥만 제목이 요약으로 읽는다.

제목에 붙이는 이유가 있다. 그래프를 감싼 `Box`에 붙이면 자손이 있는 비병합 노드라
**포커스 대상이 되지 않아 아무도 못 듣고**, `Canvas`에 붙이면 두 번 탭할 때
포커스 사각형 한가운데에 실제 터치가 합성되어 **엉뚱한 가운데 막대가 선택된다.**

요약이 말하는 세로축 최댓값은 `barChartAxisMaxBytes()`로 그래프와 같은 계산을 쓰고,
표기도 `formatCompact`로 축 라벨과 맞춘다. **눈으로 보는 글자와 귀로 듣는 말이 달라선 안 된다.**

### 목록 행은 한 문장으로 읽는다

`clearAndSetSemantics`로 자손을 덮고 라벨이 붙은 한 문장을 대신 읽는다.
`clickable`이 체인에서 **앞에** 있어야 두 번 탭 동작이 살아남는다. 순서가 중요하다.

> 실기기 덤프로 확인: `다음, 합계 111.44 MB` 한 노드로 병합되고
> 앱 이름이 개별 노드로 남지 않았다.

몫(%)도 이 문장에 들어간다. **화면이 `<1%`로 다듬어 적은 값을 낭독이 `0%`로 되돌리면 안 되므로**
문구를 잇는 쪽은 백분율을 다시 계산하지 않고 화면에 적힌 글자를 그대로 받는다.

**화면이 보여주는 조건과 읽어 주는 조건이 어긋나는 것**이 이 화면의 가장 쉬운 실수이고
눈으로는 확인되지 않는다. 조건을 `describeAppUsageRow`로 떼어내 테스트가 고정한다.

### 손대지 않은 것

`UsageSplitBar` / `UsageStateBar` / `LegendItem`은 **바로 옆 숫자를 그림으로 되풀이할 뿐**이다.
노드를 만들면 같은 말을 두 번 듣는다. 새 호출처에도 이름과 값을 함께 두어야 이 규칙이 유지된다.

## 7. 에러 처리

| 상황 | 처리 |
|---|---|
| 사용 정보 접근 권한 없음 | `PermissionRequired` 반환 → PermissionScreen으로 유도. 크래시 금지. |
| `SecurityException` / `RemoteException` | 로그를 남기고 해당 날짜만 건너뜀. 나머지 날짜 동기화는 계속 진행. |
| UID → 패키지 매핑 실패 | 예외 대신 대체 라벨 부여 ("제거된 앱 (uid 10234)" 등) |
| Worker 실행 실패 | `Result.retry()` — WorkManager 백오프에 위임 |

## 9. 권한

```xml
<uses-permission android:name="android.permission.PACKAGE_USAGE_STATS"
                 tools:ignore="ProtectedPermissions" />
<uses-permission android:name="android.permission.QUERY_ALL_PACKAGES"
                 tools:ignore="QueryAllPackagesPermission" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
```

`POST_NOTIFICATIONS`는 Android 13부터 런타임 권한이라 설정 화면에서 요청한다.
그 이전 버전에서도 사용자가 알림을 끌 수 있으므로, 버전으로 나누지 않고
`NotificationManagerCompat.areNotificationsEnabled()`로 실제 상태를 본다.

`QUERY_ALL_PACKAGES`는 Play 스토어 배포 시 정당화 사유 제출이 필요하다.
개인 사용/사이드로드 목적이면 문제없다. 배포 계획이 생기면 재검토한다.

| `AppIdentityResolver` | `PackageManager`와 `Context`를 직접 쓴다. 테스트하려면 모킹 프레임워크(MockK/Robolectric)를 들이거나 패키지 조회를 인터페이스로 분리해야 한다. |
| `SystemUsageReaderImpl` · `UsageSynchronizerImpl` | 협력 객체인 `NetworkStatsDataSource`와 `AppIdentityResolver`가 구현 클래스라 가짜로 바꿔 끼울 수 없다. `UsageRepositoryImpl`은 Room만 만지게 되어 이 목록에서 빠졌다. |
| `DailyUsageSyncWorker` | 위 두 가지에 딸린 문제. `TestListenableWorkerBuilder`로 감쌀 수는 있으나 결국 시스템 조회가 필요하다. |

> `UsageSyncScheduler`도 여기 있었다. **판단만 순수 함수로 떼어 내** 그 부분은 덮었고,
> 남은 것은 "결정을 WorkManager 호출로 옮기는 일"뿐이라 실기기 확인으로 대신한다.
> 테스트할 수 없는 클래스를 통째로 포기하는 대신 **테스트할 수 있는 조각만 꺼내는 방법**이
> 이 프로젝트의 제약(계측 테스트 금지)에서 가장 잘 듣는다.

두 클래스의 동작은 현재 **실기기 검증으로 대신 확인**했다 (특수 UID 라벨 표시, 90일 백필,
3회 재동기화 시 수치 불변). 다만 회귀를 자동으로 잡아주지는 못하므로,
로직이 더 복잡해지면 `NetworkStatsDataSource`와 `AppIdentityResolver`를 인터페이스로 분리해
가짜 구현을 끼울 수 있게 만드는 것이 맞다.

### 실기기 수동 검증

에뮬레이터는 실제 트래픽이 없어 값이 거의 0이다. 반드시 실기기로 확인한다.

1. 권한 안내 화면 → 설정에서 허용 → 자동으로 메인 이동
2. 최초 백필 후 앱 목록에 값이 채워짐
3. **교차 검증**: Android 설정의 데이터 사용량 수치와 같은 기간을 비교.
   오차가 크면 `subscriberId` 처리나 기간 경계를 의심한다.
4. Wi-Fi를 끄고 모바일로 큰 파일을 받은 뒤, 동기화 후 그 앱의 **모바일** 사용량만 증가하는지 확인
5. **중복 집계 회귀**: 같은 날 동기화를 3회 연속 실행 → 수치가 3배가 되지 않아야 한다
6. 기기 날짜를 며칠 앞으로 돌린 뒤 동기화 → 빈 날짜가 백필로 메워지는지 확인

동기화 스케줄 상태 확인:

```
adb shell dumpsys jobscheduler | grep -i tracephone
```

따라서 시간대별 값의 근사 정도도 기기 사이에 다르지 않다.

### 13-2. Gemini 독립 검토 대조

3개 파일 이상 · 도메인 계약 변경이므로 `ask_gemini`로 2차 검토를 받았다.

| 쟁점 | Gemini 의견 | Claude 최초안 | 최종 결정 |
|---|---|---|---|
| Repository 분리 방식 | 인터페이스만 쪼개는 건 과도한 추상화. **구현체를 쪼개라** | 인터페이스 3 + 구현 1 | **Gemini 채택** |
| `UsageBarChart` 526줄 | 우선순위를 올려라 | 언급 안 함 | **채택** |
| Preferences 보일러플레이트 | **최우선**. 제네릭 래퍼로 인터페이스 제거 | 손대지 않음 | **거부** |
| `domain/model` 18파일 병합 | 파일 수가 많다 | 언급 안 함 | **거부** |
| 멀티모듈 배제 | 타당 | 배제 | 일치 |
| Compose 파일 분리 주의 | 상태 호이스팅이 끊길 수 있다 | 언급 안 함 | **채택** |

#### 채택한 이유 — Repository

최초안(인터페이스 3개 + 구현 1개)은 **403줄을 그대로 둔 채 간접층만 늘린다.**
호출부의 가시성만 좁아지고 파일은 하나도 작아지지 않는다. Gemini 지적이 옳다.

#### 거부한 이유 — Preferences

Gemini는 "설정 하나 추가 = 파일 3~4개"를 최대 고통으로 봤다. 파일을 열어 재보니 다르다.

`ThemePreferencesDataStore.kt`는 **전체 55줄, 실제 로직 15줄**이다.
나머지는 import 15 + KDoc 10 + DataStore 선언 4 + 키 상수다.
**반복되던 부분은 이미 뽑혀 있다** — `PreferencesRecovery`(IOException 복구), `EnumPreference`(enum 직렬화).

더 결정적으로 Gemini의 해법은 `domain/preferences` 인터페이스를 지운다.
그 인터페이스가 domain의 Android 의존 0개를 지탱하고
`EvaluateUsageAlertsUseCase`를 JVM에서 테스트 가능하게 만드는 장치다.
게다가 제네릭 get/set 래퍼로는 표현할 수 없는 도메인 메서드가 있다.

```kotlin
suspend fun notifiedMultiplesOn(date: LocalDate): Map<Int, Int>
suspend fun markNotified(date: LocalDate, notifiedMultiples: Map<Int, Int>)
```

**측정된 최고 자산을 15줄 절약과 바꾸는 거래**라 받지 않는다.

#### 거부한 이유 — domain/model 병합

Gemini 근거는 "파일 탐색기 스크롤"이다. 약하다.
한 타입 한 파일은 파일명으로 바로 찾을 수 있고, 묶으면 무관한 변경이 같은 diff에 섞인다.
18파일 885줄(평균 49줄)은 과하지 않다.

### 13-3. 단계별 변경 계획

**원칙: 위험이 낮은 것부터. 단, 무성 실패를 막는 것을 반드시 포함한다.**

#### 1단계 — 큰 파일 분리 ✅ 완료 (2026-09-11)

두 파일을 여덟 개로 나눴다. 결과와 기준은 **2절 「화면 파일을 나누는 기준」으로 옮겼다.**

계획은 요약 화면을 4파일로 적었으나 **5파일로 나눴다.** 선택 칩과 합계 카드를 한곳에 두면
`UsageTotalsCard.kt`라는 이름이 내용의 절반만 설명한다. 파일명이 안을 말하지 못하면 나눈 의미가 없다.

예고했던 `private` → `internal` 승격은 실제로 필요했고, **파일 지역 상태에 기대던 곳은 없었다.**
전부 파라미터로 받고 있어 Gemini가 우려한 상태 호이스팅 문제는 일어나지 않았다.

검증: 빌드 성공 · 단위 테스트 154 / 실패 0 · lint 코드 지적 0건.
실기기(S23+)에서 요약·상세·시간대별 화면과 막대 선택까지 분리 전과 같게 동작하는 것을 확인했다.

#### 2단계 — `work`를 테스트 가능하게 ✅ 완료 (2026-09-11)

`UsageSyncScheduler`가 쥐고 있던 예약 판단을 `work/FastAlertCheckPlan.kt`로 떼어 냈다.
구조와 근거는 **6-1절 「판정 주기는 두 갈래다」로, 테스트는 10절로 옮겼다.**

계획은 `sealed interface`로 적었으나 **nullable 반환**으로 바꿨다.
분기가 둘뿐인데 타입을 두 개 만들면 과한 추상화가 되고,
이 프로젝트는 이미 `MonthlyLimitStatus?`처럼 "없으면 null"을 쓰고 있다.

**테스트가 실제로 잡는지 확인했다.** 조건을 일부러 뒤집으니 6개 중 5개가 깨졌고,
되돌린 뒤 전체 재실행(`--rerun-tasks`)으로 160개 전부 통과했다.

검증: 빌드 성공 · 단위 테스트 160 / 실패 0 · lint 변화 없음.
실기기(S23+)에서 두 작업이 각각 `+4m59s`, `+14m59s`로 걸리는 것을 확인했다.

#### 3단계 — Repository 구현을 실제로 쪼갠다 ✅ 완료 (2026-09-11)

403줄 한 클래스를 셋으로 나눴다. 구조와 근거는 **2절 「사용량 창구를 셋으로 나눈 이유」로,
테스트는 10절로 옮겼다.**

```
UsageRepositoryImpl  403줄  ->  UsageRepositoryImpl    163  (Room만, 생성자 인자 3개)
                                SystemUsageReaderImpl  156
                                UsageSynchronizerImpl  116
```

`FakeUsageRepository`도 76줄 12개 구현에서 **46줄 8개**로 줄었고,
시스템 값만 필요한 테스트는 `FakeSystemUsageReader`만 쓰면 된다.

위험했던 단계라 **두 번에 나눠** 진행하고 사이에서 빌드·테스트를 확인했다.
1차는 `SystemUsageReader` 추출, 2차는 `UsageSynchronizer` 추출과 기간 합계 규칙의 도메인 이동이다.

검증: 빌드 성공 · 단위 테스트 **164 / 실패 0** · lint 변화 없음.
실기기(S23+)에서 한도 카드가 리팩터 전과 같은 `2.5 GB / 6 GB · 41%`를 보이는 것을 확인했다.
**옮긴 규칙이 같은 값을 낸다는 뜻이라 이 단계에서 가장 중요한 확인이었다.**

### 13-4. 테스트 전략

계측 테스트 금지(누적 DB 소실)와 Robolectric 배제(AGP 9.4 조합 미검증) 아래에서
**JVM 순수 테스트로 갈 수 있는 곳**만 고른다.

| 우선 | 대상 | 방법 |
|---|---|---|
| 1 | `work` 예약 판단 | 2단계의 `planAlertCheck` — 순수 함수라 분기 전수 커버 |
| 2 | `data/preferences` enum 복원 | `toEnumOrDefault`는 이미 순수. 알 수 없는 값 / null |
| 3 | `UsageSynchronizer` | 3단계 후 Fake 둘을 주입 — 권한 없음 / 하루 실패 시 건너뜀 / 빈 결과가 기존 행을 지우지 않음 |

`widget` · `ui/settings`는 Compose/Glance 런타임이 필요해 **이번 제약에서는 커버할 수 없다.**
대신 순수 문구 조립(`AppUsageRowDescription` 같은)으로 밀어내는 기존 방식을 유지한다.

## 14. 주기 이력 화면

### 14-1. 왜 만들었는가

한도 기능은 있는데 **한도를 얼마로 잡을지 판단할 근거가 화면에 없었다.**
`GetMonthlyLimitStatusUseCase`는 `cycleContaining(today)`로 **이번 주기만** 계산하고,
`ObserveMonthlyLimitStatusUseCase`는 기간 인자를 아예 받지 않는다.
90일 백필 + 무한 누적으로 데이터는 쌓여 있는데 쓰는 화면이 없었다.

진입은 두 곳 — 요약 화면의 한도 카드 탭, 설정의 요금제 한도 카드 안 `주기 이력 보기`.

### 14-2. `MonthlyLimitStatus`를 재사용하지 않는다

그 모델의 파생값은 전부 '오늘' 기준으로 잘려 있다.

| 파생값 | 끝난 주기에 넣으면 |
|---|---|
| `remainingDays = (today~end + 1).coerceAtLeast(1)` | **항상 1** |
| `elapsedDays = (start~today + 1).coerceIn(1, dayCount)` | **항상 dayCount** → 경과율 100% |
| `pace()` | `progress - 1.0`이라 **초과가 아니면 언제나 '여유'** |

그래서 `BillingCycleUsage`를 새로 두고, **끝난 주기에서 뜻이 있는 것만** 담는다.
`MonthlyLimitStatus`는 위젯·알림·요약 화면이 함께 쓰므로 한 줄도 건드리지 않았다.

`dailyAverageBytes`는 **주기 길이가 아니라 센 날수로 나눈다.** 주기는 28~31일로 길이가 달라
총량만으로는 견줄 수 없고, 진행 중인 주기를 주기 길이로 나누면 실제보다 작게 나와
'적게 쓰는 달'로 보인다.

### 14-3. 한도는 기준선 하나로만 긋는다

한도 설정은 DataStore에 **현재 값 하나뿐**이고 주기별 이력이 없다.
지난 3월에 4 GB였는데 지금 6 GB라면 `5.24 / 6.0 GB · 87%`는 **근거 없는 주장**이다.

> **거짓은 선이 아니라 라벨에서 나온다.** 기준선은 지금의 사실(한도는 6 GB다),
> 막대는 과거의 사실(8월에 5.24 GB 썼다)이다. 둘 다 참인 값을 같은 자에 올린 것이라,
> 사용자가 읽어 내는 "지금 한도로 치면 8월엔 빠듯했겠다"는 **맞는 추론**이다.
> 거짓이 되는 순간은 그 줄에 `87%`나 `남음`/`초과`를 적는 순간이다.

그래서 **줄에는 사용량만 적는다**(총량 + 하루 평균). 그리고 `BillingCycleHistory`에
한도 파생 비율을 만들 수단을 두지 않았다 — 모델 수준에서 비율을 계산할 방법이 없으므로
나중에 누가 무심코 `%`를 적는 일 자체가 어렵다. **정직성을 주석이 아니라 타입으로 지킨다.**

`scaleMaxBytes = maxOf(peakBytes, currentLimitBytes)`로 **한도를 자에 함께 넣는다.**
한도가 최대 사용 주기보다 크면(넉넉한 경우) 자에서 빠져 기준선 자리가 사라지고,
정작 알고 싶은 '얼마나 여유인가'가 없어진다.
**`AppListScale`과 규칙이 다른 지점**이라 그 타입을 쓰지 않는다 —
저쪽은 기준이 자를 넘으면 눈금을 일부러 지운다.

### 14-4. 이번 주기는 목록에서 뺀다

진행 중인 주기(12일치)를 끝난 주기(31일치)와 같은 자에 나란히 놓으면
**"이번 달에 갑자기 줄었다"**로 읽힌다. 맨 위 카드로 빼 성격이 다름을 자리로 알린다.

평균에도 넣지 않는다. 아직 덜 쓴 값이 평균을 끌어내린다.

### 14-5. 반쪽만 기록된 주기는 제외한다

최초 백필은 주기 중간에서 시작하므로 가장 오래된 주기는 거의 항상 반쪽이다.
반쪽을 섞으면 **'주기끼리 견준다'는 목적 자체가 깨진다.**

제외 조건은 `cycle.startDate >= recordsStartDate` 하나다. 빠진 사실은 한 줄로 밝히되
**개수를 적지 않는다** — 빠진 이유가 둘(반쪽 주기, 개수 상한 12)인데 목록 길이를 적으면
그 길이가 상한인 것처럼 읽힌다. 실기기에서 "최대 3개까지"로 잘못 읽히는 것을 보고 고쳤다.

### 14-6. 거슬러 올라가기

`BillingCycle.previousPeriod(period, startDay) = periodContaining(period.startDate.minusDays(1), startDay)`

**3줄로 끝난다.** `periodContaining`의 "빈틈도 겹침도 만들지 않는다"는 불변식 덕분에
시작일 하루 전은 반드시 앞 주기에 속한다. 시작일 31일이 짧은 달에서 줄어드는 경우까지
이 성질이 지켜지므로 달을 빼는 계산을 따로 두지 않는다.

테스트가 이 불변식 자체를 고정한다 — 시작일 6종 × 12개월 루프와, 윤년을 지나는
24회 연속 역추적에서 "직전 주기 종료일 + 1일 == 현재 주기 시작일"을 확인한다.

### 14-7. 재사용한 것

| 기존 | 변경 |
|---|---|
| `GetMobileUsageForPeriodUseCase(period)` | **없음.** "오늘을 포함하지 않으면 저장소만 읽는다"가 이미 들어 있다 |
| `UsageScaleBar` | **없음.** `markerFraction`을 이미 받는다 |
| `observeEarliestRecordedDate()` | **없음** |

`UsageBarChart`는 쓰지 않았다. 세로 기준선 API가 없어 추가하면 `DailyTrendChart`·
`HourlyUsageScreen`·`AppDetailScreen` 세 사용처가 공유하는 컴포넌트를 건드린다.

이번 주기 사용량은 `GetMonthlyLimitStatusUseCase`와 **같은 인자**(주기 전체)로 읽는다.
값은 '오늘까지'와 같지만, 같은 인자를 쓰면 요약 화면 한도 카드와 어긋날 자리가 없다.

### 14-8. 함께 고친 것 — 한도 카드 제목

과거 기간으로 스와이프해도 한도 카드는 **늘 이번 주기**를 보여준다. 이것은 의도이지만
제목이 `요금제 한도`여서 기간 선택을 따라가는 것처럼 읽힐 수 있었다.
`이번 주기 한도`로 바꿔 글자로 못 박았다. 사용처가 한 곳(`MonthlyLimitProgressCard`)뿐이라
위젯·알림에는 번지지 않는다.

카드를 누를 수 있게 만들면서 `semantics(mergeDescendants = true)`는 **쓰지 않았다.**
그러면 막대의 `stateDescription`("주기의 40%가 지났습니다")이 카드 전체 설명에 묻힌다.
실기기 접근성 트리에서 `한도 사용 막대` 노드가 별도로 살아 있음을 확인했다.
`Card(onClick=)`에는 라벨을 넘길 자리가 없어 `semantics { onClick(label) { ... } }`로 따로 붙였다.

## 15. 마지막 확인 시각

### 15-1. 설계가 두 번 뒤집혔다

처음 동기는 "`recordedAtEpochMillis`가 모든 행에 이미 있으니 가장 값싸다"였다.
**결과적으로 그 컬럼을 쓰지 않는다.** 그 경로를 남긴다.

| 안 | 무엇이 틀렸나 |
|---|---|
| 1차 — `MAX(recordedAtEpochMillis)` 전역 | `RECENT_BACKFILL_DAYS = 7`이라 7일보다 오래된 행은 다시 쓰이지 않는다. 9월을 보고 있으면 화면 숫자는 3주 전 것인데 전역 MAX는 오늘을 가리켜 "방금 수집한 기록"이 된다 |
| 2차 — 기간 한정 `MAX` | 두 구멍이 더 있었다 (아래) |
| **3차 — 질문을 바꾼다** | 채택 |

2차 안의 구멍 둘:

1. **집계에는 '한 수집 시각'이 없다.** `upsertAll(entities)`가 **날짜마다** 호출되고
   실패한 날짜는 `continue`로 건너뛴다(`UsageSynchronizerImpl.kt`). 월 보기는 애초에
   30일치가 섞인다. `MAX`는 신선도를 과장하고 `MIN`은 늘 기간 끝을 가리킨다.
   **어느 쪽도 집계를 옳게 설명하지 못한다.**
2. **"안 썼다"와 "확인 못 했다"를 구별할 수 없다.** 오늘 데이터를 전혀 안 쓰면 행이 없어
   `MAX`가 NULL이다. 5분 전에 정상으로 확인했는데도 "기록 없음"이 된다.

### 15-2. 그래서 '나이'가 아니라 '사건'을 말한다

두 구멍은 같은 뿌리다. **"이 집계는 몇 시 것인가"라는 질문 자체에 답이 없다.**

사용자가 정말 알고 싶은 것은 **"앱이 지금 정상으로 돌고 있나"**다.
그래서 보여주는 것을 **데이터의 나이**에서 **앱이 마지막으로 확인한 시각**으로 바꿨다.

> "3시간 전에 **확인함**"은 실제로 일어난 사건을 말한다. 저장할 것이 없었던 날에도
> 확인은 일어났으므로 문장이 깨지지 않는다. 반면 "N 전에 수집한 기록"은 집계 전체의
> 나이를 주장하는데 **그런 값이 존재하지 않는다.**

문구에서 '동기화'·'갱신'이라는 말을 쓰지 않는다. 그것은 값이 바뀌었다는 뜻으로 읽힌다.

**대가**: `recordedAtEpochMillis`는 계속 미사용으로 남고, 6번째 DataStore가 생겼다.
싼 것이 옳은 것을 이기지 않는다.

### 15-3. 기록 조건 — `Success`만으로는 틀리다

```kotlin
if (result is UsageSyncResult.Success && result.syncedDayCount > 0) {
    syncStatusPreferences.recordSuccessfulSync(clock.millis())
}
```

**`syncedDayCount > 0`이 반드시 필요하다.** `Success`는 **모든 날짜가 `continue`로
건너뛰어진 경우에도 반환된다**(`syncedDayCount = 0`). 조건을 `Success`만으로 두면
단 하루도 읽지 못한 동기화가 화면에 "방금 확인함"을 적는다.

반대로 **저장한 레코드 수는 보지 않는다.** 데이터를 한 바이트도 쓰지 않은 날에는
저장할 것이 없지만 확인은 분명히 일어났고, 그것을 '확인 못 함'으로 적으면 거짓이 된다.

`UsageSyncResult`가 `Success`/`PermissionRequired`/`Failure`로 깔끔히 갈리므로
권한 미허용·실패에서는 전진하지 않는다.

### 15-4. 표시

**현재 기간에서만 적고, 과거 기간에서는 숨긴다**(`uiState.selection.isCurrent`).
지난 달의 합계는 확정된 기록이라 "언제 확인했나"가 답할 질문이 아니다.
"3주 전에 확인함"은 정보가 0인데 **"앱이 3주 동안 멈췄나"라는 불안만 만든다.**

| 나이 | 문구 |
|---|---|
| 확인 기록 없음 | `아직 확인하지 않았습니다` |
| 1분 미만 (미래 포함) | `방금 확인함` |
| 1시간 미만 | `%d분 전에 확인함` |
| 24시간 미만 | `%d시간 전에 확인함` |
| 24시간 이상 | `10월 1일에 확인함` |

**색·아이콘으로 강조하지 않는다.** 동기화 주기가 6시간이고 Doze로 몇 시간 밀리는 것이
정상이다(야간 실측 157회/15시간). 어떤 임계값을 잡아도 정상 상태를 빨갛게 칠하게 되고
사용자는 그 색을 무시하는 법을 배운다. 강조가 필요한 지점에서는 색이 아니라
**형식이 바뀐다**(상대 → 날짜). 이것이 "색은 문제가 있을 때만 쓴다"를 지키는 유일한 방법이다.

위치는 **합계 카드 맨 아래**다. 이 화면은 신선도가 균일하지 않다 —
합계 카드·앱 목록은 DB만 읽지만 한도 카드는 오늘치를 `SystemUsageReader`에서 **생값**으로
읽는다. 앱 바나 머리말 최상단에 두면 한도 카드까지 수식해 거짓이 된다.

### 15-5. 깨어나는 간격

고정 틱이 아니라 현재 단계가 정한다(`nextSyncAgeRefresh`).

```
JustNow → 10초   Minutes → 1분   Hours → 10분   Older·NeverChecked → 깨어나지 않는다
```

분류와 간격을 **같은 파일에 둔다.** 단계를 늘리면서 간격을 잊으면 그 단계는 영영
갱신되지 않는데, 그 실수는 화면에 드러나지 않는다.

`SyncAge`가 단계로 나뉘어 있어 같은 단계 안에서 다시 세면 값이 `==`이고,
`StateFlow`는 같은 값을 흘리지 않는다. 깨어나도 **다시 그려지지 않고 스크린 리더가
같은 말을 되풀이하지도 않는다.** `Duration`을 그대로 노출하면 깨진다.

`WhileSubscribed` 안에서 돌므로 화면이 사라지면 저절로 멈춘다.

## 16. 목록 잡음 제거 · 지운 앱 표시 · 주기 예상 · 알림 지점 확장

### 16-1. 정렬 기준값과 '목록에 둘 값'을 나눈다

목록 필터가 `totalBytes > 0`(모바일+Wi-Fi 합계)이어서 **Wi-Fi만 쓴 앱이 모바일순 목록에
`0 B`로 남았다.** 실기기 실측에서 최근 30일 **192개 앱 중 61개(32%)**가 그랬다.
같은 앱의 위젯 쿼리는 이미 `HAVING mobileBytes > 0`으로 걸러, 두 경로의 기준이 달랐다.

`UsageSortOrder.visibleBytesOf`를 새로 두고 필터를 그것으로 바꿨다.

| 정렬 | `sortKeyOf` | `visibleBytesOf` |
|---|---|---|
| TOTAL | 합계 | 합계 |
| MOBILE | 모바일 | 모바일 |
| WIFI | Wi-Fi | Wi-Fi |
| **MOBILE_BACKGROUND** | **모바일 백그라운드** | **모바일 전체** |

> **마지막 줄이 이 분리의 전부다.** 포그라운드 구분이 기록되지 않은 앱은 백그라운드 몫을
> 알 수 없어 정렬 키가 0이다. 그 앱들은 모바일을 분명히 썼는데, 정렬 키로 거르면
> **통째로 사라진다.** 화면은 멀쩡하고 줄만 없어지는 오류다.

같은 함정이 세 번째다 — "큰 숫자를 정렬 기준값으로 바꾸기"를 기각할 때도 근거가 됐다.
두 함수를 합치려는 시도가 보이면 `visibleBytesOf`의 KDoc을 먼저 읽어야 한다.
뮤테이션 확인으로 고정했다: `visibleBytesOf = sortKeyOf(usage)`로 되돌리면
`백그라운드순에서 구분이 없는 앱도 모바일을 썼으면 남는다`가 실패한다.

#### 거르는 자리는 **합계 뒤**다

처음에는 `GetAppUsageUseCase`에서 걸렀다. **실기기에서 무너졌다** —
같은 10월이 모바일순에서 `Wi-Fi 5.49 GB`, Wi-Fi순에서 `6.38 GB`로 보였다.

합계 카드가 `appUsages`를 더해 만드는데 그 목록을 정렬별로 걸러 버려,
**정렬 칩을 눌렀을 뿐인데 그 기간의 Wi-Fi 총량이 달라진 것**이다.
**합계는 기간의 사실이고 목록은 보는 방식이다.** 둘을 같은 값에서 뽑으면 안 된다.

그래서 유스케이스는 예전처럼 `totalBytes > 0`만 거르고,
정렬별 판단은 `UsageSummaryUiState.visibleAppUsages`가 맡는다 —
합계보다 **뒤**에서 파생되므로 합계에 닿지 않는다.

이것도 뮤테이션으로 고정했다: 합계를 `visibleAppUsages`에서 뽑도록 되돌리면
`합계는 정렬을 바꿔도 달라지지 않는다`와 `목록에서 뺀 앱의 사용량도 합계에는 들어간다`가 실패한다.

**고치지 않은 것**: Wi-Fi순·합계순에서는 여전히 큰 숫자가 `0 B`일 수 있다.
큰 숫자는 언제나 모바일이기 때문이고, 이는 13장의 "남은 어긋남" 그대로다.

### 16-2. 지운 앱을 지운 앱이라고 적는다

`AppIdentityResolver.resolveFromStoredPackageName`은 설치 목록에 없는 UID에 대해
**저장해 둔 패키지명을 그대로 라벨로** 썼다. 사용자는 `com.example.app`을 보고,
그것이 지워진 앱이라는 사실은 어디에도 없었다.

이 앱의 존재 이유가 "시스템이 지운 뒤에도 남는 기록"이다.
**앱 자체가 지워진 경우가 그 가치의 정점인데 정작 알아볼 수 없었다.**

`AppIdentity.isInstalled`(기본값 `true`)를 더해 목록 줄과 상세 화면 제목 아래에
`설치되지 않음`을 적는다.

- **'지워짐'이라 단정하지 않는다.** 조회 권한이 그 UID에 미치지 않는 경우도 같은 경로로 온다.
  둘을 구별할 방법이 없으므로 구별하는 척하지 않는다.
- **색을 쓰지 않는다.** 지워진 앱은 문제가 아니라 사실이다.
- **두 레이아웃 모두에 넣는다.** 한쪽에만 두면 모양을 바꿨을 뿐인데 정보가 사라진다.
- 낭독에도 넣는다. 위치는 이름·사용량 다음, 몫·보조값 **앞**이다 — 맨 뒤로 보내면
  보조값과 나란히 놓여 어느 값에 걸리는 말인지 흐려진다.
- `UID_REMOVED` 버킷에는 배지를 붙이지 않는다. 라벨이 이미 그 사실을 말한다.

기본값을 `true`로 둔 덕분에 **기존 테스트가 한 건도 바뀌지 않았다.**

### 16-3. 주기 예상 사용량 — 알림이 아니라 화면

`MonthlyLimitStatus.projectedBytes`를 더했다. 7일이 지나기 전에는 null이다.

> **실측이 설계를 정했다.** `pace()`의 `FASTER`를 그대로 알림 조건으로 쓰면
> **네 주기 중 세 주기가 1일째에 울린다** — 주기 초에는 분모가 작아 하루만 평소대로 써도
> '빠름'이 된다. 예측을 조건으로 바꿔도 네 번 중 한 번은 틀렸다(9월: 7일째에 8.7 GB를
> 예상했으나 실제 5.55 GB).
>
> 알림은 틀리면 대가가 크고 화면에 숫자로 적으면 대가가 없다. **화면에만 적는다.**

`MIN_DAYS_FOR_PROJECTION = 7`은 관측에서 나왔다 — 1~5일째 예상치가 실제의 1.5~2.5배로 튀었다.

표시는 **예상이 한도를 넘을 때만**이다. 넘지 않으면 바로 위 '적정/여유'가 이미 그 말을 하고,
숫자를 하나 더 얹으면 카드가 빽빽해진다. **줄의 등장 자체가 정보가 된다.**
문구는 `이 속도면 13.0 GB` — '넘긴다'고 단정하지 않는다. 예측이지 사실이 아니다.
같은 이유로 색을 쓰지 않는다.

### 16-4. 알림 지점 50·90% 추가

```kotlin
enum class MonthlyLimitThreshold(val percent: Int) { HALF(50), WARNING(80), ALMOST(90), REACHED(100) }
```

**이름이 고르지 않은 이유가 중요하다.** `MonthlyLimitPreferencesDataStore`가 이미 알린 지점을
**열거형 이름 문자열로 저장**한다(`toThresholdOrNull`이 `entries.firstOrNull { it.name == … }`).
`WARNING`/`REACHED`를 이름 바꾸면 저장된 값이 어느 지점도 가리키지 못해
**이번 주기에 이미 알린 지점을 다시 알린다.** 저장 호환이 이름 일관성보다 앞선다.
`지점의 이름과 퍼센트가 짝을 유지한다` 테스트가 이것을 고정한다.

**더하는 것은 안전하다** — 판정은 `entries`를 돌고 중복 방지는 이름 집합이라 둘 다 따라온다.
고친 곳은 `SystemMonthlyLimitNotifier.titleFor` 하나뿐이고, `REACHED`만 전용 문구,
나머지는 기존 문구가 `%d%%`로 퍼센트를 받으므로 **새 문자열이 0개**다.

지점마다 다른 말을 지어내지 않는다. 같은 사실("얼마나 썼다")을 네 가지 말투로 적게 되고
번역할 곳도 그만큼 는다.
